# Component tokens (`--md-comp-*`) for `@windmorph/react`: plan

Status: approved 2026-10-14 with the decisions in §9. Phase 0 (the engine, the generator, the tests, the docs wiring and Card) is built. Written 2026-10-13 against `release/0.1.0` (`7d0390a`), so the file and line references below are as of that commit. **The verified names in §5.0 replace the planned names in §5.1–§5.12.**

**Goal.** An app can restyle every instance of a component, globally or within a scope, from CSS only, without a `className` on each instance. It uses M3's own component token names:

```css
:root, [data-theme] { --md-comp-filled-button-container-color: var(--md-sys-color-tertiary); }
[data-brand] { --md-comp-fab-container-shape: 12px; }
```

**Naming (decided by the owner).** `--md-comp-<component>-<part>-<property>`, with the component and part names taken 1:1 from M3's `md.comp.*` token names. For example, `md.comp.filled-button.container.color` becomes `--md-comp-filled-button-container-color`.

## 1. Prior art (short)

| Library | Component-level styling | What we take |
|---|---|---|
| **Material Web** (`@material/web`, maintenance mode) | CSS custom properties `--md-<component>-<token>`, e.g. `--md-filled-button-container-color`, next to `--md-sys-*`. They're read in shadow DOM with the system token as the fallback. | The model itself: M3 token names as CSS variables that fall back to system tokens. We add `comp-` (see below). |

**Naming trade-off (decided).** `--md-comp-*` matches M3's `md.comp.*` names and our one existing token, can never collide with `--md-sys-*` / `--md-ref-*`, and is greppable. The cost is that it differs from Material Web's `--md-<component>-*` by the `comp-` segment, so a Material Web user can't paste their CSS unchanged. The Customisation guide gets a mapping note (§6.2).

**Curated, because every token is a contract.** A public token can't be renamed or removed without a major version. Adding a token is non-breaking, and so is adding a more specific token *in front of* an existing one in a fallback chain. So we start small and grow on request (⏸ items below can be added later without breaking anything).

## 2. Naming rules

1. **Component and part 1:1 from M3.** Take `md.comp.<component>.<part…>.<property>` and join it with `-`:
   - `md.comp.filled-button.container.color` → `--md-comp-filled-button-container-color`.
   - `md.comp.button.small.container.shape.round` → `--md-comp-button-small-container-shape-round`.
   - `md.comp.outlined-text-field.focus.outline.color` → `--md-comp-outlined-text-field-focus-outline-color`.
2. **Variant names are M3's component names, not our prop values.** `variant="tonal"` maps to `filled-tonal-button`, `variant="standard"` (icon button) maps to `icon-button`, and the FAB `color="primary-container"` maps to `fab-primary-container`. The variant goes in the component segment wherever M3 puts it there.
3. **Size names are M3's.** `xs/sm/md/lg/xl` become `xsmall/small/medium/large/xlarge` (`md.comp.button.xsmall…`). FAB `default/medium/large` become `fab` (baseline), `fab-medium` and `fab-large`. Extended FAB `sm/md/lg` become `extended-fab-small/-medium/-large`.
4. **States use M3's web words, never Compose's:** `hover`, `focus`, `pressed`, `dragged`, `disabled`, `selected`, `unselected`, `error`. They sit where M3 puts them, which is usually right after the component: `--md-comp-filled-card-hover-container-elevation`, `--md-comp-filled-button-selected-container-color`.
5. **Properties use M3's words:** `color`, `shape`, `elevation`, `width` (outline), `height`, `size`, `opacity`. Compose's `LabelTextColor` maps to `label-text-color`, `ContainerShapeRound` to `container-shape-round`, and `ActiveIndicatorColor` to `active-indicator-color`.
6. **Source of truth for each name:** m3.material.io's token tables. Compose's `*Tokens.kt` object and property names are the fallback. Compose files don't carry the `md.comp` string, so every name in §5 that comes only from a Compose object name is marked **(verify)** and must be confirmed against m3.material.io before it ships. Once shipped, it can't change.
7. **Private variables** are `--_md-comp-<set>-<token>`, one per *part* (not per variant). Apps never set them. They aren't documented as API, the same as Pro's `--_wm-*`.

## 3. Scope: which kinds of token to expose

| Kind | M3 examples | Rec. | Why |
|---|---|---|---|
| Container colour (per variant, resting) | `filled-button.container.color`, `filled-card.container.color` | ✅ | The most-asked brand override. Reads a system role by default. |
| Content colour (label text, icon, headline, supporting text, input text) | `filled-button.label-text.color`, `dialog.headline.color` | ✅ | Must be overridable together with the container, or contrast breaks. In Windmorph, the icon colour follows the label (`currentColor`), so the icon token is ✅ only where M3 and our styles paint it separately (chips, list, text field, nav). |
| Shape (resting container) | `button.small.container.shape.round`, `fab.container.shape`, `dialog.container.shape` | ✅ | The second-most-asked override ("our brand is squarer"). Only changes `border-radius` on the root, which the state layer and ripple follow automatically (§10 rule 2). |
| Elevation (resting) | `elevated-button.container.elevation`, `elevated-card.container.elevation`, `dialog.container.elevation` | ✅ | Value is `var(--md-sys-elevation-level-N)`. Skipped where a prop already sets elevation (FAB, toolbar `elevation`). |
| Outline colour | `outlined-button.outline.color`, `outlined-text-field.outline.color` | ✅ | |
| Selected / unselected colours (toggles, filter / input chips, tabs, nav, switch, checkbox) | `filled-button.selected.container.color` | ✅ | Without them, an app that rebrands the container is left with a mismatched selected state. |
| Focus colours that carry meaning (text field focus outline, active indicator, label) | `outlined-text-field.focus.outline.color` | ✅ | Text fields only, where the brand colour is the focus signal. |
| Hover / focus / pressed **elevation** | `filled-card.hover.container.elevation` | ⏸ | Rarely rebranded. Can be added later in front of the resting value without breaking anything. |
| Pressed / selected **shape** (the Expressive morph) | `button.small.pressed.container.shape` | ⏸ | Tied to the morph motion and the connected group's shapes. Add on request. |
| State-layer colour per state | `filled-button.hover.state-layer.color` | ❓ | Our state layer follows `currentColor` (`utilities.css`, `--m3-state-layer-color`), so overriding `label-text-color` already moves it. Per-state colours need the `state-layer` utility to read per-state variables: a small change, but a cross-cutting one. Owner to decide. |
| Disabled colours / opacities | `filled-button.disabled.container.color` + `.opacity` | ⏸ | Fixed by M3 for accessibility (`on-surface` at 10–12% / 38%). Keep them as today's classes. |
| Outline **width**, heights, widths, icon sizes, paddings, gaps | `button.small.container.height`, `button.small.leading-space` | ⏸ | Geometry is coupled to the `size` prop, the corner caps (`min(full, h/2)`), the 48px touch targets, the button-group press expansion and the chip's `--m3-chip-border` padding compensation. Exposing it would freeze the implementation and could break §10. The `size` prop is the API. |
| Typography (`label-text.font/size/weight/tracking`) | `filled-button.label-text.font` | ⏸ | `--md-sys-typescale-*` / `--md-ref-typeface-*` already cover brand type globally. Five tokens per text part would add a lot of contract surface. |
| Motion (springs, durations) | — | ⏸ | System-level (`data-motion`, `--md-sys-motion-spring-*`). |
| Focus indicator colour / width | `*.focus.indicator.color` | ⏸ | System-level (`--md-sys-focus-indicator-*`, `secondary`). Keep it consistent across the app. |
| Size-less shape aliases (non-M3), e.g. `--md-comp-button-container-shape-round` for every size | — | ❓ | Handy ("all buttons square in one line"), but not an M3 name. If the owner wants it, it goes at the *end* of each size's fallback chain (`var(--md-comp-button-small-container-shape-round, var(--md-comp-button-container-shape-round, <default>))`), which can be added later without breaking anything. The plan ships the per-size M3 names only. |

## 4. Mechanism

### 4.1 Reuse and extend the token engine (one source per component)

Every token-bearing component gets a `<component>-tokens.ts` built with `defineComponentTokens`. The core generator writes the CSS, the site's `TokenTable` renders the docs, and the tests read the set. That's the same pipeline Pro already uses, so there's no second mechanism.

The one extension needed: **a public name per variant or size value.** M3 names put the variant in the *component* segment (`filled-button` vs `outlined-button`), while one shared class should read *one* private variable per part. So `ComponentTokenSet` gets an optional `scopes` field:

```ts
// button-tokens.ts (sketch)
export const buttonTokenSet = defineComponentTokens({
  name: 'md-comp-button',            // data-tokens value and private prefix
  tokens: {},                        // tokens with one public name (--md-comp-button-<token>); none here
  scopes: {
    variant: {                       // reads data-variant on the same element
      filled: {
        prefix: 'md-comp-filled-button',
        tokens: {
          'container-color':            { value: color('primary'),           description: 'Container.' },
          'label-text-color':           { value: color('on-primary'),        description: 'Label and icon.' },
          'selected-container-color':   { value: color('primary'),           description: 'Toggle, selected.' },
          'unselected-container-color': { value: color('surface-container'), description: 'Toggle, unselected.' },
          // …
        },
      },
      text: {
        prefix: 'md-comp-text-button',
        tokens: { 'label-text-color': { value: color('primary'), description: '…' } },
        fixed: { 'container-color': 'transparent' },   // private-only: no public name, not documented
      },
      // elevated, tonal → filled-tonal-button, outlined
    },
    size: {
      xs: { prefix: 'md-comp-button-xsmall', tokens: { 'container-shape-round': …, 'container-shape-square': … } },
      // sm → button-small, md → button-medium, lg → button-large, xl → button-xlarge
    },
  },
  derived: {
    // The full-corner cap, so classes never put a private variable after a comma (component.test.ts).
    'container-shape-round-capped': 'min(var(--_md-comp-button-container-shape-round), var(--_md-comp-button-cap))',
  },
});
```

`componentTokensCss` writes, for each scope value:

```css
:where([data-tokens~="md-comp-button"][data-variant="filled"]) {
  --_md-comp-button-container-color: var(--md-comp-filled-button-container-color, var(--md-sys-color-primary));
  --_md-comp-button-label-text-color: var(--md-comp-filled-button-label-text-color, var(--md-sys-color-on-primary));
}
:where([data-tokens~="md-comp-button"][data-variant="text"]) {
  --_md-comp-button-container-color: transparent;
}
```

The existing `tokens` / `states` behaviour is unchanged, so Pro's sets keep generating byte-identical CSS (a test checks this).

`TokenTable` learns `scopes`: one row per public variable, grouped by scope value ("Filled", "Small", …).

### 4.2 Styles read one private variable per part

```ts
// button-styles.ts (sketch): the variant classes disappear into the token set
root: [
  'bg-[var(--_md-comp-button-container-color)] text-[color:var(--_md-comp-button-label-text-color)]',
  'shadow-[shadow:var(--_md-comp-button-container-elevation)]',
  'rounded-[var(--_md-comp-button-container-shape-round-capped)]',
  'data-disabled:bg-on-surface/10 data-disabled:text-on-surface-variant/38', // ⏸ stays a class
],
```

- The root renders `data-tokens="md-comp-button"`, `data-variant`, `data-size` (and `data-color` on the FAB, `data-kind` on chips). These follow §9 ("state exposed as `data-*`"), so they're useful to apps as well. They're new DOM, so DOM-snapshot unit tests change, but pixels don't.
- **Values that aren't exposed (⏸) stay as today's classes.** The core doesn't adopt Pro's "no number in a class" rule. Only exposed values go through tokens, which keeps each component's diff small.
- **Type hints in arbitrary values**, checked with this repo's `cn()` (tailwind-merge 3.7) and Tailwind 4:

  | Class we write | Consumer class | `cn()` result | Rule |
  |---|---|---|---|
  | `bg-[var(--_x)]` | `bg-tertiary` | `bg-tertiary` ✓ | fine as is |
  | `text-[color:var(--_x)]` | `text-tertiary` | `text-tertiary` ✓ | **always** hint `color:` (the `text-` prefix is shared with the type scale) |
  | `shadow-[var(--_x)]` | `shadow-elevation-3` | **both kept** ✗ | **always** write `shadow-[shadow:var(--_x)]`, which merges ✓ (Tailwind 4 compiles all three forms identically) |
  | `rounded-[var(--_x)]`, `border-[color:var(--_x)]`, `outline-[color:…]` | `rounded-corner-small`, `border-primary` | consumer wins ✓ | |

  A lint test (§7.4) rejects un-hinted `text-[var(` and `shadow-[var(`.

### 4.3 How it behaves

| Concern | Behaviour |
|---|---|
| **Defaults identical** | Each private variable defaults to the exact system token today's class uses (`bg-primary` → `var(--md-sys-color-primary)`). Proved by screenshots and a computed-style diff (§7.1). |
| **Runtime cost** | None. No JS, no context, no re-render. A few hundred `:where()` declarations in one generated CSS file, written at build time (`pnpm generate`). |
| **`className` / `classNames` still win** | Classes read private variables. A consumer utility (`bg-tertiary`) conflicts with ours in `cn()` and replaces it (§4.2 table). A consumer can also set the public variable on the instance: `className="[--md-comp-filled-button-container-color:red]"`. |
| **Scope** | Public variables inherit, so setting one on any ancestor (`:root`, `[data-brand]`, a section) restyles every instance inside. **Set them on the component root or an ancestor, never on an inner slot**, because the private variable is resolved on the root. |
| **Nested same components** | Each root re-declares every private variable for its own variant and size, so a parent's resolution never leaks into a nested instance. A completeness test makes sure every scope value declares every private variable that a shared class reads. |
| **ThemeScope, dark mode, contrast** | A default like `var(--md-sys-color-primary)` resolves on the component's own element, so it follows `data-theme` / `data-mode` / `data-contrast` exactly as today. **Pitfall: a public value that itself uses `var()` resolves where it's declared.** `:root { --md-comp-x: var(--md-sys-color-tertiary) }` freezes the *root* theme's tertiary, so a `<ThemeScope theme="forest">` or a dark subtree would still get the root's colour. The docs say to declare role-based values on `:root, [data-theme]` (ThemeScope and Overlay both write `data-theme` on their element, so the value re-resolves in every scope). Literal values (`12px`, `#0050C8`) don't have this problem, but they don't follow dark mode or contrast either. The guide says so. |
| **Overlays** (menu, select, tooltip, dialog, sheet, snackbar, date and time pickers) | They portal to `body`. Tokens set on `:root` / `[data-theme]` reach them. **Tokens set on an arbitrary ancestor of the trigger don't**, because the portal isn't inside it. Overlay already re-applies theme attributes and `dir` (`Overlay.tsx:81`). Proposal (❓): ThemeScope's `className` is carried in `ThemeScopeContext` and re-applied by Overlay on its `display: contents` wrapper, so `<ThemeScope className="brand-a">` with `.brand-a { --md-comp-… }` reaches its overlays. Until then, the docs say: scope overlay tokens via ThemeScope, a `[data-theme]` selector or the overlay's `className`. |
| **Variants and sizes** | Per-variant and per-size public tokens (M3's names), each resolved into one private variable per part. Classes don't branch on variant for exposed values. |
| **Composites** | Split button halves read `md-comp-button` (they use `buttonVariantClasses` today), so `--md-comp-filled-button-container-color` restyles them too, as §3 promises ("an override on Button also applies to the Button inside SplitButton"). The split button only adds its own outer `container-shape` per size. ButtonGroup sets nothing. |
| **Existing `--md-comp-icon-button-icon-color` contract** | Kept: it's the public name of the *standard* icon button's `icon-color` (M3 baseline `md.comp.icon-button.icon.color`). The outlined icon button reads `var(--md-comp-outlined-icon-button-icon-color, var(--md-comp-icon-button-icon-color, <default>))`, so toolbars and app bars that set it to `currentColor` keep tinting outlined buttons exactly as today. The setters (app bar, search, toolbar, dialog close, Pro) need no change. |
| **Internal `--m3-*` variables** | Stay private (`--m3-menu-corner`, `--m3-carousel-item-corner`, `--m3-rail-collapsed-width`, the state layer's). Where an exposed token replaces one (the carousel item shape, the menu shape), the internal variable takes the token as its value, so registered `@property` animations keep working. |
| **Layout safety (§10)** | Only colour, shape, elevation and outline colour are exposed, and none of them touch `position`, `overflow`, `display`, `transform` or box size. Shape changes `border-radius` on the root, which the background-painted state layer follows. Outline *width* and all sizes stay ⏸ for this reason. The layout-override matrix runs unchanged. |
| **Forced colours** | Unaffected: `forced-colors:` classes come later and win. |
| **Precompiled CSS** | `generated/components.css` is imported by `styles.css` (after `theme.css`, before `utilities.css`) and included in `styles.compiled.css` by `build-css.ts`. `check-dist.ts` asserts it's present in both. |

### 4.4 Generator and discovery (minimises merge conflicts)

`packages/react/scripts/generate.ts` gains a step that **discovers** `src/**/*-tokens.ts` (readdir + dynamic import, sorted by path) and writes `src/styles/generated/components.css` (gitignored, like the other generated files). There's no hand-maintained list, so parallel component agents never touch the same line. Each component exports its set from its own block in `src/index.ts` (for example `export { buttonTokenSet } from './components/button/button-tokens'` next to `buttonStyles`), so edits are local and merges are trivial.

Why they differ:

- **Buttons and icon buttons:** M3 Expressive's token sets are `md.comp.button.<filled|elevated|tonal|outlined|text>.*` and `md.comp.icon-button.<standard|filled|tonal|outlined>.*`; `md.comp.filled-button.*`, `md.comp.filled-tonal-button.*`, `md.comp.filled-icon-button.*` and their siblings are marked deprecated, and the Expressive toggle (`selected` / `unselected`) tokens exist only in the new sets. The size sets (`md.comp.button.small.container.shape.round`, `md.comp.icon-button.small.container.shape.round`) are as planned. `--md-comp-icon-button-icon-color` is the baseline set's active name and the existing contract, so it stays; the standard icon button reads `var(--md-comp-icon-button-standard-icon-color, var(--md-comp-icon-button-icon-color, <default>))`, and the outlined one falls back the same way.
- **Menus:** the Expressive sets are `md.comp.menus.*` (common) and `md.comp.menus.standard.*` / `md.comp.menus.vibrant.*`; `md.comp.menu.*` is the baseline set. Items are `menu-item`, not `list-item`.
- **Navigation bar and rail:** the Expressive sets are `md.comp.nav-bar.*` and `md.comp.nav-rail.*`; `md.comp.navigation-bar.*` and `md.comp.navigation-rail.*` are the baseline (pre-Expressive) sets.
- **Toolbars:** `md.comp.toolbar.floating.*` and `md.comp.toolbar.docked.*`.
- **Chips, tabs, dialog, slider, FAB menu:** the icon and label tokens carry M3's `with-icon` / `with-leading-icon` / `with-label-text` segments, the filter chip's unselected colours say `unselected`, and the FAB menu's items are `menu-item`.
- **Scrim:** M3 has no scrim component token (only the deprecated navigation drawer's `md.comp.navigation-drawer.scrim.*`). Recommendation: don't ship `--md-comp-scrim-*`; the system role `--md-sys-color-scrim` already restyles every scrim. If a per-component control is wanted, it's a non-M3 name (`--wm-scrim-*`) for the owner to decide.

- The **`/from-compose` guide** gains "Your `*Tokens` overrides": the Compose `FilledButtonTokens.ContainerColor` maps to `--md-comp-filled-button-container-color`, generated from the `compose` field.

### 6.2 The Customisation guide

Add a section **"Component tokens"** between "The override ladder" and "className and classNames", and add it as rung 1b of the ladder (also in `docs/architecture.md` §8):

1. What they are: the M3 names, `--md-comp-<component>-<part>-<property>`, unset by default, falling back to system tokens.
2. Global, themed and scoped examples. **Declare role-based values on `:root, [data-theme]`** (the resolution pitfall, §4.3).
3. Overlays: what reaches them, and how to scope them.
4. Literal values vs roles: literals don't follow dark mode or contrast. Check contrast yourself.
5. Precedence: system token < component token < `className` / `classNames`.
6. **"Coming from Material Web"**: insert `comp-`, so `--md-filled-button-container-color` becomes `--md-comp-filled-button-container-color` and `--md-outlined-text-field-outline-color` becomes `--md-comp-outlined-text-field-outline-color`. Differences, in a small table:
   - Material Web's single `container-shape` is per size in Windmorph (`button-small-container-shape-round`, …), because Expressive sizes have their own shapes.
   - Expressive-only tokens (toggle `selected-*` / `unselected-*`, sizes) have no Material Web equivalent.
   - Material Web's typography, state-layer, disabled and spacing tokens aren't exposed. Use `--md-sys-typescale-*`, `className` or `classNames` instead.
   - Material Web's `--md-icon-button-icon-color` maps to `--md-comp-icon-button-icon-color`.
7. A link to each component's Tokens table.

## 7. Tests

### 7.1 Defaults are unchanged (the gate for every component PR)

- **Screenshots.** The existing Storybook Playwright suites (`apps/docs/e2e/*.spec.ts`, 30 files with `toHaveScreenshot`) run with **no baseline updates allowed** (`--update-snapshots=none`). Any pixel diff fails the PR.
- **Computed-style snapshot** (more sensitive than pixels, and it catches a 1% colour shift). Phase 0 adds `apps/docs/e2e/computed-styles.spec.ts`. For every story, in light/dark × the three contrast levels × two themes, it records `background-color, color, border-*-color, border-radius, box-shadow, outline-color` for every `[data-slot]` / root element and states (rest, `data-hovered`, `data-selected`, `data-disabled` forced through story args). Phase 0 records it on `main` **before** any token work, and every component PR must match it exactly.
- **Pro unchanged.** Pro's `componentTokensCss` output is byte-identical after the engine extension (unit test with its eight sets, or a fixture copy).

### 7.2 Each token changes what it says (one generic, data-driven spec)

- Each token entry in a set gets test metadata: `paints: { slot: 'root' | '<classNames slot>', property: 'background-color', state?: 'selected' | 'hover' | … }`.
- `apps/docs/e2e/component-tokens.spec.ts` iterates every exported set. For each scope value (variant and size) it opens a `Tokens` probe story for that component, sets the public variable on a wrapper to a sentinel (`rgb(1, 2, 3)` for colours, `7px` for shapes, a sentinel shadow, `0.5` for opacity), forces the state, and asserts the computed property on the slot equals the sentinel.
- It also asserts, once per set: (a) set on `:root` and on an ancestor `div` both work; (b) inside `<ThemeScope theme="forest" mode="dark">` with the role-based value on `[data-theme]`, the colour is forest-dark's role; (c) `className="bg-tertiary"` (or the slot's matching utility) beats the token; (d) for overlay components, a `:root` token reaches the portalled surface.

### 7.3 Coverage (static, Vitest node)

`packages/react/src/tokens/component-coverage.test.ts`, generalising Pro's test:

1. Every private `--_md-comp-<set>-*` read in `src/**/*-styles.ts` and `styles/utilities.css` is defined by that set (tokens, scopes, fixed values or derived values). **This fails when a documented token isn't read.**
2. Every defined token is read by some class or derived value.
3. **Scope completeness:** every scope value of an attribute defines every private variable that the shared classes read.
4. **Contract snapshot:** the sorted list of all public names is compared with a checked-in `packages/react/component-tokens.txt`. Removing or renaming a name fails the test, and adding one needs a reviewed update to the file, so the public-API diff is visible in the PR.
5. **Names:** every public name matches `^--md-comp-[a-z0-9]+(-[a-z0-9]+)*$`, uses only the state words from §2.4, and doesn't contain a Compose word (`hovered`, `focused`).

### 7.4 Lint-style guards

These go in `tokens/component.test.ts`:
- Reject `text-[var(` and `shadow-[var(` (un-hinted, §4.2).
- Keep the existing "no private variable after an operator" check.

### 7.5 Unchanged

The layout-override matrix (`layout-safety.ts`), unit tests (beyond DOM snapshots that gain `data-tokens`/`data-variant`/`data-size`), and `check-dist.ts` (plus the new assertion that `components.css` is in both CSS entries).

## 9. Decisions (2026-10-14)

1. Per-size M3 names only; no size-less shape aliases.
2. Overlay re-applies ThemeScope's `className` on its wrapper, so scoped tokens reach portalled overlays (built in Phase 0).
3. No per-state state-layer tokens.
4. `selected-*` tokens default to M3's system values.
5. Every name is verified against m3.material.io before it ships (§5.0).
6. The full set (≈266, less the renames and the scrim above).
7. `data-variant` and `data-size` on roots are documented public styling hooks; `data-tokens` stays internal and undocumented.
8. `llms-full.txt` already exists; the API tabs' Tokens tables appear in it, and its generator fails if a token is missing.
9. Divider thickness isn't exposed.

The questions as asked:

1. **Size-less shape aliases** (non-M3 names, e.g. `--md-comp-button-container-shape-round` for every size), or per-size M3 names only? The plan ships per-size only. Adding the aliases later is non-breaking.
2. **Overlay reach:** should ThemeScope's `className` be re-applied by Overlay, so that scoped tokens reach portalled menus, dialogs and tooltips? Without it, only `:root` / `[data-theme]` / `className` tokens reach overlays.
3. **State-layer colour tokens:** expose per-state M3 tokens (`hover-state-layer-color`, …) with a change to the `state-layer` utility, or keep following the content colour (the plan's default: ❓ / ⏸)?
4. **Toggle defaults:** should `selected-container-color` default to the variant's `container-color` token, so one override restyles both? That's not M3's default chain, but it's friendlier. The plan uses M3's system-token defaults.
5. **Name verification:** the tonal button (`filled-tonal-button`, M3 baseline, vs the Expressive `TonalButtonTokens`), Expressive menu `standard`/`vibrant` segments, the rail and rail items, the side sheet, the carousel, the split button and the FAB menu. All are marked (verify). Fix the list before Phase 1 ships anything, because names are permanent.
6. **First-wave size:** the full ≈266, or the ≈150 core (container, content, shape, outline) first?
7. **New DOM attributes** `data-tokens`, `data-variant`, `data-size` (`data-color`, `data-kind`) on component roots become documented API (§9). OK?
8. **`llms.txt`:** add it now as part of this work, and also `llms-full.txt`?
9. **Divider thickness and outline widths:** keep ⏸ (layout coupling), or expose `divider-thickness` as the one cheap exception?

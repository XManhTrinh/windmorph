# @windmorph/react — Architecture

Status: **Tier 3 complete** · Last updated: 2026-10-13 (rev. 44 — type in rem, layout in px)

A production-ready React component library implementing the **latest Material Design 3 Expressive** specification, consumed by many React and Next.js projects. This is the free, MIT-licensed core: M3 Expressive components only.

```tsx
import { Button, Dialog, DialogTrigger, ThemeProvider } from '@windmorph/react';
```

## 3. Composition architecture (DRY)

Four layers. **Dependencies only point downward**, enforced by `eslint-plugin-boundaries` in `eslint.config.js`. In source, the layers are `src/tokens` → `src/utils` → `src/theme` / `src/motion` → `src/primitives` → `src/components` → `src/composites`. Composites may not import `src/primitives`. `src/shapes` (the androidx.graphics.shapes port) is pure geometry: it imports nothing, and primitives and components may import it.

**Windmorph Pro (decision #22):** components outside the M3 spec are not in this package, so `src/components` stays M3 only. They live in Windmorph Pro (`@windmorph/react-pro`), which lists `@windmorph/react` as a peer dependency and imports only its public entries (`@windmorph/react`, `/primitives`, `/next`). The core never imports Pro: `no-restricted-imports` forbids `@windmorph/react-pro` in `packages/react`. What Pro needs to build its components (the token value helpers, `defineComponentTokens`, `componentTokensCss`, `OptionPopover`, `useTriggerProps`, `splitDataAttributes`, `ThemeScopeContext`, `generateSchemeColors`, `materialShapeMask`) is public API, documented on the docs site's Primitives page.

**Every new component is also added to the docs site** (2026-10-08): a catalog entry in `apps/site/content/components/catalog.ts` puts it in the side nav under the right category, in the components listing and in the component count (both computed from the catalog), and in the search index, with `keywords` for the words people search for that aren't in its title or summary; plus its page body, examples and playground. **Docs completeness is tested** (2026-10-13): the playground has a control for every public prop of its component (or the prop is in the descriptor's `notControlled` allowlist with a reason), every component and hook the core exports has a generated table (hooks are documented as functions: parameters and return value), and the component's spec data (`apps/site/content/components/spec-data/`) maps each M3 Expressive spec variant and configuration it covers to a live example. The same data lists its deliberate differences from the spec, its extensions beyond it and its Compose counterparts, and builds the API tab's spec status, the `/spec-status` summary and the `/from-compose` guide.

1. **Tokens** — CSS variables for colour, shape, type, motion, elevation, state opacity, z-index.
2. **Primitives** (internal; also exported from `@windmorph/react/primitives`)
   - `useM3Interaction` — wraps React Aria `usePress` / `useHover` / `useFocusRing` / drag → emits `data-pressed`, `data-hovered`, `data-focus-visible`, `data-dragged`, `data-disabled`, `data-selected`. Pass `isPressed` from another React Aria hook (e.g. `useButton`) to skip its own press handling. It also sets the ripple origin on pointer-down (primary button) or Enter/Space. The **ripple follows Compose's `RippleAnimation`**: it fades in over 75ms; its radius grows from 30% of the longer side to half the diagonal + 10px over 225ms (fast-out-slow-in) while its centre moves to the middle; it fades out over 150ms. `data-rippling` (from `useRippleHold`, also used by Checkbox, Radio and Switch) stays on from press start until release, but for at least 225ms, so a quick tap still grows to the edges before fading. Earlier the growth was tied to `data-pressed` and froze wherever it was on a short press. Every press starts a **fresh** ripple, as in Compose, even while the last one is still growing or fading: `restartRipple` pins the ripple's animated properties to the new press's start values with their transitions off, flushes, and releases them. Only the ripple's transitions are switched off (2026-10-13): the component's own (`--m3-transition-property`) keep running, since switching every transition off cancelled a running corner morph and made the corners jump on a quick second press. Otherwise the delayed reset of the idle ripple made a press grow from the previous press's position.
   - `ButtonBase` — unstyled button behaviour shared by every button-like component: `<button>`, link (`href`, via `useLink`) or toggle (`toggle`, via `useToggleButton`), with `useM3Interaction` applied. `children` may be a function of `{ isSelected }`. Button, IconButton and later FAB / chips render it and only add styling. It also takes `dragged` (2026-10-13), passed to `useM3Interaction` as `isDragged`, so `data-dragged` comes from the same source as the other states; a consumer's own `data-dragged` attribute counts as dragged rather than being overwritten.
   - `TouchTarget` — 48×48px hit area for small controls, placed in the inner wrapper.
   - State layer + ripple as **background-layer utilities** on the root (no child elements — see §10): `state-layer`, plus `focus-ring` / `focus-ring-inset` (outline). `Surface` (`container` role + `elevation` 0–5 + `shape`) covers elevation; there is no separate `Elevation` component.
   - `Overlay`: portal to `body` that **re-applies the theme attributes and text direction (`dir`) of where it was rendered**, so overlays opened inside a `ThemeScope` or an RTL region keep them. Passes `isExiting` to React Aria so focus containment is released while animating out. `topLayer` marks the overlay as React Aria's top layer (`data-react-aria-top-layer`, as its toasts use): a portalled overlay sits outside any open modal, whose `ariaHideOutside` would otherwise mark it `aria-hidden`; a top-layer one stays visible to assistive tech, focus may reach it and a press on it is not a press outside the modal. Tooltips and rich tooltips use it, so they work inside dialogs, sheets and viewers. **Direction before first style** (2026-10-13): on mount the wrapper (`data-overlay-scope`, now the overlay's `useId`) gets its `dir` from the marker's ref callback, which runs before the content's layout effects, read with `:dir(rtl)` (no style recalculation) where `CSS.supports` says so. The content's own layout effects can force styles (React Aria's scroll lock reads `clientWidth`), and the old layout effect ran after them, so `@starting-style` transitions began in the wrong direction; the layout effect still keeps `dir` current afterwards.
   - `TriggerContext`: an overlay trigger (DialogTrigger, MenuTrigger, SheetTrigger, the tooltip triggers) passes its press handler, ARIA attributes and ref to whichever button-like child opens it. `ButtonBase` merges them in, so no cloning or private React Aria APIs are needed. Triggers nest: each merges its props into an enclosing trigger's (`useTriggerProps`, React Aria `mergeProps`: handlers chained, refs merged), so `<TooltipTrigger><MenuTrigger><IconButton/>…` gives a menu button its tooltip. Overlays, and a FAB menu's items, reset it to `null`.
   - `DomDirectionLocale`: React Aria takes keyboard direction from its locale, not the DOM `dir`. This render-prop component reads an element's computed direction and, when it differs from the locale's, provides **the same locale with only its script changed** (`localeWithDirection`: `en-US` → `en-Arab-US`, `ar` → `ar-Latn`), which React Aria's `isRTL` reads, so dates and numbers keep the app's language. Toolbars, lists, sliders and the pickers use it, and Tabs uses `localeWithDirection`. (Before rev. 35 it switched to `ar` / `en-US`, which also changed formatting; found when the date picker printed Arabic month names in an RTL region.)
   - `usePresence(isOpen, property = 'opacity')`: keeps an overlay mounted until its exit transition of `property` ends (fallback 800ms). The full-screen search view ends on `clip-path`. Dismissal, focus containment and scroll lock come from the React Aria overlay hooks (`useModalOverlay`, `usePopover`, …) used by each component.
   - `useM3Morph` (built): `useM3Morph(shapes, progress, { size, startAngle })` returns a Motion value of SVG path data for an `m.path`'s `d`. `shapes` are `MaterialShapes` names or any normalized `RoundedPolygon`; progress `0…n-1` walks the sequence, and values outside it extrapolate the first or last morph, so springs can overshoot. Morph matching is cached per shape pair. Reduced motion is the caller's job (snap `progress`). `morphPathAt` is the same thing as a plain function.
   - **Shape library** (`src/shapes`, exported from `@windmorph/react/primitives`): a TypeScript port of `androidx.graphics.shapes` (`RoundedPolygon`, `CornerRounding`, `Morph`, `circle` / `rectangle` / `star` / `pill` / `pillStar`) and Compose's 35 `MaterialShapes`, from androidx `120345129e`. The androidx commonTest suites are ported too. Deviations: 64-bit numbers (so the tests androidx skips on JS for float rounding pass here); `calculateBounds` seeds with ±Infinity, fixing shapes in negative space; no SVG parser, serializer or validation. `polygonToPath` / `morphToPath` port Compose's internal `ShapeUtil.kt` but emit SVG path data (4 decimals) and rotate about the pivot, since SVG has no re-centering step. Coordinates are snapped to 9 decimals before that rounding (2026-10-13): Node and browsers can differ in the last bits of `Math.sin` / `Math.cos`, which rounded a Triangle coordinate (0.45625) differently on each side and broke a server-rendered `Avatar`'s hydration. **Note:** morphs use each polygon's unsplit feature cubics, so mid-morph control points can sit up to ~1% outside the unit square (as upstream); render with `overflow="visible"` or padding.
   - `useM3Spring` (resolves the active motion scheme → Motion spring config)
   - `Field` parts: `FieldLabel`, `SupportingText`, `ErrorText`, `CharacterCounter`
3. **Components** — Button, IconButton, FAB, Card, TextField, Checkbox, Radio, Switch… assembled from primitives.
4. **Composites** — built **only from public components** (dogfooding the public API):
   - Button group (connected) = Buttons / IconButtons + group context
   - Select / Combobox reuse `Field` parts + Menu list

### Rules
- **Flat named exports** for multi-part components: `Dialog`, `DialogTrigger`, `DialogTitle`, `DialogContent`, `DialogActions`. No dot-notation (`Dialog.Title`) — it breaks in Next.js Server Components.
- **Two API levels**: a convenient "batteries-included" form (`<TextField label="Email" />`) built from exported parts for full control. One implementation, not two.
- **Context cascade**: parents pass shared props to children (`ButtonGroup size="sm"` → Buttons). Child's explicit prop wins.
- **Shared style fragments**: state-layer, focus-ring, disabled styles defined once and reused; never copy class strings.
- Because composites use public components, a theme or `className` override on Button also applies to the Button inside SplitButton.

## 4. Tokens — single source of truth

One token source file (TypeScript) generates **all** of:
- the CSS variables in `styles.css` (`@theme` / `@theme inline`)
- the token lists used by `cn()`'s tailwind-merge config
- the Motion spring configs used by `useM3Spring`

so CSS, class merging and JS motion can never drift apart.

In practice the source is `packages/react/src/tokens/*.ts`. `pnpm generate` writes `src/styles/generated/{tokens,themes,theme}.css`; those files are gitignored and Turborepo regenerates them before build, typecheck, lint and test. `cn()` and `useM3Spring` import the token objects directly.

Tailwind utility names:

| Token | Utilities |
|---|---|
| Colour roles | `bg-primary`, `text-on-surface`, `border-outline-variant`, … |
| Type scale | `text-<role>` sets size, line height, tracking and weight (`text-body-large`, `text-label-large-emphasized`), in rem so text follows the browser's font size (see Typography below); typeface via `font-brand` / `font-plain` |
| Corners | `rounded-corner-<name>` (`rounded-corner-full`, `rounded-corner-medium`, …) |
| Elevation | `shadow-elevation-0` … `shadow-elevation-5` |
| Springs | `ease-m3-<family>-<speed>` and `duration-m3-<family>-<speed>`; legacy curves are `ease-m3-emphasized`, … |
| Variants | `medium:` / `expanded:` / `large:` / `xlarge:`; `dark:` follows `data-mode` (including `system`); `motion-standard:` |

### Shape (corner) scale — spec tokens only
| Token | Value |
|---|---|
| none | 0 |
| extra-small | 4px |
| small | 8px |
| medium | 12px |
| large | 16px |
| large-increased | 20px |
| extra-large | 28px |
| extra-large-increased | 32px |
| extra-extra-large | 48px |
| full | 9999px |

No invented radii (e.g. the earlier `m3-expressive-1` / `m3-expressive-2` are removed). The 35 Expressive *shapes* (cookie, clover, burst, …) are path shapes in the shape library, not radii.

### State layer opacities
hover 8% · focus 10% · pressed 10% · dragged 16% · disabled content 38% · disabled container 12%.

### Typography
Full baseline type scale + Expressive **emphasized** variants for every role (display/headline/title/body/label × large/medium/small).

**Type in rem, layout in px** (2026-10-13). Android sizes text in sp, which follows the system font scale, and everything else in dp, which doesn't. The web equivalent is rem for type and px for layout: the token source keeps Compose's values (px at a 16px root) and the generator writes each role's size, line height and tracking as rem (`px / 16`, so `body-large` is `1rem` / `1.5rem` / `0.03125rem`). At the browser's default 16px the result is pixel-identical to the px scale; when a reader raises the browser's font size, every role scales with it while containers, padding, corners, icons and touch targets keep their px sizes, as on Android. Browser zoom scales both, as before. Before this, the scale was in px, so a 32px default font size still gave a 24px dialog title: WCAG 1.4.4 (resize text) relied on zoom alone, and the M3 guidance that text should work at 200% was not met. Tracking is rem rather than em so it stays a fixed fraction of the root, matching Compose's sp tracking.

Components write text through the type roles (`text-<role>` or the `typescale()` tokens), never as px sizes. Where a container had a fixed height that 200% text overflowed, it has a minimum height instead and grows, as Compose's `heightIn(min = …)` / `defaultMinSize` containers do: the small top app bar's row (64px), tabs (48 / 64px), the time picker's period selector (80 / 72 / 38px) and the large badge (16px, Compose's `Badge` uses `defaultMinSize`). Containers whose 200% text still fits keep their fixed height (buttons, chips, the search bar, dialog headers and action bars, the slider's value label). Sizes the spec fixes as geometry keep it: the time picker's 96 × 80px selectors and 256px dial, and the date picker's 48px day cells, so their larger digits fill the box. `apps/docs/e2e/type-scale.spec.ts` sets a 32px root and checks that the roles double, that layout stays in px and that the grown containers hold their text.

## 5. Theming

### Token layering
```css
/* Layer 1 — theme sets M3 system tokens */
[data-theme="ocean"][data-mode="dark"] { --md-sys-color-primary: …; }

/* Layer 2 — Tailwind utilities reference them at runtime */
@theme inline { --color-primary: var(--md-sys-color-primary); }
```
- Components use **only semantic M3 roles** (`bg-primary`, `text-on-surface`, `bg-surface-container-high`, …), never raw colours → every component is themed automatically.
- Switching theme = changing attributes on an ancestor. No re-render, SSR-safe.

### Attributes
- `data-theme` — colour theme
- `data-mode` — `light` | `dark` (or system)
- `data-contrast` — `standard` | `medium` | `high`
- `data-motion` — `expressive` | `standard`

### Built-in themes (ColorSpec2025)
| Theme | Seed | Scheme |
|---|---|---|
| `baseline` (default) | `#6750A4` | Tonal spot |
| `ocean` | `#0061A4` | Tonal spot |
| `forest` | `#386A20` | Tonal spot |
| `sunset` | `#A04100` | Tonal spot |
| `rose` | `#9C4146` | Tonal spot |
| `slate` | `#545F71` | Neutral |

Each: light + dark × 3 contrast levels, generated at **build time** into static CSS. Mode follows system preference unless set.

### API
- `<ThemeProvider defaultTheme defaultMode defaultContrast defaultMotion themes>` + `useTheme()` → `{ theme, setTheme, mode, setMode, resolvedMode, contrast, setContrast, motion, setMotion, themes }`.
  - Each dimension can also be controlled: `theme` + `onThemeChange`, and likewise for the others.
  - `storage`: `"cookie"` (default), `"local-storage"` or `"none"`. The key is `windmorph-theme` (`storageKey`) and the value is URL-encoded `theme=…&mode=…&contrast=…&motion=…`.
  - The stored value is read with `useSyncExternalStore`, so there's no hydration mismatch or extra render.
  - `applyToDocument={false}` stops it from writing to `<html>`.
  - `createTheme()` results passed in `themes` are injected as hoisted React 19 `<style precedence>` tags.
- `<ThemeScope theme mode contrast motion>` — theme a subtree; nestable. It writes all four attributes, inheriting the ones you don't set, and adds `text-on-surface`, which `className` can override. `useThemeScope()` reads the effective state.
- Attribute fallbacks: a missing `data-contrast` behaves as `standard`, a missing `data-mode` as `light`, and a root without `data-theme` gets `baseline`.
- `createTheme({ name, seed, variant, contrast })` — runtime custom theme. `contrast` takes one level or a list (default: all three).
- `palettes` (on `createTheme`, `ThemeSeed` and the CLI's repeatable `--palette <name>=<source>`) takes any of the scheme's six palettes (`primary`, `secondary`, `tertiary`, `error`, `neutral`, `neutralVariant`) from another variant of the same seed or from a hex colour, as Material Theme Builder's core colours do (2026-10-08; docs/plans/create-theme-palettes.md). Roles still take their tones from the theme's own variant, so contrast holds. Without `palettes`, output is byte-for-byte unchanged. The common case is vivid accents on calm surfaces: `variant: 'vibrant'` with `palettes: { neutral: 'tonal-spot', neutralVariant: 'tonal-spot' }`.
- **Success and warning** (2026-10-10; docs/plans/custom-colors.md): every theme has `success`, `on-success`, `success-container`, `on-success-container` and the same for `warning`, made the way Material Theme Builder makes custom colours. Each colour's tonal palette (green `#1E8E3E`, amber `#F9AB00`) is harmonised toward the seed (`Blend.harmonize`, up to 15° of hue) and takes the error roles' tone rules, so it has error's contrast in every mode and at every contrast level (a test checks 4.5:1 for content and 3:1 against `surface` for every built-in theme). `customColors` and `harmonize: false` on `createTheme`, `ThemeSeed` and the CLI (`--custom`, `--no-harmonize`) set a brand's own.
- CLI: `npx @windmorph/react theme --seed <hex> --name <name> [--variant] [--contrast] [--out]` → static CSS (no flash). The bin is `windmorph`.

## 6. Motion system (M3 Expressive)

Springs replace duration + easing pairs.

- **Two motion schemes**: `expressive` (visible overshoot/bounce, **default**) and `standard` (restrained, no visible overshoot). Set via `data-motion` / `ThemeProvider` / `ThemeScope`, independent of colour theme.
- **Two spring families**:
  - **Spatial** — position, size, shape, rotation. May overshoot.
  - **Effects** — colour, opacity. Never overshoot (critically damped).
- **Three speeds** each: fast, default, slow.
- Expressive spatial overshoot: fast ≈ 9%, default/slow ≈ 1.5%. Standard spatial: no visible overshoot. Exact damping/stiffness taken from Compose `MotionScheme` tokens (decision #3).
- **Delivery**:
  - CSS: `--md-sys-motion-spring-{spatial|effects}-{fast|default|slow}-{easing|duration}`, easing as `linear()` approximations; values switch with `data-motion`. Utilities like `ease-m3-spatial-fast` read these variables, so they follow the scheme automatically.
  - JS: `useM3Spring('spatial', 'fast')` → Motion `{ type: 'spring', stiffness, damping, mass }` for the active scheme.
- **Reduced motion**: `prefers-reduced-motion` forces `standard` springs and removes non-essential movement (morphs, overshoot). For buttons (2026-10-13): `container-motion` sets the corner duration to 0, so press and selection morphs snap (buttons, icon buttons, split buttons and every other container using it), the button group's press bump doesn't happen, and the split button's chevron turns without animating.
- Legacy M3 easing/duration tokens kept only for consumers migrating from baseline M3.

## 8. Consumer overrides (broad → narrow)

1. **Tokens via CSS** — globally or per theme:
   ```css
   :root { --md-sys-shape-corner-full: 12px; --md-ref-typeface-brand: "Inter"; }
   [data-theme="ocean"] { --md-sys-color-primary: #0050C8; }
   ```
2. **Brand theme** — `createTheme({ seed })` or the CLI.
3. **Restrict the picker** — `<ThemeProvider themes={['baseline','ocean','acme']}>`.
4. **Subtree** — `<ThemeScope theme="forest" mode="dark">`.
5. **Component** — `className`, `classNames={{ root, label, icon }}` (consumer always wins via `cn()`); exported variant definitions (`buttonStyles`, …) can be extended with new variants.

## 9. Component API conventions

- `variant`, `size`, `className`, `classNames` (per slot), `ref` as prop.
- Controlled + uncontrolled (`value`/`defaultValue`, `open`/`defaultOpen`, `selected`/`defaultSelected`, `onChange`/`onOpenChange`/`onSelectedChange`).
- State exposed as `data-*` attributes for consumer styling.
- Icons passed as React elements (`icon`, `leadingIcon`, `trailingIcon`).
- Accessibility target **WCAG 2.2 AA**: keyboard, visible focus, 48px touch targets (even for XS visuals), `prefers-reduced-motion`, RTL, screen-reader labels required by types where needed (e.g. icon-only buttons require `aria-label`).
- Links (`href`) use client-side routing via React Aria `RouterProvider`.

### Expressive Button family (API fixed from day one)
- **Button** (built): `variant` = `elevated | filled | tonal | outlined | text`; `size` = `xs | sm | md | lg | xl`; `shape` = `round | square`; `toggle` + `selected`/`defaultSelected`/`onSelectedChange` (selected state changes colour and shape); **press morph** — corners animate squarer on press. Also `leadingIcon` (one icon, before the label: the spec says "Don't use two icons in the same button", so `trailingIcon` was removed on 2026-10-13), `href` (renders `<a>` via React Aria `useLink`), `disabled`, `classNames` slots `root | content | label | icon`, and `ButtonContext` so a parent (button group) can cascade `variant` / `size` / `shape` / `disabled`.
  - **Values follow the M3 Expressive specs and the token files** (2026-10-13; earlier they followed Compose's code where it overrides its tokens): text buttons use `primary` (Compose's code; the token file says `on-surface-variant`, flagged by a Compose TODO); XS padding is 16px with an 8px icon gap (`ButtonXSmallTokens`; Compose's code uses 12 / 4); small text buttons have 16px padding like the other small buttons (the spec: "24dp: Not recommended. Use 16dp"; Compose used 12); and toggle buttons press to the same corners as the others, 8 / 8 / 12 / 16 / 16px ("Both round and square buttons should have the same pressed shape"; Compose pressed small toggles to 6px). Label type: `label-large` (XS, S), `title-medium` (M), `headline-small` (L), `headline-large` (XL).
  - **Press morph** is a CSS `border-radius` transition on the root (border-radius is not a transform, so §10 rule 4 holds). Since 2026-10-13 it uses the **fast spatial** spring for every button, toggle or not, which bounces in the expressive scheme: the spec drives "rounded corners" with spatial springs and all component motion with the fast speeds (Compose uses a non-bouncing effects spring). The `container-motion` utility holds it for every interactive container (buttons, icon buttons, split buttons, FABs, menu items), so `container-motion-spatial` is gone. **Rapid presses:** the spec allows "a modified motion curve to avoid resonant effects from overlapping animations" on the web. `useM3Interaction` sets `data-rapid-press` when a press starts while the last release morph (the fast spatial spring's duration) is still running, and `container-motion` then morphs on the fast effects spring, which doesn't overshoot. Full corners are capped at half the container height (`min(var(--md-sys-shape-corner-full), h/2)`) so the transition interpolates smoothly.
  - **Toggle shape:** selected round buttons become square, as Compose does. Selected square buttons become round, which follows m3.material.io; Compose only ships round toggles. Text buttons have no toggle form, which the types enforce.
  - **Disabled:** container `on-surface` 10% and content `on-surface-variant` 38% for every variant (the Expressive token files). Compose's older `FilledTonalButtonTokens` (12%, `on-surface`) are not used.
  - **Elevation:** elevated rests at level 1 and hovers at 2; filled and tonal rest at 0 and hover at 1. A pressed button shows the pressed level (elevated 1, filled and tonal 0, the `PressedContainerElevation` tokens) even while the pointer is over it: the hover shadows are `data-hovered:not-data-pressed:` (2026-10-13; before, a mouse press kept the hover level). Split button halves share it through `buttonVariantClasses`.
  - **Outline inside the edge spacing** (2026-10-13): the leading and trailing space (16 / 16 / 24 / 48 / 64px) is measured from the container's edge for every style, so the outlined style's outline (1 / 1 / 1 / 2 / 3px, the `--m3-button-border` variable that also sets `border-width`) comes out of the padding (`px-[calc(16px-var(--m3-button-border,0px))]`). An outlined button is now the same size as a filled one with the same content (before, 2–6px wider). Split button halves do the same; chips took the same approach (`--m3-chip-border`). To change the outline width, set `--m3-button-border` rather than a `border-*` class, so the padding follows.
  - **Disabled outlines** (2026-10-13): a disabled outlined button's outline is `outline-variant` at 10%; a selected outlined toggle has no outline, disabled or not (`data-selected:border-transparent`; the dimmed outline is `data-disabled:not-data-selected:`), the same as IconButton. Before, a selected toggle kept a 10% outline once disabled.
  - **Selected icon** (2026-10-13, "use an outlined icon when unselected, and a filled version of the icon when selected"): toggles take `selectedLeadingIcon`, shown instead of `leadingIcon` while selected (as `IconButton`'s `selectedIcon`), so an uncontrolled toggle can swap its icon too.
  - **Touch targets:** XS and S get a 48px `TouchTarget` inside the library-owned inner wrapper. Layout height stays 32 / 40px.
- **IconButton** (built): `variant` = `filled | tonal | outlined | standard` (no elevated or text), **filled by default** as the spec says ("Filled (default)"; 2026-10-13, it was standard like Compose's plain `IconButton`). Containers whose icon buttons M3 shows as standard (the toolbars, top app bar and search app bar) give them that default through `ButtonContext.iconButtonVariant` (`standardIconButtons`); an icon button's own `variant` wins. **Tooltip:** "On web, icon buttons should display a tooltip with an accessibility label", so an icon button wraps itself in a `TooltipTrigger` showing its `aria-label` (2026-10-13). `tooltip={false}` turns it off; it steps aside when named by `aria-labelledby`, and inside a `TooltipTrigger` or `RichTooltipTrigger` of the app's (`useInTooltipTrigger`), so there's never a second tooltip; same `size` / `shape` / `toggle`, plus `width` = `narrow | default | wide`, `icon`, an optional `selectedIcon` for toggles, and `href`.
  - **Name required by the types:** either `aria-label` or `aria-labelledby`.
  - **Tooltip, announced once** (2026-10-13): the built-in tooltip only repeats the `aria-label`, so the icon button drops the `aria-describedby` its `TooltipTrigger` adds (a `TriggerContext` wrapper inside `IconButton`; `Tooltip` itself is unchanged). Screen readers no longer read "Search, button, Search". A consumer's own `aria-describedby`, or a `TooltipTrigger` of the app's with other text, still describes the button.
  - **Width** = icon size + leading + trailing space. Compose's `Uniform` option is the default width, which resolves the `LargeIconButtonTokens` naming gap. In px (narrow / default / wide): XS 28/32/40, S 32/40/52, M 48/56/72, L 64/96/128, XL 104/136/184. Icons are 20/24/24/32/40px.
  - **Colour** (2026-10-13, from the spec's colour table; before, standard and outlined inherited the text colour like Compose's `LocalContentColor`): standard icons are `on-surface-variant`; outlined ones are `on-surface-variant` inside an `outline-variant` outline. Disabled is `on-surface` 38% for every variant, with filled / tonal / selected-outlined containers `on-surface` 10%. A disabled outlined icon button's outline dims to `outline-variant` at 10% (2026-10-13; before, it kept full strength): the token keeps `outline-variant` and gives no opacity, and 10% is the disabled outlined Button's (Compose's code draws the icon button's at 38% of the content colour; we keep both outlined styles alike). A container that needs another content colour for its standard and outlined icon buttons sets **`--md-comp-icon-button-icon-color`** on an ancestor, usually `currentColor` to inherit its own: the vibrant floating toolbar (so its standard icons are `on-primary-container`) and the app bars' navigation and action slots do. Inside a toolbar, `ToolbarContext` sets the icon button's `toolbar` variant, which only carries what the token can't: a vibrant toolbar's selected tonal toggles turn `surface-container` / `on-surface` (§9 Toolbars). There is no separate vibrant icon button variant.
  - **Selected toggles:** standard turns `primary`, filled `primary`/`on-primary` (unselected `surface-container`), tonal `secondary`/`on-secondary`, and outlined `inverse-surface`/`inverse-on-surface` with no border, disabled or not (2026-10-13, Compose `outlinedIconToggleButtonBorder` returns none when checked; before, a selected disabled outlined toggle showed its outline). Shape swaps round ↔ square (Compose tokens). Every icon button morph, toggles included, uses the non-bouncing effects spring, as Compose does.
  - Reads `size` / `shape` / `disabled` and its default `iconButtonVariant` from `ButtonContext`, but not the Button `variant`, because the variant sets differ. A button group turns its `buttonVariant` into `iconButtonVariant` when icon buttons have that style (below).
- **Colour note:** the 2025 colour spec makes `inverse-on-surface` noticeably muted (baseline light `#a09ba1` on `#0f0d12`, about 7:1 contrast). Selected outlined buttons and icon buttons look greyer than the 2021 palette did. That's correct, not a bug.
- **Button group** (built, `ButtonGroup`, a composite): `variant` = `standard | connected`; shares `size` / `shape` / `disabled` and `buttonVariant` through `ButtonContext`, and the child's own props win. `buttonVariant` reaches `IconButton`s too when they have that style (`filled`, `tonal`, `outlined`, as `iconButtonVariant`; 2026-10-13, "Don't mix color styles in connected button groups"); `elevated` and `text` reach Buttons only.
  - **Development warnings** (2026-10-13, once per group): standard icon buttons or text buttons in a group (the spec: "Avoid using standard icon buttons or text buttons, as they have no container treatment"), counting only variants the group or the button sets (a toolbar's standard default doesn't count); and a connected group with no toggle buttons ("Avoid using a connected group when none of the buttons can be toggled").
  - **Overflow menu** (`overflow`, 2026-10-13; the spec: "Buttons at the trailing edge of the button group can be customized to collapse into an overflow menu at smaller breakpoints … Place the overflow menu at the trailing end of the group"; Compose `ButtonGroup(overflowIndicator = …)`): the group appends an icon button (`more_vert`, named and tooltipped "More options", `labels.more`) in its `ButtonGroupDefaults.OverflowIndicator` role, taking the group's icon button variant. `useOverflow` measures the items at their natural width (the group briefly takes `w-max` with no button growing, all in one synchronous pass before paint), fits as many as the group's width allows with room for the indicator (Compose's measurement), and hides the rest with `data-overflow-hidden` (`display: none`, so they leave the tab order and the accessibility tree). A `ResizeObserver` on the group and its children re-measures. With `overflow` a standard group fills its container's width (`flex w-full min-w-0`) so it has a width to measure; its buttons stay at the start. The menu lists the folded buttons with their label (a Button's children, an icon button's `aria-label`) and icon; disabled ones are disabled items; toggles are checkable items (radio items in a single-selection group, checkbox items otherwise), checked from the group's selection or the button's `aria-pressed`. Choosing an item calls `click()` on the folded button, so its own press handler, link, toggle or group selection runs (React Aria treats it as a virtual press). Folded buttons don't take part in the press bump. Connected corners follow the visible buttons, the indicator taking the trailing corners.
  - **Spacing** (2026-10-13, the spec's "Standard button group inner padding"; before, 12px at every size from Compose's small tokens): standard groups are 18 / 12 / 8 / 8 / 8px apart (XS–XL) so small buttons' 48px targets never overlap; connected groups are 2px apart at every size. The group's `size` (or the enclosing context's, else `sm`) picks the gap.
  - **Keyboard:** without a selection mode the group is a React Aria `useToolbar` (role `toolbar`, or `group` inside another toolbar): Tab enters and leaves it, and the arrow keys move between its buttons ("the arrow keys to navigate between each item in the group", 2026-10-13). It sits in a `DomDirectionLocale`, so the arrows follow the DOM direction.
  - **Press expansion (standard groups only):** neighbours react to a pressed button (Compose `ButtonGroup`). Connected groups never do this: "Connected button groups don't add any interaction between buttons … They only affect the shape of the button being selected or activated" (2026-10-13). The pressed item grows by `expandedRatio` (0.15) of its width, and its neighbours shrink by the same amount. Each neighbour gives up at most its compression limit, which is half the space around its content (Compose: the item's end padding). Middle items split the growth across both sides, so the group's total width stays constant.
  - **How it works on the web:** the group watches its children's public `data-pressed` attribute (a MutationObserver), pins their `flex-basis` to the measured width, and animates it on the fast spatial spring (added to `container-motion`). While pinned, `min-width` is 0 (Compose forces exact widths too). Inline styles are removed once the release settles, so consumer sizing such as `flex-1` applies again. `expandedRatio={0}` turns it off.
  - **Connected:** 2px gap. **They span their container** ("The connected button group should span the width of the page or surface it's placed on, increasing the button widths inside"): `flex w-full`, and the buttons share the width **equally** (`*:grow *:basis-0`, 2026-10-13, as Compose's connected sample gives each `Modifier.weight(1f)`; before, each grew by an equal extra share, so widths followed the labels). `*:basis-auto` on the group sizes them by their labels again; a consumer `w-fit` or `max-w-*` narrows it. Corners follow the spec by size (2026-10-13; before, one set for every size from Compose): round groups keep full outer corners and inner corners of 4 / 8 / 8 / 16 / 20px; **square groups** (`shape="square"`, now honoured) give every corner that size. Pressed inner corners tighten to 4px (Compose's `PressedInnerCornerCornerSize`; the spec gives none), and to **2px at XS** (2026-10-13), whose inner corners already rest at 4px, so a press always shows a change; 2px is the one radius outside the shape scale (§4), an owner decision. Selected buttons become fully round. **Press bump:** by default a connected group doesn't change widths (the spec: they "don't affect adjacent buttons"; Compose's connected sample has no `animateWidth`). Google's Expressive showcase video does show the bump on a connected group, so `expandedRatio` opts a connected group into it (2026-10-13), as Compose allows by combining `animateWidth` with the connected shapes; the home page bento uses it. XS and S connected icon buttons are at least 48px wide ("a minimum width of 48dp"). The classes live in `components/button/connected-shapes.ts`, shared by Button and IconButton. These are logical corners, so they mirror in RTL. Children get `connected` = `leading | middle | trailing` through a per-child `ButtonContext` provider; Button and IconButton apply it in their recipes, and it replaces their normal shape classes.
  - **Selection:** `selectionMode` = `none | single | multiple` with `selectedKeys` / `defaultSelectedKeys` / `onSelectionChange` / `disallowEmptySelection`. Toggle buttons with a `value` join the group's React Aria toggle-group state (`ToggleGroupStateContext`, read by `ButtonBase`). Single selection renders as a `radiogroup` of `radio`s. React Aria keeps every option tabbable and adds arrow-key movement. No-op changes that React Stately reports (same keys) are not passed to `onSelectionChange`.
  - **Spec gaps:** Compose only has *Small* tokens for groups (standard gap 12px; connected gap 2px, inner corners 8/4px). They are used at every size until per-size values are published.
  - Children must be direct elements (each is wrapped in its own context provider).
- **FAB** (built, `Fab` + `ExtendedFab`): `Fab` `size` = `default | medium | large` (56 / 80 / 96px; small FAB deprecated); `ExtendedFab` `size` = `sm | md | lg` (56 / 80 / 96px tall).
  - **Shared:** `color`, `elevation`, `visible`, `appear` and `href`.
  - **Shapes and icons follow the spec tokens** (decided 2026-10-13, from the M3 Expressive spec audit; earlier revisions followed Compose's overrides): corners are large (16px) / large-increased (20px) / extra-large (28px), and icons are 24 / 28 / 32px (`FabLargeTokens.IconSize`; Compose's 36px override is not used).
  - **Extended FAB:** padding 16 / 26 / 28px; icon gap 8 / 16 / 20px (the `ExtendedFab*Tokens.IconLabelSpace` tokens, 2026-10-13); label `title-medium` / `title-large` / `headline-small`.
  - **Size guidance** (2026-10-13): the spec calls the medium FAB "most recommended", but the default `size` stays `default` (56px), matching Compose's `FloatingActionButton`; the docs recommend `size="medium"` for most layouts.
  - **Elevation** (`elevation`, 2026-10-13, replacing the `lowered` boolean): `default` is level 3, hover 4, pressed 3; `lowered` is level 1, hover 2, pressed 1 (the hover level never applies while pressed, so pressing with the pointer still over the FAB drops it back to its resting level, the `PressedContainerElevation` token; 2026-10-13); `flat` is level 0 in every state, because the spec says "When nested within another component, such as the navigation rail, the FAB's resting elevation should be level 0". Rail-header examples use `flat`. There's no press morph, and no `disabled` (FABs have none in M3; the types enforce it).
  - **Colour styles:** `primary-container` (default), `secondary-container`, `tertiary-container`, `primary`, `secondary`, `tertiary`, each a role + on-role pair. Compose only ships tokens for the first two; the other four follow m3.material.io's colour styles.
  - **Tooltip:** `Fab` (and `ToolbarFab`) show their `aria-label` in a plain tooltip on hover and keyboard focus, as the spec asks of FABs on the web (2026-10-13). `tooltip={false}` turns it off, e.g. inside a consumer's own `TooltipTrigger`. `ExtendedFab` has none while expanded ("The extended FAB doesn't need a tooltip": its label is visible), but collapsed to the icon it is an icon-only FAB, so it shows its label (or `aria-label`) in the same tooltip (2026-10-13), with the same `tooltip={false}` opt-out; like an icon button's, it steps aside inside an app's own `TooltipTrigger` or `RichTooltipTrigger`. The tooltip stays mounted and is disabled while expanded (`fab/FabTooltip.tsx`, controlled so an open one closes as the label reappears), so collapsing never remounts the FAB. **Not beside a floating toolbar** (2026-10-13; "Floating toolbars can be paired with FABs, but not extended FABs"): an `ExtendedFab` inside a `FloatingToolbar` (the internal `ToolbarContext`) warns once in development.
  - **`expanded` (Extended FAB):** collapses to an icon-only square. The label sits in a CSS grid column that transitions between `0fr` and `1fr`, so the FAB's natural width animates without JavaScript or transforms. Both directions run on the fast spatial + fast effects springs ("All component motion is driven by two tokens: expressive fast spatial and expressive fast effects", 2026-10-13). The label stays in the accessible name while collapsed.
  - **Appear / disappear** (2026-10-13; the spec: "When a FAB animates on screen, it expands outward from a central point", and the FAB disappears and reappears on page and tab changes): `visible={false}` scales the FAB to 0.2 around its centre (Compose's `animateFloatingActionButton` target) on the fast spatial spring and fades it on the fast effects spring, then hides it (`visibility`) and makes it `inert`. `appear` plays the entrance on mount (`@starting-style`), so a new `key` replays it on a tab change. Reduced motion keeps only the fade. The scale is a `transform` on the root, set only while hidden or appearing: an exception to §10 rule 4 (see there).

### Card (built)
- `variant` = `filled | elevated | outlined` (default `filled`, as Compose's `Card`). All have 12px corners and `on-surface` content: filled is `surface-container-highest`, elevated is `surface-container-low` at level 1, outlined is `surface` with a 1px `outline-variant` border.
- **Clipping:** cards clip content to their corners (`overflow-hidden`, as Compose clips), so media gets rounded edges; `overflow-visible` turns it off. They're `flex flex-col` with no padding, and content sets its own.
- **Three forms:**
  - **Static** (`<div>`).
  - **Pressable** (`onPress`): renders `<div role="button">` through `ButtonBase`'s new `elementType: 'div'`, because a `<button>` may only contain phrasing content and cards hold headings, media and blocks.
  - **Link** (`href`, `<a>`).
- **Interactive cards** fill their container's width (`w-full`), get state layers and the focus ring, and should be named with `aria-labelledby` (their headline). In development they warn if they contain buttons, links or fields, since interactive content can't nest; use a static card with its own actions instead.
- **States follow the spec's state list with the card token values** (2026-10-13; this replaces following Compose's code, which kept outlined cards flat on hover):
  - Elevation, rest / hover / focus and press / dragged: filled 0 / 1 / 0 / 3, elevated 1 / 2 / 1 / 4, outlined 0 / 1 / 0 / 3. Hover applies only while the card isn't pressed, keyboard-focused or dragged, so exactly one rule wins.
  - A keyboard-focused outlined card's border is `on-surface` (`FocusOutlineColor`).
  - **Dragged** ("When moving a card, increase its elevation"): `dragged` sets `data-dragged`, on static and interactive cards alike; interactive cards also show the 16% dragged state layer. The app's drag and drop code sets it. An interactive card passes it to `ButtonBase`'s `dragged` input (2026-10-13; before, the card set the attribute in a layout effect because `ButtonBase` took no dragged state), and a static card renders the attribute itself.
  - Disabled: filled `surface-variant` 38% over its container (`color-mix`), elevated `surface` 38% over `surface-container-low` (`DisabledContainerOpacity`, 2026-10-13; it was solid `surface` before), the outlined border `outline` 12% (`DisabledOutlineOpacity`, over the card's own `surface`). Content is `on-surface` 38%.
- No anatomy sub-components (headline, media, actions) in v1. Compose doesn't ship them, and layout utilities cover them.

### TextField (built)
- `variant` = `filled | outlined`, a floating `label`, `supportingText` (with `supportingTextOnFocus`), `errorMessage` / `invalid` / `validate` (React Aria `useTextField`), `required` (`*` in the accessible name, `aria-required`), `disabled`, `readOnly` (`data-readonly`), `leadingIcon`, `trailingIcon` (may be an `IconButton`), `errorIcon`, `prefix` / `prefixLabel`, `suffix` / `suffixLabel`, `maxLength` with a `count/max` counter, `multiline` (a fixed-height text area of `rows` lines, 4 by default, that scrolls) with `autoGrow` (grows from `rows` up to `maxRows`, then scrolls), and `labels` (`error`, `characterCount`). It's controlled or uncontrolled through `value` / `defaultValue` / `onChange(value)`.
- **Accessibility from the M3 spec** (2026-10-13; the text field accessibility page wins over our earlier choices):
  - The required `*` is part of the label's text, so the accessible name is "Email \*" ("The accessibility label must include the asterisk"). Only the copy in the outlined notch is hidden, with its fieldset.
  - `ErrorText` has the `alert` role ("When there is an error, "alert" is applied to the role"), and stays in `aria-describedby` after the supporting text.
  - The counter is read as "Character count: 12 of 80" (`labels.characterCount`): its digits are hidden and its id joins the input's description. It used to be hidden from assistive tech.
  - The prefix and suffix have ids and join the description, read as `prefixLabel` / `suffixLabel` ("US dollars" for "$") when given.
  - An invalid field shows an error icon (Material Symbols `error`, role `img`, named "Error" by `labels.error`) in the trailing slot, unless a `trailingIcon` holds it; `errorIcon` replaces it, `false` turns it off. M3 "strongly recommend[s]" it.
  - Supporting text and the counter take the `error` colour in every error state, with or without a message (Compose's `ErrorSupportingColor`).
- **Text area** (2026-10-13): M3 says text areas, "a fixed height and scroll vertically", "should be used instead of multi-line fields on the web". So `multiline` is now a fixed-height text area (4 rows by default), and the growing field is opt-in with `autoGrow`. Before, `multiline` grew without limit.
- **Read-only:** M3 asks for it to be "clearly labeled as read-only"; the field looks like a regular one, gets `data-readonly`, and the docs put "Read-only" in its supporting text.
- **Naming:** a `label` **or** `aria-label` / `aria-labelledby` is required by the types.
- **Where props go:** `ref`, `className`, `style` and `data-*` go on the root; `inputRef` and every other attribute go to the input.
- **Values from Compose** (`TextFieldImpl.kt` + tokens):
  - 56px minimum height, 280px default width (`max-w-full`).
  - 16px padding; next to an icon it drops to 4px, because icons sit in 48px boxes.
  - Filled with a label: 8px padding, label floated 8px from the top. 4px above supporting text, 2px around affixes.
  - Filled has `surface-container-highest` with an `on-surface-variant` indicator (2px `primary` on focus). Outlined has a 1px `outline` border, 2px `primary` on focus, and the label centred on the border at 16px inside a notch with 4px padding.
  - With a leading icon, an outlined label moves from after the icon to 16px when it floats, while a filled label stays aligned with the text.
  - Hovered labels stay `on-surface-variant` on filled fields and darken to `on-surface` on outlined ones. Error-hover switches to `on-error-container`.
  - The label floats on the fast spatial spring and recolours on fast effects. The motion page says the web text field uses Standard easing; it compares easing sets rather than springs, so the label keeps the active scheme's spring (2026-10-13) rather than adding scheme-independent system tokens.
- **One state:** colours follow a single computed `data-field-state` (`disabled > error-focus > error-hover > error > focus > hover > rest`), so the styles of each part never compete on CSS order. `data-focused` / `data-hovered` / `data-invalid` / `data-disabled` / `data-floated` are exposed too.
- **Floating label:** an absolutely positioned `<label>` that transitions `top`, `inset-inline-start` and the type-scale properties, so it needs no transforms and mirrors in RTL. It also floats for browser autofill (`:has(:autofill)`), since autofilled values are hidden from JavaScript until the user interacts.
- **Outlined notch:** a hidden `fieldset`/`legend` carrying the label text, so the gap matches the label exactly. The outline is shifted up 8px only when there is a label. The legend is a one-column grid that opens from `0fr` to `1fr` of the label's own width on the label's fast spatial spring, so the gap keeps pace with the label (Compose sizes the cut-out from the moving label; 2026-10-13). It used to open `max-width` to 100% on effects-fast, fully open while the label had barely moved.
- **Timing** (Compose, 2026-10-13): the outline and indicator change thickness on the fast spatial spring and colour on the fast effects spring; the placeholder fades in on the fast effects spring as the label floats.
- **Errors:** the error message replaces the supporting text visually, but the supporting text stays in the accessible description (`sr-only`).
- With a label, the placeholder, prefix and suffix appear only once the label floats (Compose). The prefix and suffix fade in on the fast effects spring (M3 motion: opacity uses the effects springs; Compose's `affixOpacity`, 2026-10-13); they used Tailwind's default 150ms ease.
- Pressing the container focuses the input (not when pressing an icon button).
- **Not in v1:** composable TextField parts (the doc's "two API levels"); only the batteries-included form is exported, built from the Field primitives.

### Selection controls (built: Checkbox, RadioGroup + Radio, Switch)
- **Shared anatomy:** the `SelectionControl` primitive + `selectionControlStyles`.
  - A root `<label>` (`ref`, `className`, `style`, `data-*`) with a visually hidden native input (`inputRef`) from React Aria (`useCheckbox` / `useRadio` / `useSwitch`), so forms, labels and assistive tech work natively.
  - A control holding the focus ring and a 48px touch target, and the label text (`text-body-large`).
  - `kind: 'circle'` (Checkbox, Radio) makes the control the 40px state-layer circle: `on-surface` unselected, `primary` selected, inverted while pressed, `error` when invalid (M3 spec; this token set has no state-layer colours).
  - `kind: 'track'` (Switch) makes the control the track, with a state layer that follows the thumb.
  - The types require a label or an accessible name. Selection is `selected` / `defaultSelected` / `onSelectedChange` (Checkbox, Switch) or the group's `value` / `defaultValue` / `onChange` (RadioGroup).
- **Checkbox:** Compose's **M3 styling**, i.e. `ComposeMaterial3Flags.isCheckboxStylingFixEnabled = true`. Compose defaults that flag to false, which keeps M2 styling.
  - Geometry: an 18px box with 2px corners and a 2px outline; check path (0.25, 0.5) → (0.4, 0.65) → (0.75, 0.3), 2px square cap.
  - Outline (CheckboxTokens, 2026-10-13): unselected `on-surface-variant`, darkening to `on-surface` on hover, focus and press (`Unselected{Hover,Focus,Pressed}OutlineColor`), and `error` when invalid, pressed included (stacked variant). A checked or indeterminate box has **no outline** (`Selected*OutlineWidth = 0`): its border turns transparent and the fill shows through, so an invalid one is a plain `error` box. Until then the outline stayed `on-surface-variant` in every state and a selected box kept a `primary` border, which ringed an invalid box's `error` fill.
  - Motion: the check draws on default spatial and snaps away 100ms after unchecking; the box fills on default effects and empties on fast effects.
  - `indeterminate` draws a dash path. **Deviation:** Compose morphs the check into the dash, but CSS can't animate a path shape in Safari, so the dash draws on its own.
  - Error uses `error` / `on-error`. Disabled checked is `on-surface` 38% with a `surface` check.
- **Radio:** a 20px ring (2px). The dot is 10px and grows on fast spatial; colour changes on default effects.
  - The unselected ring darkens to `on-surface` on hover, focus and press. Disabled is `on-surface` 38%, which also overrides the selected colour (stacked variant).
  - M3 radios have **no error colour**; an invalid `RadioGroup` shows its error text.
  - `RadioGroup` provides the state, arrow keys, label (`text-title-small`), supporting/error text and orientation. A `Radio` outside a group throws.
- **Switch:** a 52×32px track (2px outline).
  - Thumb geometry is computed like Compose's `ThumbNode`: 16px off, 24px on or with an icon, 28px pressed, centred 16 / 36px from the start. It's passed as `--m3-thumb-size` / `--m3-thumb-center`, so no CSS state selectors compete.
  - Pressing snaps the thumb; release animates `width` / `height` / `top` / `inset-inline-start` on fast spatial. Mirrors in RTL.
  - Hover, focus and press change the thumb to `on-surface-variant` (off) / `primary-container` (on). Disabled colours are Compose's composites over `surface` (`color-mix`).
  - `icons` shows the default check / close icons; `selectedIcon` / `unselectedIcon` override them. The focus ring surrounds the track.
  - **Enter toggles it, as Space does** (M3 spec, keyboard table; 2026-10-13): browsers toggle a checkbox input on Space only, so the switch handles Enter itself (the thumb grows on key down, the switch toggles on key up).
  - **The thumb can be dragged** (M3 spec, "Touch: Tap, Drag"; 2026-10-13): it follows the pointer between its off and on centres (mirrored in RTL, `data-dragged` while it moves) and releasing sets the switch from the half it's in; a tap still toggles. The track is `touch-action: pan-y`, and the drag uses window pointer listeners because React Aria `useMove` stops the pointer-down the label's press handling needs. `SelectionControl` takes `controlProps` for these handlers.
- **No CheckboxGroup** in v1. Compose has none, and a fieldset of Checkboxes with `name` covers forms.
- `splitDataAttributes` (utils) routes `data-*` to the root for components whose remaining props go to a React Aria hook (TextField, the selection controls). Those hooks forward only the attributes they know, so consumer `data-*` attributes were being dropped.

### Dialog (built; a component, not a composite)
- `DialogTrigger` (trigger + dialog, `open` / `defaultOpen` / `onOpenChange`) or a standalone controlled `Dialog`. Flat parts: `DialogTitle`, `DialogContent`, `DialogActions`, and `DialogHeader` for dialogs that can be full screen. Children may be `({ close }) => …`. `icon` centres the title. `dismissable`, `keyboardDismissDisabled` and `placement` are configurable.
- **Role** (2026-10-13, the spec: "On web, basic dialogs should have the alert dialog role"): `role` defaults to `alertdialog` for a basic dialog and to `dialog` when `fullScreen` isn't `never`. An alert dialog is described by its `DialogContent` (React Aria's `contentProps`; the reference is left out when there's no content) and, as before, isn't dismissed by pressing outside, which fits "Basic dialogs require a person to take action before it will close". `role="dialog"` or `dismissable` restores the press-outside dismissal.
- **Initial focus** (2026-10-13, the spec: "focus should automatically land on the first interactive element within the dialog"): `useDialog` focuses the panel unless something inside took focus (`autoFocus`); an effect then moves focus from the panel to its first tabbable element (`utils/focus.ts` `firstTabbable`). A dialog with no controls keeps focus on the panel.
- **Placement** (2026-10-13, the spec: basic dialogs are centred by default, "Their position can be overridden", in an area "that respects a 56dp margin from the edges of the screen"): `placement` = `center | top | bottom | start | end` aligns the panel in the positioner, which pads 24px on compact windows and 56px from the medium breakpoint (it was 24px everywhere). **Custom position** (2026-10-13, the spec: dialogs can be "custom-positioned anywhere on larger screens"): `classNames.positioner` is merged (`cn()`) over the positioner's classes, so `items-*` / `justify-*` place the dialog anywhere while the padding keeps the margin; the defaults are unchanged. The §10 override matrix runs on it (`PositionerOverride` story): with `fixed`, `absolute`, `sticky`, `static`, overflow, `w-full` or a transform on the positioner, the panel keeps its size, corners, motion and focus ring, the scrim covers the window and pressing outside still dismisses.
- **Built on** `Overlay` + React Aria `useModalOverlay` (dismissal, scroll lock, hiding the rest of the page) + `useDialog` (labelling, initial focus). Focus is contained and returns to the trigger. React Aria sets no `aria-haspopup` for dialog triggers; it does set `aria-expanded` / `aria-controls`.
- **Values** (Compose `AlertDialog.kt`, `DialogTokens`):
  - Size: 280–560px wide, 24px padding, 28px corners, `surface-container-high`, level 3. The minimum is `min(280px, 100vw − 48px)` on the panel (2026-10-13): it was `min(280px, 100%)`, whose percentage had no definite base in the content-sized motion wrapper, so short dialogs measured 231–255px.
  - Level 3 stays (2026-10-13): `DialogTokens.ContainerElevation` is level 3 and the spec's dialog pages state no elevation, though Compose's `AlertDialogDefaults.TonalElevation` is 0dp.
  - Text: a 24px `secondary` icon, a `headline-small` title and `body-medium` `on-surface-variant` text.
  - Spacing: 16px below the icon and the title, 24px below the text, 8px between actions.
  - Stacked actions put the confirm action (last) **on top**, matching Compose's flipped `FlowRow` (`flex-wrap-reverse`).
  - **At most two actions** (2026-10-13, the spec: a single action only to acknowledge, at most two, no third "Learn more"): `DialogActions` warns once per instance, in development only, when it holds more than two elements (a fragment's children are counted, not the fragment; `null` and `false` aren't counted).
  - Long content scrolls inside the panel. The scrim is `scrim` at 32%.
  - **Scrolling content and the keyboard** (2026-10-13, the spec: assistive tech must be able to "Scroll the dialog to access all of its contents"): while `DialogContent` overflows (a `ResizeObserver` on it and its children) it is `tabIndex=0` with `data-scrollable` and the `focus-ring`; React Aria's focus containment skipped it before. Initial focus skips it (`firstTabbable(panel, skip)`) and still lands on the first control.
  - **Dividers** (2026-10-13, the spec's anatomy: "Divider (optional)", 1dp): `DialogContent dividers` draws 1px `outline-variant` lines across the panel's full width above and below the content, 8px from it, keeping 24px to the actions. Opt-in rather than automatic, as the spec only marks them optional; basic dialogs only (from 600px for `compact`).
  - **Initial focus skips unrendered elements** (2026-10-13): `firstTabbable` leaves out elements whose `checkVisibility()` is false, so a `compact` dialog shown as a basic dialog no longer tries to focus the header's `medium:hidden` close button (focus stayed on the panel).
- **Motion (not from Compose,** which uses platform window animations), changed 2026-10-13 to follow the spec's transitions page ("Scale and z-axis motion is avoided"; components "expand and collapse along the x or y axis"); it used to scale from 90%:
  - Enter: the scrim fades and the panel fades while it **expands away from the window edge it sits against** on the default springs (CSS `@starting-style`): a `clip-path: inset()` from the collapsed inset in `--m3-dialog-collapsed` to 32px outside the panel (the margin keeps the shadow). 2026-10-13, the spec: "The direction a component enters is informed by their location on screen, expanding away from the device edge": downward for `center` and `top` (as before), upward for `bottom`, along the x axis from the start or end edge for `start` / `end` (physical sides flipped with `rtl:`). It always expanded downward before.
  - Exit: the same collapse and fade on the fast springs. Reduced motion keeps only the fades: the clip stays open on `starting:` and `data-exiting` (2026-10-13; the exiting clip used to jump shut, so the panel vanished at once and only the scrim faded), and a full-screen dialog no longer jumps 48px or slides under `compact` (its `max-medium:` transition list had overridden `motion-reduce:`).
  - Speeds: default (the motion overview: default is for "Animations that partially cover the screen"), not the overview's "fast spatial and fast effects" component line, which is generic.
  - It runs on a library-owned wrapper with no transform, so it isn't a containing block for fixed children.
- **Full screen** (`fullScreen` = `never | always | compact`; `compact`, the spec's recommendation, applies below 600px only): the panel fills the window on `surface-container-high` (2026-10-13, the spec's full-screen colour roles; it was `surface`) with no corners, elevation or padding. `DialogHeader` is a **56px** header (the spec; it was 64px) with the close icon button, a `title-large` headline and the confirming `action`; `divider` adds a 1px `outline-variant` line under it. With a header action the `DialogActions` are hidden; without one they form the spec's **56px bottom action bar** (the header reports its action through context). The panel slides up 48px and fades on the **slow** springs (the spec's speed for full-screen animations). 2026-10-13, from the spec's full-screen measurements and colour roles: the content is padded **24px at the top** as well as the sides (it started flush under the header), and the close icon is **`on-surface`** like the headline (it was the standard icon button's `on-surface-variant`; set through `--md-comp-icon-button-icon-color` on the `close` slot). `always` fills wide windows too; the docs point to `compact`, since the spec keeps full-screen dialogs to compact windows, instead of capping the width at 560px.
- **Moved to the components layer:** the doc listed Dialog as a composite, but its core is the `Overlay` primitive and React Aria hooks, which composites may not import. Consumers' buttons go in `DialogActions`.
- **Container transform** (2026-10-13, the spec: "Use a container transform pattern to transition a FAB into a full-screen dialog"): `origin` = `"trigger"` (the `DialogTrigger`'s button, now in its context) | an `Element` | a `DOMRectReadOnly`, used only while the dialog is full screen (`always`, or `compact` below 600px). `Dialog` measures the origin in a layout effect before the modal mounts (one synchronous re-render, so nothing has resolved the dialog's styles yet) and again as it closes: its box as a `clip-path: inset(… round r)` of the window (`--m3-dialog-origin`; a % radius resolves against the shorter side) and its background colour (`--m3-dialog-origin-color`, or `surface-container-high` when transparent). Enter: the clip opens from the origin to `inset(0 round 0)` on the slow spatial spring, the container fades in on the fast effects spring, its colour moves to `surface-container-high` and the panel's children fade in on the slow effects spring; no 48px slide. Exit: back into the origin on the fast spatial spring, with the opacity stretched over the same time so presence ends with the collapse. Reduced motion keeps the fades only (`motion-safe:` on the exiting clip and colour, no colour transition). `"trigger"` with no trigger opens without a transform. The panel gets `data-origin`.
- **Spec items left as guidance or open** (2026-10-13 audit): the full-screen "Max 560dp" width (the spec also keeps full-screen dialogs to compact windows, so `always` isn't capped); the full-screen fifth colour role `on-surface-variant` (unassigned in the spec; the divider is `outline-variant`, the M3 divider role); the header's 8dp "padding between elements" (the header keeps top-app-bar insets); a `compact` dialog keeps `role="dialog"` and press-outside dismissal in its basic form; titles wrap rather than truncate.

### Menu (built)
- `MenuTrigger` (trigger + `Menu`, `open` / `defaultOpen` / `onOpenChange`), `ContextMenuTrigger` (content + `Menu`) and `Menu` with `MenuItem` / `MenuGroup` / `SubmenuTrigger` children. `MenuItem` / `MenuGroup` are typed aliases of React Stately's collection `Item` / `Section`, identified by React `key`; `SubmenuTrigger` (an item, then the submenu's `Menu`) is a collection element whose `getCollectionNode` yields the item with the submenu on its props.
- **Built on** React Aria `useMenuTrigger`, `usePopover`, `useMenu`, `useMenuItem`, `useMenuSection`. You get `onAction(key)`, `selectionMode` `none | single | multiple` with `selectedKeys` / `onSelectionChange`, `disabledKeys`, arrow keys, typeahead (a letter moves to the *next* item starting with it, wrapping, as the M3 keyboard table says; `useTypeaheadDelegate`, 2026-10-13), Escape / outside-press dismissal and focus return.
- **Item props:** `leadingIcon`, `selectedIcon`, `description` (accessible description), `badge` (M3 anatomy; before the trailing text, read as part of the description), `shortcut` (rendered as `<kbd>`), `trailingIcon`.
- **Layout** (M3 spec, 2026-10-13): `layout` = `divider` (default) | `gap`. The spec's vertical menus come "with gap" or "with divider", and it says "On web, use a divider to separate menu items", "Gaps are not currently available on web" and "Don't use gaps in scrollable menus". `divider` is one surface (elevation 2, 4px padding, 16px corners) with a 1px `outline-variant` `Divider` and 8px above and below it between groups (the baseline menu's divider padding); its first and last items nest in the surface's corners. `gap` is the grouped look below; a `gap` menu that has to scroll (a `ResizeObserver` on the list) switches to dividers for as long as it's open. A submenu inherits the layout, variant and density.
- **Expressive grouped menu** (`layout="gap"`; Compose `Menu.kt`, `MenuDefaults.kt`, Menu / Standard / Vibrant / Segmented tokens):
  - **Groups:** each `MenuGroup` is its own surface at elevation 2, 2px apart, with 4px padding on every side (the SegmentedMenu `GroupPadding` token; Compose's code insets items only 2px vertically, which left the first and last items closer to the edge than the sides). Corners: only 16px; first 16 / 8px; middle 8px; last 8 / 16px. Loose items form implicit groups. Labels start 12px and end 4px from the group's edge (Compose).
  - **Items:** at least 44px tall, 112–280px wide, 12px padding, `label-large`, 20px icons with an 8px gap.
  - **Item corners nest inside the group's:** where an item meets a 16px group corner it gets 12px (16 − the 4px padding), and every other corner is 4px; a heading above the first item takes the group's top edge. **Deviation:** Compose picks item shapes per group alone (first 12 / 4px, last 4 / 12px), so the last item of a leading group was rounder than the group's 8px corner around it. Selected items are 12px, morphing on fast spatial.
  - **Selection:** selectable menus show a check that expands in (grid `0fr → 1fr`) when the item has no leading icon.
  - **`variant`:** `standard` is `surface-container-low` with on-surface content and selects with `tertiary-container`. `vibrant` is `tertiary-container` with `on-tertiary-container` content (icons turn `tertiary` on hover, focus and press) and selects with `tertiary`. Disabled is 38%.
  - **Shadows and scrolling:** the list scrolls when tall, and a scroll container clips its children's shadows to its box, which cut the groups' elevation-2 shadow off at a square edge around the rounded corners. The list therefore has 8px of padding cancelled by a −8px margin (nothing moves; group widths stay 112–280px), and that ring is `pointer-events: none` (groups re-enable it) so a press just outside the menu still dismisses it. A Playwright test checks the 8px inset.
  - **Motion:** revealed from its anchored edge by a `clip-path: inset(…)` (with 24px of room for the shadows) as it fades in, on fast spatial / fast effects: downwards below the trigger, upwards above it, sideways for a submenu. The M3 motion spec avoids scale ("Scale and z-axis motion is avoided"; 2026-10-13); Compose scales from 80%; the menu uses the `reveal` slot, and since 2026-10-13 so do the exposed dropdown menus (Select, Autocomplete) and the docked date picker, through `OptionPopover` (the `motion` slot that scaled them is gone). A clip also leaves the items' layout alone, so a submenu opened while its parent is still animating is placed against the item's final position (a scaled parent misplaced it). The motion wrapper passes the popover's `max-height` down, so a long menu scrolls inside the window. **Reduced motion** (2026-10-13): the clip stays open and the menu only fades, as dialogs, snackbars and tooltips do (the clips are `motion-safe:`); the dropdown menus share this through `reveal`.
- **Submenus** (M3 spec, 2026-10-13: "On web, menus can open submenus"): React Aria `useSubmenuTrigger` / `useSubmenuTriggerState` on the root's `RootMenuTriggerState`. A submenu opens on hover (200ms, `delay`), press, Enter, Space or the arrow pointing away from the menu, and closes with the other arrow or Escape. It's placed `end top` beside its item without covering it (6px: the 4px padding and a 2px gap; first items level), flipping when there's no room. Its popover is portalled into the root popover, so the root's focus scope and outside-press handling cover it and the modal root (`inert` outside) never hides it. The root menu supplies an `I18nProvider` whose locale has the DOM's direction, so the arrow keys and `end` follow an RTL region. **Active state:** the item whose submenu is open keeps a pressed layer (`data-menu-open`). **Shape morph** ("the corners of the focused submenu become more rounded, while the unfocused submenu becomes less rounded"): while any submenu is open, the menu holding focus (`data-shape="active"`) has 24px outer corners (SegmentedMenu `ActiveContainerShape`) and the others 8px (`InactiveContainerShape`), through `--m3-menu-corner` on the fast spatial spring; edge items nest at the corner less 4px.
- **Context menus** (M3 spec: "A secondary click … opens a context menu"; 2026-10-13): `ContextMenuTrigger` uses React Aria `useMenuTrigger` with `trigger: 'contextMenu'` (secondary click, Shift + F10, long press on touch) and opens the menu at the pointer (`usePopover` reads the trigger state's point). The content is wrapped in a `display: contents` element. React Aria names the menu after its trigger, here the whole content, so the `Menu`'s own `aria-label` names it instead.
- **Spec behaviours** (2026-10-13): disabled items can receive focus but do nothing (`disabledBehavior: 'selection'` plus `isDisabled` on each item); multi-select menus stay open on Enter too (`closeOnSelect: false`); while a menu is open its trigger keeps a pressed state layer, however it was opened (`MenuTrigger` passes `data-menu-open` through `TriggerContext`, and the `state-layer` utility adds `--m3-open-opacity`, the pressed opacity, to its hover or focus layer; the split button's checked layer uses it too); `density` = `0 | -1 | -2 | -3` (web only) takes 4px per step off the 44px items.
- **Placement:** `placement` defaults to `bottom start` with no offset; `offset` (px, added 2026-10-13) sets a gap, which the split button uses for its 4px. The clip reveal opens from the anchored edge across the whole width, so it follows any alignment (`bottom end` included). React Aria resolves `start` / `end` from its locale, not the DOM `dir`, so `Menu` converts them to physical sides from the trigger's computed direction (read with `useSyncExternalStore`).
- **Focus fix:** a menu opens on pointer down and takes focus. React Aria then hides the rest of the page, trigger included, from assistive tech. The browser's follow-up `mousedown` on the trigger would then drop focus on `<body>`, so Escape did nothing. `MenuTrigger` cancels the trigger's `mousedown`; React Aria has already focused it on pointer down. A browser test asserts focus is on the first item after a mouse open. **Initial focus** (2026-10-13; M3: "When a menu opens, focus should be placed on the first menu item"): every open focuses the first item unless the opening sets a strategy (↑ on the trigger focuses the last item, as the APG asks); a mouse open and a context menu used to focus the `role=menu` container. The focus ring still shows only for keyboard focus.
- **Persistent scrollbar** (2026-10-13; M3: "Menus can scroll when all menu items can't display at once. In this state, menus show a persistent scrollbar"): a scrolling menu draws the same scrollbar as the exposed dropdown menus' option list (a 4px `outline` thumb in a 12px track, `scrollbar-width: thin` in other engines), from a class list both share (`persistentScrollbar` in `menu-styles.ts`). Before, the menu had an overlay scrollbar, hidden at rest. A menu that fits shows none. A `gap` menu that scrolls has switched to dividers, so its scrollbar sits on the one surface. `e2e/menu-scrollbar.spec.ts` measures it in full Chromium, since Playwright's default headless shell hides scrollbars.
- **Tab closes the menu** (2026-10-13; the APG menu button pattern, and M3's "Tab: Focus lands on menu" leaves Tab to the page): Tab or Shift + Tab in an open menu or submenu closes every menu, and React Aria's focus scope moves focus to the element after (or before) the trigger, or back to the trigger when nothing follows. Before, focus left the popover for `<body>` and the menu stayed open, out of the keyboard's reach. The scope handles Tab on the document's capture phase and stops it, so the root menu listens on the window's capture phase while it's open.
- **Presentation** (2026-10-13; M3: "Consider adapting menus into bottom sheets on small screens"): `presentation` = `popover` (default) | `sheet` | `auto`, as `Select`'s: `sheet` opens the menu in a modal `BottomSheet`, `auto` does so on compact windows (below 600px, `COMPACT_WINDOW` through `useMediaQuery`) and anchors a popover from 600px up. The sheet is a dialog named like the menu (its `aria-label`, or the trigger through `aria-labelledby`); the `role=menu` list inside keeps its keyboard, typeahead, Escape and first-item focus, closes the sheet on an action and returns focus to the trigger. In a sheet the list takes the `divider` layout and spans the sheet (the `embedded` style: no surface, shadow, corners or width limits of its own) with 8px of side padding, as `Select`'s sheet. The Tab-closes listener is the popover's; a sheet is a dialog, so Tab moves within it.
- **Instant** (2026-10-13; M3: "In dense products, such as on desktop, menus can open instantly to reduce motion"): `instant` drops the reveal (`[transition-property:none]` on the `reveal` slot) and unmounts on close without waiting for an exit transition; submenus follow the root through the tree context. It's explicit rather than tied to `density`.
- **Not in v1:** the ButtonGroup overflow menu (now unblocked), and a separate `MenuDivider` item (groups give the dividers; React Stately collections only build items and sections).

### Select and Autocomplete (built; plan `docs/plans/select-autocomplete.md`)
- M3's **exposed dropdown menu**, from Compose's `ExposedDropdownMenuBox`: `Select` is the read-only anchor (`MenuAnchorType.PrimaryNotEditable`), `Autocomplete` the editable one (`PrimaryEditable`). Built on React Aria `useSelect` / `useComboBox`, so they follow WAI-ARIA's select-only combobox and editable combobox with list autocomplete.
- **One field, one list, shared:** the field is `select/field-shell.tsx`, the Text field's markup and `textFieldStyles` (both variants, floating label, notch, indicator, supporting text, errors, the `data-field-state` machine); the list is `select/option-list.tsx`, drawn with `menuStyles` (the `surface-container-low` panel at elevation 2, 44px items, `tertiary-container` and a check for chosen options, sections with headings and dividers, the inset focus ring). Neither can drift from Text field or Menu.
- **Items:** `SelectItem` / `SelectSection` / `AutocompleteItem` / `AutocompleteSection`, typed aliases of React Stately's `Item` / `Section` identified by React `key`, with `leadingIcon`, `description`, `trailing` and `textValue`. They must be created in client components (`assertCollectionChildren`).
- **Menu:** under the field, at least as wide (Compose's `exposedDropdownSize`), above it when there's no room, opening and closing as Menu does: revealed from the field's edge by a clip as it fades in (M3 motion avoids scale; 2026-10-13, it used Compose's scale from 80%). The arrow (`arrow_drop_down`) turns over on the fast spatial spring. `Select`'s `presentation` is `menu` (default, M3's baseline on every window), `sheet` (the library's bottom sheet, with the list but not its panel) or `auto` (a sheet below 600px). `Autocomplete`'s popover is non-modal so the input keeps working, and its options show keyboard focus while DOM focus stays in the input.
- **Selection:** `selectionMode` `single | multiple` with `value` / `defaultValue` / `onChange` (React Aria's newer value API, not `selectedKeys`). Multiple `Select` lists the chosen options in the field (two, then `+N` from `labels.more`); multiple `Autocomplete` shows them as `InputChip`s in a growing field, removed by their close button or Backspace in the empty input. `maxSelections` owns the chosen keys (`select/selection-cap.ts`): options past the cap are disabled, and a change past it (a click or Enter) is turned away.
- **Filtering:** `matchesSearch` (exported with `normalizeSearch`) matches anywhere, ignoring case and accents, `đ` included, so "zurich" finds "Zürich" and "dakovo" finds "Đakovo". `filter` replaces it; controlled `items` are left to the app, with `loading` showing a `LoadingIndicator` row. An empty list shows a `role="status"` row.
- **Naming:** React Aria's `isDisabled`, `isRequired`, `isInvalid`, `isReadOnly` and `isOpen` become `disabled`, `required`, `invalid`, `readOnly` and `open`; the deprecated `validationState` is left out. Words the components show or announce are in `labels`.
- **Behaviour notes:** a press anywhere on a `Select` field opens it (as Compose); on an `Autocomplete` it puts the caret in the input and opens the whole list, as the arrow does (M3: "A menu should open when a person … Selects an element, such as … a text field"; Compose's editable anchor; 2026-10-13). Keyboard focus alone doesn't open it (React Aria's default `menuTrigger="input"`; `"focus"` opens on focus too), and `menuTrigger="manual"` leaves opening to the arrow and the arrow keys. Focus returns to the field a frame after the menu unmounts. While an `Autocomplete` menu is open, React Aria hides the rest of the page (chips included) from assistive technology, as the combobox pattern expects.
- **Searchable** (`docs/plans/select-searchable.md`): `searchable` puts a search at the top of the menu or sheet (`select/search-list.tsx`), wired to the list with React Aria `useAutocomplete` + `useSearchField` as one editable combobox with list autocomplete. The field then has `aria-haspopup="dialog"`; in the menu the panel is the dialog, named by the label. Filtering is section-aware through `useListState`'s `filter` (a section with no matches hides with its heading), with `matchesSearch` by default, `filter(textValue, search, key)` to replace it, and none when the app handles `onSearchChange`. The search takes focus in the menu; a sheet shows the list first (the keyboard would cover half of it), and `useDialog` focuses the sheet. Escape clears the search, then closes; the list's own Escape handling is off (`escapeKeyBehavior: 'none'`), since it read `disallowEmptySelection` from props and swallowed Escape whenever an option was chosen. Multiple selection keeps the dialog and the search. The search is the M3 search bar's field at **48px** (M3's minimum touch target) rather than 56px, so it doesn't dominate the 44px rows, and a searchable menu is at least 280px wide. React Stately's `useAutocompleteState` is private, so `Select` keeps the two values it holds (the text and the active option's id) itself. `UNSTABLE_useFilteredListState` needs a `BaseCollection`, which `Item`/`Section` children don't build.
- **`renderValue`:** what the field shows for the chosen option(s) (`SelectedOption`: key, text, item); the rendered value is `aria-hidden` and the options' text stays in the field's name.
- **From the M3 spec** (2026-10-13):
  - The field shares the Text field's accessibility fixes: the `*` in the name, the error as an `alert`, the error icon (before the arrow; `errorIcon`, `labels.error`) and the error-coloured supporting text.
  - **Typeahead moves on** (keyboard table: "Letters — Focus moves to the next menu item starting with letter"): a letter, or the same letter again, moves to the next option starting with it after the focused one (on a closed `Select`, after the chosen one), wrapping to the top; a longer search still refines from the focused option. React Aria's search started *at* the focused option, so a second press stayed put. `utils/typeahead.ts` (`useTypeaheadDelegate`) gives the list, the closed field and `Menu` the same delegate.
  - **Disabled options keep focus** ("Disabled menu items can receive focus but aren't selectable"): the list states use `disabledBehavior: 'selection'` (`FOCUSABLE_DISABLED_OPTIONS`), `Autocomplete` hands `useComboBox` a `ListKeyboardDelegate` with it, and options are marked `aria-disabled` by the list itself, options past `maxSelections` included. Typeahead on a closed `Select` still skips them.
  - **The label rests with a placeholder:** it floats only on focus, an open menu or a value, and the placeholder shows once it floats, as in Text field. It used to float whenever there was a placeholder.
  - **Persistent scrollbar** ("menus show a persistent scrollbar"): the list styles WebKit's scrollbar (shared with `Menu` since 2026-10-13) (a 4px `outline` thumb in a 12px track), which is always drawn where overlay scrollbars would hide; other engines get `scrollbar-width: thin`.
  - **Filtering motion** ("Menu items ease into their new position as the menu is filtered"): `Autocomplete` and a searchable `Select` move the options that stay from their old places on the default spatial spring (a FLIP read only when the collection changes); nothing moves under reduced motion.
  - `Select` has `readOnly`: the menu doesn't open and the keyboard finds no option (an empty keyboard delegate), with `data-readonly` on the root. `Autocomplete` has `clearable`, M3's clear icon while there's text (`labels.clear`), outside the Tab order since Escape clears.
  - **Kept on purpose:** an opening `Select` focuses the chosen option, or the first one (WAI-ARIA's listbox pattern), where M3's menu page says "the first menu item", written for action menus. `presentation` stays `menu` by default; M3 only says to "consider" a sheet on small screens.
- **Hidden select:** rendered only with `name`, `autoComplete`, `form` or native validation. Otherwise a long list's text was server-rendered twice, and `Intl.DisplayNames` country names can differ between Node and the browser, which broke `PhoneField`'s hydration.
- **Not in v1:** virtualised lists (plain DOM is fine for a few hundred options, the 245 countries included).

### Progress indicators (built, Tier 2)
- `LinearProgressIndicator` and `CircularProgressIndicator`: `value` (0–1; leave it out for indeterminate), `wavy`, `thickness` / `trackThickness` (4px; the track follows `thickness` unless set) and `track` (default on). Linear adds `stopIndicator` (default on). Both are React Aria progress bars that need a name.
- **Indeterminate circular is built** (2026-10-13, following the spec, which lists Determinate and Indeterminate behaviour for both variants in M3 Expressive and uses circular indicators for short indeterminate activities). An earlier revision called it deprecated: only the old separate circular token set is. The `LoadingIndicator` stays the recommended choice for short waits.
- **Thickness** (2026-10-13, the spec's "Track thickness: Configurable"): thicker strokes grow the box by the extra thickness, keeping the wave's room. Linear height = max(stroke, track) (+ 6px wavy); circular size = 40px (48px wavy) + max(stroke, track) − 4. The spec's thick configuration (8px) gives Compose's thick samples: 14px wavy linear, 52px wavy circular (44px flat). The size is a `--m3-progress-height` / `--m3-progress-size` variable the component sets, and stroke widths are SVG attributes. Round caps inset by half the thicker stroke; the stop dot stays at most 4px, inset by a quarter of a thicker track (Compose).
- **No track** (`track={false}`) for use inside a button, as the spec's accessibility guidance asks; the stop dot goes with it. The docs pair it with `classNames.indicator="stroke-current"`.
- **Values** (Compose `ProgressIndicator.kt`, `WavyProgressIndicator.kt`, `Linear/CircularWavyProgressModifiers.kt`, and the ProgressIndicator / Linear / Circular tokens):
  - Shared: `primary` active indicator and stop dot on a `secondary-container` track, with 4px round strokes and a 4px gap.
  - Linear: 240px wide (resize with `className`, e.g. `w-full`), 4px tall, 10px when wavy.
  - Circular: 40px flat, 48px wavy.
- **Circular `size`** (2026-10-13, the spec: circular indicators "can range from 24dp to 240dp … Avoid exceeding"): the diameter in px, clamped to 24–240 like `LoadingIndicator`'s (no warning, as there). Without it the defaults above apply (40 / 48, plus extra thickness). The strokes keep their `thickness` in px rather than scaling (they used to scale with a `size-*` class, 2.4px at 24px): the SVG's viewBox is the box, so only the ring and its wave grow. The wave follows Compose at every size: the star's inner radius stays 0.75 of the ring and the vertex count is the circumference over the 15px wavelength (at least 5), so a bigger ring gets more waves of the same length.
- **Linear drawing** ports `LinearProgressDrawingCache.updateDrawPaths`:
  - Segments are inset for the round caps. The track fills the gaps between active segments, after a gap that shrinks while progress enters. The stop dot shrinks once progress reaches it.
  - The wave is Compose's run of quadratic half-waves, each control point halfway along. It peaks at (height − stroke) / 2 = 3px, is scaled by amplitude about the centre line, and is drawn as exact SVG quadratics.
  - Wavelength 40px (20px indeterminate), travelling a wavelength per second.
  - A wavy determinate indicator flattens below 10% and above 95% (`indicatorAmplitude`). The amplitude changes over 500ms: standard easing as it grows, emphasized-accelerate as it shrinks.
- **Indeterminate linear:** Compose's four keyframed curves over a 1750ms cycle (first head 0–1000ms, first tail 250–1250ms, second head 650–1500ms, second tail 900–1750ms, emphasized-accelerate), drawn as two lines.
- **Indeterminate circular:** Compose's 6000ms cycle: a linear 1080° turn, plus a 90° step in the first 300ms of every 1500ms (emphasized decelerate), while the arc grows from 10% to 87% of the ring over 3000ms and shrinks back (standard easing). Compose's keyframes attach those easings to the hold after each move, so its moves run linear; we apply them to the moves, as its comments describe. The arc and its gapped track turn together (a `<g>` rotation). Both flat and wavy keep the track, since the spec's indeterminate indicators "move along a fixed track" (Compose's flat one hides it). The wavy one has full amplitude.
- **Indeterminate to determinate** (2026-10-13, the spec's "a progress indicator should change from indeterminate to determinate", shown animated): when `value` arrives, the last indeterminate frame eases into the value over 500ms (standard easing). Linear: the first line's tail and head move to 0 and the value, the second line collapses to the start and the wavelength widens to 40px. Circular: the ring keeps turning clockwise to 12 o'clock while the arc takes the value. Reduced motion snaps.
- **Value changes animate** (2026-10-13, the spec: "Linear indicators animate from the leading to the trailing edge along the track. Circular indicators animate from the top of the track, clockwise"): a determinate `value` change eases along the track instead of jumping, with Compose's `ProgressAnimationSpec` curves: flat indicators on a critically damped spring (stiffness 50, no bounce, ~0.4s), wavy ones over 500ms (standard easing). Only the drawing eases; `aria-valuenow` updates at once. Leaving indeterminate, the handoff above does the easing instead. Reduced motion jumps.
- **Circular drawing:**
  - Flat: arcs from 12 o'clock with a gap of (4px + stroke) of circumference either side, drawn as dashes on a `pathLength="1"` circle.
  - Wavy: Compose's `CircularShapes` from our shape library. The active ring is `star(n, innerRadius 0.75, rounding 0.35 / smoothing 0.4, innerRounding 0.5)`, with n = round(2πr / 15px) (9 at 48px), morphed from an n-vertex circle by amplitude.
  - The ring is drawn twice (`pathLength="2"`, Compose's `repeatPath`). The dash shifts along it while the group rotates back, so the wave travels while the arc stays put: one revolution per n seconds.
- **Rendering:** geometry and timing are pure functions (`progress-geometry.ts`), unit-tested against Compose's numbers. Animated variants write paths to the SVG from Motion's `useAnimationFrame`. The first render is a deterministic frame at t = 0, so it's SSR-safe. The linear SVG mirrors in RTL; the circular one doesn't (2026-10-13, the spec: "Circular progress indicators don't need to be mirrored", and they run clockwise).
- **Reduced motion:** the wave stops travelling and amplitude changes snap. Indeterminate motion stays, because it conveys activity.

### Tooltip (built, Tier 2)
- **Plain:** `TooltipTrigger` (trigger then `<Tooltip>`) on React Aria `useTooltipTrigger` / `useTooltip`. It shows on hover, keyboard focus or a touch long press, describes the trigger (`aria-describedby`), stays while hovered, and Escape hides it. `delay` defaults to 0, since Compose shows at once; `closeDelay` is **1500ms** (2026-10-13, the spec: "Both plain and rich tooltips disappear 1.5 seconds after navigating away from the target region"; it was 0). `placement` = `top | bottom | left | right | start | end | top start | top end | bottom start | bottom end`, flipping when there's no room; `start` / `end` are turned into physical sides from the anchor's computed direction (as `Menu` does). `offset` (4px) is the spec's distance for an anchor with a visual boundary; text anchors use 8. Both kinds keep 8px from the screen edge (`containerPadding`, the spec's 8dp increments). Both roots are `w-max` up to their maximum (2026-10-13): a box that shrink-wrapped to the space left before the window edge was squeezed there (a rich tooltip at a 360px window's edge wrapped to 78px), so now React Aria measures the natural width and shifts it inside the margin; a rich tooltip is capped at the window less 16px.
- **In app bars** (2026-10-13, the spec: "If the element is in an app bar, the plain tooltip appears below the element at the same distance"): `TooltipPlacementContext` (public) sets the default placement of the plain tooltips inside; a trigger's own `placement` wins. `TopAppBar` and `SearchAppBar` provide `bottom` through `AppBarItems` (with `standardIconButtons`), so their icon buttons' automatic tooltips and the app's own `TooltipTrigger`s open below. It's a separate context rather than a `ButtonContext` field, because button groups and the search bar's field set their own `ButtonContext`.
- **Touch** (2026-10-13, the spec: "tap and hold the element on mobile"): a touch long press (React Aria `useLongPress`, `pointerType: 'touch'`, 500ms) opens the tooltip without pressing the button (React Aria cancels the press), and it closes 1.5s after the finger lifts. Only the long press's `onPointerDown` reaches the trigger, so its keyboard handling doesn't compete with the trigger's. No extra accessibility description: the tooltip already describes the trigger for keyboard and screen-reader users.
- **Rich:** `RichTooltipTrigger` (trigger then `<RichTooltip title action>`), placed `bottom start` by default (bottom right in LTR, the spec's default; it was `top`).
  - **Transient (default, 2026-10-13, the spec's "Transient by default"):** the plain tooltip's behaviour (hover, focus, long press, 1.5s close delay) on `useTooltipTrigger` / `useTooltip`, so it's a `role="tooltip"` describing its trigger. It stays open while hovered or while focus is inside it.
  - **`persistent`:** a **non-modal popover dialog** (`useOverlayTrigger` type `dialog` + `usePopover isNonModal`, with `role="dialog"` and no `aria-modal`), named by its subhead (or `aria-label`). The trigger has `aria-expanded` and `aria-controls` pointing at it. A non-modal `dialog` is the role for an interactive popup a trigger controls (`role="tooltip"` can't hold controls, and nothing says "modal"). A press opens it; it stays when the pointer leaves, and a press on the trigger again, Escape, or a press anywhere outside it (on another element or on empty space) closes it (Compose's persistent rich tooltip; the spec: "Persistent rich tooltips only appear when clicked or tapped" and "They only disappear once a person interacts with another UI element"). **Outside presses** (2026-10-13): a non-modal `usePopover` isn't dismissable, so a press on empty space (where focus doesn't move) left it open; `useInteractOutside` now closes it, and `shouldCloseOnInteractOutside` leaves out the trigger, so pressing the trigger toggles it instead of closing it on blur and reopening it. Use it when the actions must be reachable from the keyboard.
  - **Focus and Tab order** (2026-10-13, the spec's accessibility page: "Avoid trapping screen reader and keyboard focus on rich tooltips. People should be able to move linearly through the rest of the page", "Focus order within the rich tooltip moves top to bottom", parent element → inline link → text button): opening it **leaves focus on the trigger** (it used React Aria's `useDialog`, which focuses the dialog; now the attributes are set directly). Though it's portalled to the end of the document, it's **next in the Tab order**: a capture-phase `keydown` listener while it's open (`useTabOrderAfterTrigger`) sends Tab from the trigger to its first control, Tab from its last control to the first tabbable after the trigger, Shift+Tab from its first control to the trigger, and Shift+Tab from the element after the trigger to its last control. The overlay's own restoring focus scope is off for it (`disableFocusManagement`): it sends Shift+Tab from the first control to whatever precedes the trigger. **Escape** on the trigger or inside closes it and puts focus on the trigger (stopping the event, so an enclosing dialog stays open). The container has `tabIndex={-1}` (not a Tab stop) so a press on its text takes focus and Escape still reaches it. **Dismissal stays consistent:** focus moving to another element closes it (React Aria's blur-within rule, which leaves out the trigger), so Tab past its last control closes it, like a press elsewhere; moving between the trigger and the tooltip doesn't.
- **Values** (Compose `Tooltip.kt`, Plain / RichTooltipTokens):
  - Plain: `inverse-surface`, `body-small`, 8 × 4px padding, at least 40×24px, at most 200px wide, 4px corners.
  - Rich: `surface-container` at level 2, 12px corners, 16px sides, up to 320px. A `title-small` subhead with its first baseline 28px down. `body-medium` text with its first baseline 24px below the subhead. Without a subhead the box has 12px top padding, and without an action 8px bottom padding (2026-10-13, the spec's 12 / 8dp; it was 4px around plain text). With an action the text has 16px under it and the action row is at least 36px tall with 8px under it. `richTooltipStyles` variants are `subhead` and `action` (they replaced `spaced`).
  - Baselines become padding from Roboto Flex metrics: subhead 13px, text 9px.
  - Both sit 4px from the anchor (plus 8px with the optional 16×8 caret). They **expand along the axis facing the anchor** (2026-10-13, the spec's transitions page: "Scale and z-axis motion is avoided"; they scaled from 80%): a `clip-path: inset()` reveal from the anchor's side, by `data-placement`, which is rendered from the requested physical side on the first render and the resolved side after React Aria measures (2026-10-13: React Aria reports no placement on its first render, so the `@starting-style` clip never matched and only the fade ran), resting 16px outside the box so the shadow and caret show, on fast spatial while fading on fast effects. Reduced motion keeps only the fade.
- **Deviations:**
  - A focus-triggered plain tooltip doesn't auto-hide after 1.5s (Compose's `TooltipDuration`); it stays until blur, leave or Escape (WCAG 1.4.13).
  - Triggers must read `TriggerContext` (library buttons do), as with `MenuTrigger`. A button that opens a menu, dialog or sheet takes a tooltip by putting that trigger inside the `TooltipTrigger`; pressing it opens the overlay and hides the tooltip.
- **Testing note:** React Aria counts a hover only after a pointer move has set its interaction modality. Tests move the pointer before hovering, as any real approach does.

### Snackbar (built, Tier 2)
- `Snackbar`: the message as `children`, `actionLabel` + `onAction`, `onDismiss` (shows the × button), `onEscape` (Escape inside it; defaults to `onDismiss`), `dismissLabel`, `actionOnNewLine`.
- `SnackbarHostState` (from `useSnackbarHostState()`) ports Compose's queue. `showSnackbar({ message, actionLabel, withDismissAction, actionOnNewLine, duration }, { replace })` shows one snackbar at a time and resolves `'action-performed'` or `'dismissed'`. `replace` (2026-10-13, the spec: "a snackbar with updated information can immediately replace an outdated snackbar") dismisses the current one and shows the new one at once. `SnackbarHost` renders it; the consumer positions it with `className`.
- **Values** (Compose `Snackbar.kt` with its `isSnackbarStylingFixEnabled` layout, `SnackbarHost.kt`, `SnackbarTokens`):
  - Container: `inverse-surface`, level 3, 4px corners, 48px minimum height, up to 600px wide.
  - Text and spacing: `body-medium` `inverse-on-surface` with 16px before it and 14px above and below; 8px after the action when there's no dismiss button.
  - Actions: the action is our text `Button` in `inverse-primary` (a component-to-component dependency); the dismiss is a standard `IconButton`.
  - On a new line, the actions sit at the end, 4px from the bottom.
  - The host pads each snackbar by 12px.
- **Motion and timing:**
  - Snackbars fade on fast effects and **expand upward from the bottom edge** on fast spatial, on a host-owned wrapper (not the snackbar's root): a `clip-path: inset()` reveal whose top edge moves from 100% to 32px outside the box (the margin keeps the shadow). 2026-10-13, the spec's transitions page: "Scale and z-axis motion is avoided" and "a snackbar at the bottom of the screen expands upwards"; it used to scale from 80%. Reduced motion keeps only the fade. A leaving snackbar stays, `inert`, while the next one appears, both sharing one grid cell.
  - Durations: short 4s, long 10s. **A snackbar with an action never times out** (2026-10-13, the spec: "Snackbars with actions shouldn't auto-dismiss"), so `duration` is ignored then; Compose allowed it. There's no platform accessibility multiplier. The docs say to use auto-dismissing snackbars on the web only alongside inline feedback.
  - **Addition:** the timer pauses while the pointer or focus is on the snackbar (WCAG 2.2.1).
- **Accessibility:** the host is a persistent `aria-live="polite"` region, so new messages are announced. Snackbars don't take focus. Added 2026-10-13 from the spec's accessibility page:
  - **Announced from the start** (2026-10-13, the spec: "If a snackbar appears when the app is launched, it should be announced after the page's title"): screen readers often skip content that arrives together with its live region, so the host renders its region empty and adds snackbars only after `LIVE_REGION_DELAY` (100ms, as React Aria's announcer waits). A snackbar shown before the host mounts appears then, and its timer starts when it's shown.
  - **Without a host** (2026-10-13): a `Snackbar` rendered directly announces its message's text itself, through one visually hidden polite region kept on `document.body` (`utils/announce.ts`, created on first use and written to once it's had the same delay; each announcement is removed after 7s). It announces when it appears and when the text changes, not on every render; inside a host (`InSnackbarHost` context) the host's region does it, so nothing is announced twice. React Aria's own announcer isn't in its public API, so it isn't used.
  - `focusShortcut` (default `Alt+G`, `false` to turn off) moves focus to the shown snackbar's first control when it has one; letters also match the physical key, since Alt changes the character on some layouts. An actionable snackbar's wrapper carries it in `aria-keyshortcuts`.
  - Escape dismisses the host's snackbars whether or not the × is shown.
  - When a snackbar leaves with focus inside it, focus returns to the element focused before it entered (the focus event's `relatedTarget`), if that's still in the page.
  - `utils/focus.ts` holds `firstTabbable` (React Aria's tree walker isn't public) and `matchesShortcut`.

### Navigation rail and flexible navigation bar (built, Tier 2)
- `NavigationRail` with `NavigationRailItem`, and `NavigationBar` with `NavigationBarItem`. Items are links (`href`) or buttons (`onPress`) with `icon`, optional `selectedIcon` and a label; `selected` marks the current destination with `aria-current="page"` (`data-current`, since `ButtonBase` owns `data-selected`). Each is a `nav` landmark that needs a name.
- **Rail** (Compose `WideNavigationRail.kt`):
  - Props: `expanded` / `defaultExpanded` / `onExpandedChange`, `header` (a node, or a function of `{ expanded, toggle }` for the menu button), `modal`, `hideOnCollapse`, `itemAlignment` = `top | center` and `divider` (2026-10-13, from the M3 spec), and `indicatorMotion` = `expand | slide` (below). `center` centres the items with auto margins in the space below the header (which stays at the top), so an overflowing rail still scrolls to every item; `divider` is a 1px `outline-variant` line on the edge next to the content.
  - **Keyboard** (2026-10-13, from the M3 spec: "Use arrows to move between navigation items"): Up / Down move focus between items, wrapping, and Home / End go to the first and last; Tab works as before, and arrows never change the selection. The bar takes Left / Right (mirrored right to left) the same way.
  - **Modal initial focus** (2026-10-13, from the M3 spec: "Initial focus lands directly on the first interactive item, whether it's the menu, the FAB, or the first navigation item"): the sheet focuses its first focusable element on open, instead of the dialog itself.
  - **FAB:** M3 says a FAB nested in the rail rests at level 0. The examples still use `lowered` until the FAB has a flat elevation option.
  - Collapsed: 96px, `surface`, items 4px apart. Content starts 44px down, with the header 40px above the items. The width is `--m3-rail-collapsed-width` (a registered `<length>`, default 96px), so a consumer can set M3's 80px baseline width and keep the expand motion.
  - **Icons stay on one line** in both states, through the middle of the collapsed rail, as in M3's rail motion: only the labels and the rail's edge move (2026-10-11). Nothing is centred in the animated width. Every inset derives from the collapsed width: the item inset is (collapsed − 56) / 2 (20px at 96px), collapsed items are exactly the collapsed width, and the header is a 56px column at the item inset with `justify-items: safe center`, so a menu button or FAB is centred on the icon line and an extended FAB starts at the column's edge. The modal sheet is portalled, so it copies the rail's computed collapsed width.
  - Expanded: as wide as the widest label + the item chrome (two item insets, 16px pill padding each side, 24px icon, 8px gap: 104px at the default width), clamped to 220–360px. The width springs on the default spatial spring. It's the `--m3-rail-width` variable, so a consumer `w-*` class still wins.
  - **Modal** (`modal`): the in-flow rail stays collapsed (or is hidden with `hideOnCollapse`). The expanded rail opens as a dialog sheet (`useModalOverlay` + `useDialog`): `surface-container`, level 2, 16px end corners, over a 32% scrim. It grows from the collapsed width, or slides in from the start edge when the collapsed rail is hidden, on the fast spatial spring. Escape, an outside press or choosing an item collapses it.
- **Bar** (Compose `ShortNavigationBar.kt`): at least 64px `surface-container`, no elevation. `iconPosition` = `top` (compact) or `start` (the flexible bar's inline items in medium windows). `arrangement` = `equal`, or `centered` with Compose's side padding of (100% − 10% × (n + 3)) / 2 for up to 6 stacked items. **Inline items are centred by default** (2026-10-13, from the M3 spec: "Horizontal navigation items have a fixed width, so extra space is added to the ends"): they're sized to their content, 4px each side (8px between pills, provisional: the spec gives no value), with the rest of the width at the ends.
  - `scrollBehavior="hide-on-scroll"` (2026-10-13, from the M3 spec: "Scrolling downward can hide the navigation bar; scrolling upward reveals it"): the bar is `sticky` at the bottom and an offset of 0 down to minus its height follows the scroll like the top app bar's `enter-always`, written to `--m3-nav-bar-offset` (its `bottom`), so nothing re-renders. It stays put under reduced motion; the docs say not to use it with a screen reader (the spec's rule, which a page can't detect).
  - `onReselect` on items (bar and rail) runs when the current destination is pressed again, for M3's "reset the scroll position to the top".
- **Items** (Compose `NavigationItem.kt` and tokens):
  - Rail collapsed: a 56×32 pill centred in the collapsed width (the item is that wide, even while the rail animates); the `label-medium` label sits 4px below and may use all of it, at least 64px tall.
  - Rail expanded: a 56px pill holding icon · 8px · `label-large`, 16px inside, one item inset (20px) from the rail's start edge, which keeps the icon on the collapsed rail's centre line. **The pill hugs its icon and label** (2026-10-11), as in M3 Expressive; the full-width pill was the deprecated navigation drawer's. The whole row stays the link or button, a larger target than Compose's pill-only one (a deliberate difference), with the state layer and focus ring on the pill. An item can still stretch its pill with `classNames={{ root: 'justify-items-stretch' }}`; there's no prop for it until something needs one.
  - **The pill expands from the centre of the icon in every layout** (2026-10-13, from the M3 spec: "the active indicator expands from the center of the icon"). It replaces the expanded rail's sliding pill (2026-10-11), which moved one pill from the previous item on the fast spatial spring. Collapsed items and the bar grow it from the pill's centre; in the expanded rail and the inline bar the clip starts at the icon's centre (16px + 12px from the start edge, mirrored in RTL). It fades in as it opens, on the default spatial spring.
  - **`indicatorMotion="slide"` is an extension beyond the M3 spec** (2026-10-13, opt-in; the default `expand` is the spec): it matches Google's Expressive showcase motion, where the expanded rail's pill slides from one item to the next; the spec says the indicator expands from the center of the icon. It applies only while the rail is expanded (in place or as the modal sheet): the new item's pill, whole while current, starts at the previous current pill's place and width (a `translateY` and a px `width` on the indicator, measured with `getBoundingClientRect`) and springs to its own on the fast spatial spring, and the old pill goes at once. The width animates from the start edge, so RTL needs nothing extra. The items list is `isolate` and each item's content `z-[1]`, so a moving pill never covers another item's label. Only the indicator moves, never the rail's root. The collapsed rail keeps the centre expand, and under reduced motion the pill fades in place.
  - With a `selectedIcon`, the outline and filled icons share one cell and cross-fade on default effects (every layout).
  - Bar stacked: 6px · 56×32 pill · 4px · `label-medium` · 6px.
  - Bar inline: a 40px pill holding icon · 4px · `label-medium`, 16px inside.
  - **Bar items fill the bar's height** (2026-10-13, from the spec audit: "Navigation items are centered within the container" and 48px targets): both bar layouts stretch to the bar (64px, or taller when a label wraps), so the whole height is the touch target. Inline pills sit in its middle; stacked items keep their icons on one line at the top. Before, an `h-full` that resolved to `auto` left inline items 40px tall at the bar's top edge.
  - Colours: `on-surface-variant`. The current item has `on-secondary-container` on a `secondary-container` pill; its label is `secondary` under the icon or `on-secondary-container` beside it, and bold (the emphasized label role; 2026-10-13, from the M3 spec: "a filled icon with a bold label for selected destinations"). Disabled is 38%.
  - **Labels wrap, never truncate** (2026-10-13, from the M3 spec: "Don't truncate or display an ellipsis in place of label text", and items "grow vertically to accommodate larger labels"): balanced wrapping between words, with the items and the bar growing taller (the expanded rail's pill is at least 56px, the inline bar's at least 40px). The expanded rail measures each label on one line for its width, so labels wrap only past 360px.
  - **Never inside a word** (2026-10-13): labels break only between words (no `overflow-wrap: anywhere` or `hyphens`, which split "Search" into "Searc / h" at large text sizes). A single word too long for its item stays on one line and ends with an ellipsis (`overflow: hidden` with `text-overflow: ellipsis`, which marks the line that overflows; the other words still wrap). The M3 spec asks not to truncate labels; a word broken mid-way reads worse than a clipped one, and only an unusually long word at a large text size reaches it. Playwright checks both bar layouts and the collapsed and expanded rail at a 32px root (`type-scale.spec.ts`).
  - **Badges** (2026-10-13, from the M3 spec): `badge` takes a `Badge`. It overlaps the icon's top end (`BadgedBox`) in the collapsed rail and in both bar layouts, and sits 4px after the label in the expanded rail ("In expanded nav rails, the badge should be placed next to the label text"). Its `label` or text, or `badgeLabel`, describes the item through `aria-describedby`; a small badge (no children) describes it as "New notification" (its `labels.newNotification`; 2026-10-13, from the spec: "Non-counting badges will simply announce New notification"; before, a dot added no description). Put badges on items through `badge`, never as a `BadgedBox` in `icon`, whose text sits in the hidden icon and is never read.
  - Pill and states: the pill grows from its centre (`clip-path`) on the default spatial spring, as Compose animates its width. The state layer (`on-secondary-container`) and the focus ring are pill-shaped, as in Compose's indicator ripple.
  - **A press ripples through the pill** (2026-10-13, from the spec: "A touch ripple passes through the indicator"; before, a press was a flat 10% layer). The pill's state layer is the shared `state-layer` utility: the item's hover and focus show through it, and `NavItem` gives it its own `data-rippling` (from `onPressChange` and `useRippleHold`) and a ripple origin measured in the pill's box (`setRippleOrigin`, exported from `use-m3-interaction` for this), since the pressable element is the whole item. Bar and rail share it.
- **Layout safety:** the pill, its state layer and its content share one grid cell, so nothing is positioned. The content is `relative` because the indicator's `opacity` / `clip-path` paint it in the positioned layer above plain in-flow content. A hiding bar is `sticky`, so consumer positioning classes (`fixed`, `bottom-*`) replace its scroll behaviour.
- **Labels stay on one line while the rail widens** (2026-10-13, from the spec audit: the rails "can transition into each other"): for the first frames of an expand the items already use the expanded layout while the rail is still narrow, and labels wrapped letter by letter, growing the items so the icons below jumped by up to 80px. The rail (and the modal sheet, while it grows in and while it shrinks away) sets `data-widening` from the expand until its width transition ends, which keeps labels on one line, clipped by the rail. It clears at once when no width transition runs (reduced motion, a consumer width), so labels wider than 360px still wrap at rest.
- **Deviation:** when the rail changes mode, Compose cross-fades each label while sliding it. Here items switch layout at once, the labels fade in at their new place (`@starting-style`), and the rail's width does the spring.

### Tabs (built, Tier 2)
- `Tabs` with `Tab` children, typed aliases of React Stately's collection `Item`, identified by `key`, with `title`, `icon`, `badge` and the panel as `children`. Props: `variant` = `primary | secondary`, `scrollable`, `iconPlacement` = `top | start`, `align` = `stretch | start | center`, `swipeable`, `keyboardActivation`, `selectedKey` / `defaultSelectedKey` / `onSelectionChange`, `disabledKeys`, `aria-label`.
- **Built on** React Aria `useTabList` / `useTab` / `useTabPanel`: arrow keys, Home / End. **Manual activation by default** (2026-10-13, m3.material.io's tabs keyboard table: "Arrow: focus lands on the next available navigation destination. Space / Enter: activates the focused navigation destination"); `keyboardActivation="automatic"` restores selection on focus. The panel is keyed by the selection (React Aria's pattern) so its id follows it. Tabs with no panels (navigation rows) render no panel and drop `aria-controls`.
- **Values** (Compose `Tab.kt`, `TabRow.kt`, Primary / SecondaryNavigationTab tokens):
  - Row and tabs: `surface` row with a 1px `outline-variant` divider; 48px tabs; `title-small`, 16px side padding, 24px icons.
  - **Icon above label: 64px** (rev. 41). That is the M3 token (`PrimaryNavigationTabTokens.IconAndLabelTextContainerHeight`) and what Material Web uses: the icon, a 2px gap and the label, centred (9px above and below). Compose's `Tab.kt` (`LargeTabHeight`) and MDC's `TabLayout` still hard-code 72dp, the Material Design 1 value, so this is a deliberate exception to following Compose's code over its tokens. Until rev. 41 the tabs were 72px with Compose's baseline layout.
  - Colours: labels `on-surface-variant`, `on-surface` on hover / focus / press. Selected labels are `primary` (primary) or `on-surface` (secondary). Selection recolours on default effects, deselection on fast effects. The state layer is the selected colour.
  - Indicator: `primary`, sliding on the default spatial spring. **Only a selection change animates** (2026-10-13, from the spec audit; before, the indicator slid in from the row's start edge on mount, and the default selection's colour faded in): the row sets `data-animate` when the indicator moves to a newly selected tab, which turns on the indicator's and the tabs' colour transitions. The first placement, the default selection and resizes put it in place at once. **It follows the selected tab's content** (2026-10-13): the `ResizeObserver` also watches the selected tab's parts, so the width no longer goes stale when a web font loads after mount without the row resizing. Primary tabs: 3px high, as wide as the content (min 24px), with only its top corners rounded (3, 3, 0, 0). Secondary: 2px high, the whole tab. (2026-10-13, from m3.material.io's measurements; until then both were 3px with every corner rounded, as Compose's tokens have.)
  - **Alignment** (2026-10-13, m3.material.io responsive layout: "the maximum width for each tab should be determined by the width of the widest tab … align to the center or leading edge"): `align="start" | "center"` makes a fixed row `max-content` wide with `1fr` columns, so every tab is as wide as the widest, and moves the row's surface and divider to the full-width scroller. `stretch` (default) fills the row as before.
  - **Badges** (2026-10-13): `badge` takes a `Badge`. On a stacked icon (icon above the label, or icon-only) it hangs from the icon through `BadgedBox`; otherwise it sits 4px after the label. It is `aria-hidden` and linked with `aria-describedby`, so it describes the tab instead of adding to its name.
  - **Swipe** (2026-10-13, m3.material.io: "To navigate between fixed tabs, tap an individual tab, or swipe left or right in the content area"): `swipeable` gives the panel `touch-action: pan-y`; a touch or pen swipe that travels 56px (Compose's positional threshold) more horizontally than vertically selects the next or previous enabled tab, mirrored in RTL. Mouse drags are left to text selection. The panel doesn't follow the finger (no pager).
  - Scrollable: tabs at least 90px, a 52px start inset, and the selection animates to the centre on the default spatial spring (`scrollLeft` driven by Motion). The indicator is measured from the row's content box (inside the inset), since grid items sit there; measuring from the border box once shifted it 52px in LTR.
- **Colour deviation:** Compose's `Tab` defaults its unselected colour to the selected one; the token colours are used instead.
- **Layout safety:** the indicator shares the tab row's grid cell, spans every column, sits at the bottom edge and moves with `translate`, so no element is positioned. Each tab is placed in its grid column explicitly, and the divider is an inset shadow so the indicator paints over it.
- **RTL:** React Aria takes arrow-key direction from its locale, not the DOM `dir`, so `Tabs` reads its laid-out direction and supplies an `I18nProvider` with a matching locale when they differ (as `Menu` does for placement).

### Chips (built, Tier 2)
- `AssistChip` (button or link; `leadingIcon`, `elevated`, `outline`), `SuggestionChip` (button; `leadingIcon`, `elevated`, `outline`), `FilterChip` (toggle with `aria-pressed`; `selected` / `defaultSelected` / `onSelectedChange` / `value`, `leadingIcon`, `trailingIcon`, `onRemove`, `elevated`, `outline`), `InputChip` (`avatar` or `leadingIcon`, `onPress`, `selected`, `onRemove`, `removeLabel`, `outline`) and `ChipSet`.
- **Values follow the m3.material.io chip specs** (2026-10-13), with Compose's chip token files for what the spec leaves out:
  - Size and type: 32px tall (48px touch target), `label-large`, 18px icons, 24px avatars with 12px corners.
  - **Shape:** 8px corners for every chip type, at rest, pressed and selected ("All chips are slightly rounded with an 8dp corner"). The earlier 12px / round-when-selected filter and input chips came from Compose's experimental Expressive `shapes` overload and `ChipsTokens`, not the spec, and are gone.
  - Flat chips have a 1px `outline-variant` border; `outline="strong"` draws it in `outline` for 3:1 contrast (the spec's accessibility guidance). Elevated chips are `surface-container-low` at level 1 (hover 2, dragged 4).
  - **Elevation never shows a press** (2026-10-13, the spec: "Avoid using elevation to indicate a chip's pressed state"): hover raises an elevated chip 1 → 2 and a flat selected filter chip 0 → 1 only while it isn't pressed, keyboard-focused or dragged (as cards do), so pressed is level 1 (elevated) and 0 (flat selected), Compose's `ElevatedPressedContainerElevation` and `FlatSelectedPressedContainerElevation`. The flat selected chip's hover rule belongs to flat filter chips only, so an elevated selected filter chip rises to level 2 like an unselected one (it measured level 1 before).
  - **Focus border** (2026-10-13, Compose's `FlatFocusOutlineColor` / `FlatUnselectedFocusOutlineColor`): a keyboard-focused flat chip's border is `on-surface` (assist, suggestion) or `on-surface-variant` (unselected filter and input chips; a two-part chip follows either of its buttons, `has-data-focus-visible`).
  - Disabled: content `on-surface` 38%, borders `on-surface` 12%, containers `on-surface` 12% at level 0.
  - Colours: assist labels `on-surface`; suggestion, filter and input labels `on-surface-variant`. Leading icons are `primary` (the spec's default role), a selected filter chip's `on-secondary-container`; an input chip's `on-surface-variant`, `primary` when selected.
  - Selected filter and input chips are `secondary-container` with no border.
- **Padding:** the spec's "16dp without an icon, 8dp with an icon, 8dp between elements" for every chip: 16px at an edge without an icon, 8px beside one, 4px beside an avatar, 8px between the icon, label, check and remove button. Input chips without a leading element keep Compose's 12px (the spec gives no value). **Padding counts from the container's edge** (2026-10-13): Compose's border overlays the content, so a flat chip's 1px border is taken out of each edge padding (`calc(16px - var(--m3-chip-border))`, the variable 1px on flat chips and 0 on elevated ones). Flat and elevated chips with the same content are now the same width; before, flat chips' content sat 1px further in.
- **Assist chips have no trailing icon** ("Trailing icon (optional, input and filter chips only)"); the `trailingIcon` prop was removed.
- **Filter check:** without a `leadingIcon`, a selected filter chip grows a check (grid `0fr → 1fr`, fast spatial + fast effects), and its start padding moves 16 → 8px.
- **Remove button:** an 18px icon in a 24px round state layer with a 48px `TouchTarget`, and a chip with one is at least 88px wide (the spec's "Target size for close icon: Min 48dp" and "apply a minimum width of 88dp to the chip"). Backspace / Delete on a removable chip removes it. Its close icon is `aria-hidden` (2026-10-13, the spec: "Image / Icon within chip: Hide image"); the button's name says what it does.
- **Focus stops** (the spec's accessibility tab): an input chip with only `onRemove` is **one** focus stop, its remove button ("Remove Alex"), and the chip shows the focus ring around itself. With `onPress` too, the chip's action and its remove button are two buttons (interactive content can't nest), and the container shows the state layer of whichever one is used. A filter chip with `onRemove` (the spec's trailing remove action) uses the same two-button structure. An input chip with neither is static.
- **`ChipSet`:** a labelled `group` (a `radiogroup` with single selection), 8px gaps, `layout` = `wrap | scroll` (one row that scrolls sideways, padded so the 48px targets and focus rings stay inside). Keyboard follows the spec: the set is one Tab stop (leaving with Tab and coming back returns to the chip that had focus), arrow keys move between all its focusable parts (left / right follow the laid-out direction), Home / End go to the ends. **When the focused chip is removed** (2026-10-13, WCAG 2.4.3; focus fell to the page before), focus moves to the next stop, the previous one at the end, or the set itself (`tabIndex={-1}`) once it's empty: the set reads its stops whenever focus enters one or a key is pressed, and a `MutationObserver` restores focus only if nothing else took it. `selectionMode` = `none | single | multiple` with `selectedKeys` / `defaultSelectedKeys` / `onSelectionChange` / `disallowEmptySelection` shares one selection between filter chips with a `value`, through the same `ToggleGroupStateContext` as `ButtonGroup`.
- **Icon colours:** disabled and selected colours on icons go through a named group (`group/chip`), so they win on specificity rather than CSS order.

### Split button (built, Tier 2; a component, not a composite)
- `SplitButton`: a leading action (`children` label and/or `leadingIcon`, `onPress` or `href`) and a trailing button that opens `menu` (a `<Menu>` element, through `MenuTrigger`). Props: `variant` = `filled | tonal | outlined | elevated` (Compose has no text split button), `size` = `xs`–`xl`, `menuLabel` (the trailing button's required name), `open` / `defaultOpen` / `onOpenChange`, `disabled` (both halves).
  - **Icon-only leading button** (2026-10-13, "The leading button … can have an icon, label text, or both"): `leadingIcon` with no `children` and a required `leadingLabel` (the types enforce the pair).
  - **Other overlays** (2026-10-13, "can be customized to open other components like cards"): `menu` is optional. Without it the trailing button takes an enclosing trigger (`DialogTrigger`, `SheetTrigger`, `RichTooltipTrigger`; `data-open` follows the trigger's `aria-expanded`), or, with none, toggles `open` and calls `onTrailingPress`, with `trailingRef` for anchoring a custom overlay.
  - **No `menuIcon`** (removed 2026-10-13): "The trailing button should always have the expand and collapse icon since it rotates when selected. Avoid modifying the icon."
  - **Menu placement:** the menu opens 4px from the button, aligned with the trailing button's end edge ("The menu should be 4dp from the split button", "align the menu with the trailing button when possible"): the split button passes `placement="bottom end"` and `offset={4}` (the new `Menu` `offset` prop) unless the menu sets its own. It also passes `containerPadding={0}` (a `Menu` prop added 2026-10-13, default 12, React Aria's), so against the window's edge the menu still lines up with the trailing button instead of sitting 12px inside it ("Always try to align it with one of the edges").
  - **Opens on release with a mouse** (2026-10-13): React Aria's menu triggers open on pointer down for a mouse, so the trailing button went straight to its open circle and the spec's pressed shape and optical offset never showed. The trailing button's `TriggerContext` is wrapped so a mouse opens the menu on press-up (`onPress`, after focusing the trigger so closing returns focus there); a release outside doesn't open it. Keyboard (press start) and touch (press up) are unchanged.
- **Values** (Compose `SplitButton.kt`, `SplitButton{XSmall…XLarge}Tokens`):
  - Geometry: two buttons 2px apart, each at least 48px wide, with full outer corners.
  - Inner corners are 4 / 4 / 4 / 8 / 12px and change to 8 / 12 / 12 / 20 / 20px when hovered, keyboard-focused or pressed ("The inner corners change shape for hovered, focused, and pressed states", 2026-10-13; Compose's code uses only the pressed corners). While the menu is open, hover and focus keep the round shape.
  - **Touch targets:** XS and S halves are shorter than 48px, so each gets a `TouchTarget` in a library-owned `relative` wrapper (`content`, and the new `trailingContent`).
  - Padding: leading 12/10, 16/12, 24, 48 and 64px; trailing 13, 13, 15, 29 and 43px, with a 22 / 22 / 26 / 38 / 50px icon. Measured from the container's edge: an outlined half takes its outline out of the padding, as Button does (2026-10-13), so an outlined trailing half is 48px wide at S like the others.
  - Colours and elevation: Button's, shared through `buttonVariantClasses`.
- **Menu open (Compose `checked`):** the trailing button becomes a circle with a persistent 10% layer of its content colour. It's an `inset-shadow`, so it composes with elevation shadows.
  - The chevron turns over **inwards** (clockwise in LTR, towards the leading button; anticlockwise in RTL) on the **standard scheme's fast spatial spring** whatever the active scheme ("The split button uses the standard motion scheme (not the expressive motion scheme) when rotating the menu button", 2026-10-13; it was the effects default spring). The icon carries `data-motion="standard"`, which switches the spring variables for that element only.
  - The trailing icon is **optically centred**: −1 / −1 / −2 / −3 / −6px from the centre at rest (the spec's "Menu icon offset when unselected", 2026-10-13; Compose's 0.11 × corner-difference rule gave −1 / −2 / −3 / −4 / −6), −1 / −1 / −2 / −3 / −5px pressed (Compose; the spec gives none), and 0 when round. It's a logical `inset-inline-start` that animates with the corners.
- **Label type:** follows the Button scale per size. Compose's split button provides `label-large` at every size and leaves larger text to the caller.
- **Component layer:** the per-size asymmetric corners, pressed shapes and optical offset aren't expressible through the public `Button` / `IconButton`, so the halves use `ButtonBase`. The leading half is shielded from the menu's `TriggerContext`. React Aria names the menu after its trigger.

### FAB menu (built, Tier 2; a component, not a composite)
- `FabMenu` with two to six direct `FabMenuItem` children (a development warning flags other counts, since the spec says "FAB menus can contain 2–6 items"): `open` / `defaultOpen` / `onOpenChange`, `icon` and an optional `openIcon` (usually add / close), `size` = `default | medium | large` (the FAB the button starts as), `color` = `primary | secondary | tertiary`, `presentation` = `list | menu`, and `visible` / `appear` (the FAB's appear / disappear motion, on the library-owned anchor box, so the root never transforms). The button's name (`aria-label` / `aria-labelledby`) is required by the types. **Tooltip** (2026-10-13, the FAB rule on the web): while closed, the button shows its `aria-label` in the `Fab`'s plain tooltip (`fab/FabTooltip.tsx`); open, it's the close button and has none. `tooltip={false}` turns it off, and it steps aside inside an app's own `TooltipTrigger` or `RichTooltipTrigger` (`useInTooltipTrigger`), so the app's tooltip stays the only one. Items take an optional `icon` (the spec: "Only remove the icon if necessary"), a required label, and `onAction` (both presentations), `onPress` (list only) or `href`.
- **Placement** (2026-10-13): the menu always sits on the window's trailing edge ("The FAB menu should be aligned to the trailing edge of the window"), so the `align` prop is gone; it is logical, so it mirrors in RTL. Position it with `className`: 16px margins (`fixed end-4 bottom-4`), 24px from the large window class up. The items open upwards.
- **Short windows** (2026-10-13; "The items should scroll behind the close button"): the list scrolls (`overflow-y-auto`, at most the window height less the 16px margin) and opens scrolled to the items nearest the button. It reaches under the button's box (a negative margin cancelled by padding, so layout doesn't change) and the box paints above it, so items scroll behind the close button, which stays unobstructed. 16px of padding on the other sides keeps item shadows and focus rings inside the scroll container; that ring lets clicks through.
- **Web menu** (`presentation="menu"`, 2026-10-13; "On web, the FAB menu opens from the FAB, and inherits its states and specs from the baseline menu component. The gap between the FAB and menu can vary, but 4dp is recommended."): the button is a `MenuTrigger` for a standard `Menu` placed `top end`, 4px from the FAB, with the menu pattern's semantics and keyboard. Each `FabMenuItem` becomes a `MenuItem` (icon, label, `onAction`, `href`). Choosing it per window size class is left to the app; the docs recommend `menu` on large screens (the expanded window class, 840px and up) and the default `list` in compact and medium windows (2026-10-13).
- **Elevation** (2026-10-13): `elevation` = `default | lowered | flat`, as on `Fab`, applied to the button and the items: level 3 (the spec) by default, level 1, or level 0 for a flat menu. **Transform** (2026-10-13, the spec: "The FAB should transform into the close button"): with `openIcon`, both icons share one cell and hand over halfway through the morph (Compose swaps at `checkedProgress` 0.5) through a `visibility` switch delayed by half the fast spatial spring; reduced motion swaps at once.
- **Rotating icon** (2026-10-13, an **extension beyond the M3 spec**: it matches Google's Expressive showcase motion; the spec and Compose swap the icon): `iconTransition` = `swap | rotate` (default `swap`, the handover above). With `rotate`, the outgoing icon turns 90° in the direction of the morph and fades out while the incoming one turns in from −90° and fades in: rotation on the fast spatial spring, opacity on the fast effects spring, closing reverses it. It's the CSS `rotate` property on the two face elements (never the root), so Tailwind transforms still compose; the shown face has no rotation, the turn mirrors in RTL, and reduced motion keeps only the crossfade (the turns are `motion-safe:`). Only used with `openIcon`. The faces are shared with `ToolbarFab` (`primitives/IconFaces.tsx`, `icon-faces-styles.ts`).
- **No shape morph:** Compose's FAB menu doesn't use the shape library. Earlier revisions of this doc assumed it did; the Loading indicator was the only Tier 2 consumer.
- **Values** (Compose `FloatingActionButtonMenu.kt`, `FabMenuBaselineTokens`):
  - **Toggle button:** keeps its FAB's layout box (56 / 80 / 96px, corners 16 / 20 / 28px, icons 24 / 28 / 32px) in a library-owned anchor box. Open, it becomes the 56px close button with 28px corners and a 20px icon. Compose's `TopEnd` alignment inside the box becomes the `align` side here.
  - **Button motion:** size, corners and icon follow the fast spatial spring, as Compose's `checkedProgress` does; the container and icon colours (`*-container` → the vibrant role) move on the fast effects spring (2026-10-13: "Effects spring tokens are used to animate properties such as color … where there shouldn't be any overshoot"; on the spatial spring the container passed its `primary` target). Elevation is level 3.
  - **Items:** 56px pills (min 56px wide, 24px side padding, 8px icon gap, 24px icon, `title-medium`), 4px apart and 8px above the button's box. They're `*-container` / `on-*-container`.
  - **Item elevation:** level 3, the `ListItemContainerElevation` token (2026-10-13; Compose's item `Surface` leaves it unused).
- **Stagger:** Compose animates the visible item count as an `Int` on the slow effects spring (ratio 1, stiffness 800, the same in both schemes), truncating it and ending within one item of the target.
  - `fab-menu-stagger.ts` solves that spring for the step times. Opening shows the item nearest the button first (3 items: ~42ms, then the top two together at ~81ms). Closing hides the top item at once.
  - Each item then springs its width (fast spatial, overshoot included) between 0 and its measured content width (`ResizeObserver`), and its opacity on fast effects, clipping its content from the aligned side. The list stays laid out until the bottom item has faded.
- **Accessibility and keyboard:** the button has `aria-expanded` / `aria-controls`. DOM order is button then items (shown above it with `flex-col-reverse`), so Tab goes from the button to the top item, as in Compose. ↓ from the button and ↑ / ↓ between items move focus; ↑ from the top item and ↓ from the bottom one return to the button. Hidden items are `inert`.
- **Closing:** Escape, choosing an item, or an outside press (React Aria `useInteractOutside`) closes the menu, and focus returns to the button if it was inside. Compose relies on the system back button, which the web lacks, so outside press is our equivalent.
- **Colour sets:** primary / secondary / tertiary follow m3.material.io; Compose's defaults are the primary set.
- **Component layer:** the toggle button needs `ButtonBase` and a size morph the public `Fab` doesn't offer, and composites may not import primitives.

### Loading indicator (built, Tier 2)
- **Size** (2026-10-13, the spec: "Loading indicators default to 48dp, but the size is flexible. It should be between 24dp to 240dp" and "The ratio between the container and the active indicator stays the same when resizing"): `size` (px, clamped to 24–240, default 48) sets `--m3-loading-indicator-size`; the SVG scales with the box, keeping the 38/48 ratio. A consumer `size-*` class still wins.
- `LoadingIndicator`: indeterminate by default; `value` (0–1) makes it follow a gesture's progress (pull to refresh). The spec describes it for indeterminate waits and says not to turn one into a progress indicator, so the docs lead with indeterminate and warn against switching one instance between modes (2026-10-13). `variant` = `default | contained`, and `shapes` takes at least two `MaterialShapes` names or `RoundedPolygon`s. It's a React Aria `useProgressBar` (`role="progressbar"`, `aria-valuenow` / `aria-valuetext` when determinate), and the types require `aria-label` or `aria-labelledby`.
- **Values** (Compose `LoadingIndicator.kt`, `LoadingIndicatorTokens`):
  - Box: 48px, full corners. The indicator is 38px (`ActiveIndicatorScale` 38/48) times Compose's `calculateScaleFactor`, so no shape clips as it rotates.
  - Colours: `primary`; contained is `on-primary-container` on `primary-container`.
  - Each frame is centred by its control-point bounds, like Compose's `processPath`.
- **Indeterminate:** Compose's seven shapes (soft burst, 9-sided cookie, pentagon, pill, sunny, 4-sided cookie, oval) in a loop.
  - Every 650ms a morph springs to the next shape (damping 0.6, stiffness 200). It ends at Compose's estimated duration for a 0.1 visibility threshold, **297ms**, then the next morph starts at 0 and the target angle gains a quarter turn.
  - The rotation is `progress × 90°` plus the target angle plus a linear full turn every 4666ms.
  - The morph uses the **raw spring value**, overshoot included. A Compose comment says the value is coerced, but the code isn't.
- **Determinate:** a circle (rotated 18°) morphs into a soft burst as `value` rises, turning counter-clockwise by up to 180°. It draws whatever `value` is, so consumers animate it.
- **Rendering:** every frame is a pure function of elapsed time (`loading-indicator-frames.ts`, unit-tested against Compose's numbers). Motion's `useAnimationFrame` writes the path `d` and the `<g>` rotation straight to the SVG, so animation causes no React renders. The rotation is on the inner `<g>`, never the root (§10 rule 4).
- **Reduced motion** (§6): the indeterminate indicator only rotates (the first shape at the global rate), with no morphs or springy quarter turns. Compose has no reduced-motion handling here.
- **Sizing:** there's a single spec size, so there's no `size` prop. `className` (`size-24`) resizes the box; the SVG's viewBox scales the shape and keeps it square and centred.
- **Tests:** indeterminate screenshots are taken at fixed times under a **paused** Playwright fake clock (`clock.install` + `pauseAt` before navigation). An unpaused installed clock keeps running in real time, which made a frame flaky under parallel load. The layout-safety suite has a non-interactive mode for components without press or focus.

### Pull to refresh (built, 2026-10-13, for 0.1.0)
- `PullToRefresh` (`refreshing`, `onRefresh`, `threshold` = 80px, `disabled`, `labels` = `pull | refreshing | refreshed`, `classNames` = `root | layer | indicator`) wraps a scroll container or a page. The spec covers pull to refresh in the loading indicator's guidelines ("Used for pull-to-refresh interactions", "The container should be used with pull-to-refresh behavior", a threshold, reversing cancels, visible until the refresh completes, never scrolled off-screen) and accessibility ("Initiate a content refresh without relying on a gesture"). It says the loading indicator is used in pull to refresh "on Jetpack Compose only"; the web port is a deliberate extension.
- **Values and motion** (Compose `pulltorefresh/PullToRefresh.kt`: `PullToRefreshBox`, `Modifier.pullToRefresh`, `PullToRefreshDefaults.LoadingIndicator` / `IndicatorBox`): `PositionalThreshold` 80px, `DragMultiplier` 0.5, `calculateVerticalOffset`'s resistance past the threshold (at most twice it), refresh only when the adjusted pull is strictly past the threshold. The indicator is a 48px `primary-container` circle at elevation 0 (`LoadingIndicatorElevation`), its `translateY` = fraction × threshold − its height, clipped at the area's top. A determinate contained `LoadingIndicator` follows the pull (turning back by (fraction − 1) × 180° past the threshold) and crossfades to an indeterminate one while refreshing on the default effects spring. The arithmetic is pure and unit-tested (`pull-to-refresh-math.ts`).
- **Settle:** to the threshold when `refreshing` turns true, away when it turns false or a pull is released, on the **fast spatial** spring of the active scheme (it moves position; Compose's `Animatable` uses a non-bouncing default spring). While a refresh or a settle runs, gestures don't pull (Compose's `isAnimating` / `isRefreshing` checks). Mounted with `refreshing` it starts at the threshold without motion (`onAttach`).
- **Gesture on the web** (no nested scrolling): touch events, with `touchmove` non-passive; mouse and pen through pointer events past a 4px slop, with pointer capture, the selection cleared and the closing click swallowed. A gesture pulls only when its first decisive movement goes down and every scroll container from the target up to the area's (the area if it scrolls, else the nearest above it or the page) is at its top; anything else is the browser's for the rest of the gesture, so scrolling is never blocked. A pull pushed back to zero hands the gesture back; elements whose `touch-action` blocks vertical panning keep their drags; a second finger cancels. While pulling (and at the top while refreshing) `touchmove` is cancelled, so the browser's own pull to refresh and iOS rubber-banding don't start; the root also sets `overscroll-behavior-y: contain`. `touch-action` on the root stays `auto`, since restricting it would also block pinch zoom.
- **Uncontrolled:** without `refreshing`, a promise returned by `onRefresh` keeps the indicator until it settles.
- **Layout:** the root has no layout of its own. The indicator hangs from a library-owned zero-height `sticky top-0` layer (`z-(--md-sys-z-sticky)`) as the first child, so it stays in view while the content scrolls; the clip region is in flow, overflowing that layer, so nothing inside is absolutely positioned and the layout-safety matrix passes. A sticky app bar over a scrolling page moves it with `classNames.layer` (`top-16`). The pull re-renders only the indicator (a Motion value), never the content.
- **Accessibility:** the indicator is `role="progressbar"`, named `labels.pull` (with its value) while pulling and `labels.refreshing` while refreshing; the hidden face is `aria-hidden`. A polite `role="status"` region announces `labels.refreshing` and `labels.refreshed` on each change (not on mount). The non-gesture alternative is the app's refresh button setting `refreshing` (the spec places it "in a menu or directly alongside the content", or an app bar), so there is no built-in one. Reduced motion settles on the standard spring; the loading indicator handles its own.
- **Tests:** Vitest for the arithmetic and the gesture state machine (threshold, cancel, push-back, not at the top, sideways, `touch-action`, second finger, refreshing lifecycle, promise, announcements, mouse slop and click); Playwright drives real touch input through CDP `Input.dispatchTouchEvent` (`hasTouch`) for the indicator's size and position, the refresh lifecycle, cancelling and native scrolling when not at the top, plus mouse pulls, RTL, light and dark screenshots and the layout-safety matrix.

### Toolbars (built, Tier 3)
- `DockedToolbar` (`arrangement` = `centered | space-between`, `visible`), `FloatingToolbar` (`orientation` = `horizontal | vertical`, `color` = `standard | vibrant`, `elevated`, `expanded`, `visible` + `exitEdge`, `leading` / `trailing`, or `fab` + `fabPosition`), `ToolbarFab`, `useToolbarScrollExpansion` and `useToolbarScrollExit`. Both toolbars are React Aria `useToolbar`: `role="toolbar"`, a required name, and arrow keys between controls, following the DOM direction (`DomDirectionLocale`).
- **Keyboard: Tab moves through the controls** (2026-10-13; the spec: "Tab or Arrows: Navigate between interactive elements", "Use Tab to navigate through all other actions"). This follows the M3 spec rather than the WAI-ARIA toolbar pattern's single tab stop: `useToolbarRoot` passes every key but Tab to `useToolbar`'s handler, so Tab and Shift+Tab move through every enabled control in DOM order and then leave the toolbar, while the arrows still move between controls (orientation-aware, flipped in RTL; no Home / End, as before). React Aria's focus restoring on re-entry is dropped with it, so Tab enters at the first control and Shift+Tab at the last. It applies to every toolbar (docked, floating, vertical, and a floating toolbar with a `ToolbarFab`, which comes last in the order). Collapsed controls keep their behaviour: in the tab order, and focus reaching them expands the toolbar.
- **Values** (the toolbar spec and the `FloatingToolbarTokens` / `DockedToolbarTokens`, with Compose's `FloatingToolbar.kt` and `AppBar.kt`'s `FlexibleBottomAppBar` as the recipe):
  - Docked: 64px, `surface-container`, square corners, no elevation, 16px at each end. Items sit 32px apart in the centre by default ("By default all toolbars are 64dp high, center-aligned", 2026-10-13), or spread out (`space-between`, for compact windows). The spec's other docked layout, "Center-aligned, 8dp padding between items", is `className="gap-2"` (`cn` replaces the 32px gap); the docs show it, and recommend `space-between` in compact windows ("evenly spaced"), since the default is `centered` everywhere (2026-10-13).
  - Floating: at least 64px across, full corners, 8px padding. Standard is `surface-container`; vibrant is `primary-container`. **Level 1 by default** (2026-10-13; "Floating toolbars have elevation by default. If the content beneath the toolbar is visually distinct, elevation can be removed.", where Compose uses level 0); `elevated={false}` removes it.
  - **Content colour** (2026-10-13, the toolbar colour spec): the root's text colour is the icon buttons' role, `on-surface-variant` in a standard toolbar and `on-primary-container` in a vibrant one. Toolbars share a `ToolbarContext` (`primitives/ToolbarContext.ts`, internal) that `IconButton` reads, and give their icon buttons the `standard` default through `ButtonContext.iconButtonVariant`. In a vibrant toolbar, standard icon buttons are `on-primary-container` (the vibrant root sets `--md-comp-icon-button-icon-color: currentColor`, 2026-10-13) and selected tonal toggles `surface-container` / `on-surface` (the `VibrantButton*` tokens, through the context). Overlays reset the context, so a menu or dialog opened from a toolbar keeps its own colours. `IconButton` warns in development about square icon buttons in a floating toolbar ("Avoid using square icon buttons in floating toolbars"), and once per button about `width="wide"` in a vertical one (2026-10-13, "don't use wide icon buttons"; the context carries the floating toolbar's `orientation`).
  - **Spacing for icon buttons:** Compose's icon buttons take 48px of layout, ours 40px (the touch target is overlaid). Each content group adds 4px at its ends and 8px between items, so a toolbar of icon buttons matches Compose (12px from the edge, 8px between). The docked toolbar keeps the literal token spacing.
  - With a FAB: 8px between them; the toolbar is level 1 expanded and level 0 collapsed. `ToolbarFab` is Compose's `Standard/VibrantFloatingActionButton`: 16px corners, level 2 (hover 3, pressed 2: the hover level never applies while pressed; 2026-10-13), `primary-container` on a standard toolbar and `tertiary-container` on a vibrant one, a 24px icon, and the FAB's tooltip. `ToolbarFab` takes `elevation` (`default | lowered | flat`, as on `Fab`; 2026-10-13).
  - **Two-state FAB icon** (2026-10-13): `ToolbarFab` takes `expandedIcon`, shown while the toolbar is expanded (`icon` while collapsed); `FloatingToolbar` passes `expanded` to it through the internal `ToolbarContext`. The icons hand over halfway through the expand / collapse spring (the FAB menu's midpoint `visibility` switch, same faces). `iconTransition="rotate"` gives the FAB menu's rotating crossfade, an **extension beyond the M3 spec** (it matches Google's Expressive showcase motion; the spec and Compose swap the icon). Without `expandedIcon`, the FAB shows `icon` alone, with no faces.
- **Collapsing:**
  - Leading / trailing content closes on the fast spatial spring through a grid track (`1fr → 0fr`), anchored like Compose's `AnimatedVisibility` (horizontally, leading content expands from the start and shrinks towards the end; vertically, leading stays at the bottom and trailing at the top). A `clip-path` clips only along the toolbar, so focus rings and touch targets survive; once the track has closed (a delay as long as the collapse) it clips everything, so no sliver shows.
  - With a FAB, the component keeps its expanded size (Compose's layout): the toolbar's slot holds the measured width (`ResizeObserver`, `--m3-toolbar-size`) while the surface's width springs to 0 towards the FAB and fades, and the FAB's box grows 56 → 80px from its own edge. The root is 80px tall (wide, vertically) for the grown FAB.
- **Collapsed controls stay reachable** (2026-10-13; the spec: people should "Maintain access to toolbar controls when the content is scrolled or collapsed"): collapsed content is no longer `inert` or `visibility: hidden`. It stays in the tab order and the accessibility tree, clipped to nothing, so screen-reader browse mode and touch exploration reach it, and focus landing on it (only the keyboard or assistive tech can reach clipped controls) expands the toolbar. Keyboard focus anywhere inside (`useFocusRing({ within: true })`) also keeps it expanded; pointer focus on the always-shown controls doesn't. Compose instead forces the toolbar open under a screen reader, which the web can't detect.
- **`fabPosition`:** `start | end | top | bottom`, where `top` means `start` and `bottom` means `end`, so it can stay put when the orientation adapts. The FAB comes after the toolbar in reading order wherever it sits, as in Compose.
- **`useToolbarScrollExpansion`** ports `floatingToolbarVerticalNestedScroll`: 40px of scrolling down collapses, 40px back up expands; window or a scroll container; `reverse` for bottom-anchored content. It returns `expanded`. There's no `onExpandedChange`, since nothing inside the toolbar changes it.
- **Leaving the screen on scroll** (2026-10-13; "Docked toolbars can either remain on the screen during scroll, or animate offscreen", and the same for floating toolbars): `useToolbarScrollExit` (same thresholds and options) returns `visible` for either toolbar. Hidden, a toolbar slides past its edge plus 24px (`exitEdge` = `bottom | top | start | end`, logical; the docked toolbar always goes down) on the fast spatial spring, Compose's `exitAlwaysScrollBehavior` spec, then turns `visibility: hidden` and `inert`; reduced motion fades it instead. Unlike Compose, it doesn't follow the finger. It's documented as an alternative to collapsing, never combined ("Toolbars shouldn't both collapse and transition off page"); a `FloatingToolbar` with `expanded={false}` and `visible={false}` at once warns once per toolbar in development (2026-10-13). The slide is a `transform` set only while hidden (§10 rule 4 exception).
- **Overflow:** no built-in overflow row. The docs show a `MenuTrigger` with an icon button in a floating toolbar's trailing slot, as the spec describes ("put them in an overflow menu in the trailing slot"), and at the end of a compact docked toolbar (2026-10-13, `toolbar-docked-overflow`).
- **Unused tokens:** `FloatingToolbarTokens.ContainerBetweenSpace` (4px) isn't used by Compose's code either.
- **Deferred:** the docked toolbar's scroll collapse.

### Top app bars (built, Tier 3)
- `TopAppBar` with `variant` = `small | medium | large` (Compose's `TopAppBar`, `MediumFlexibleTopAppBar`, `LargeFlexibleTopAppBar`; the non-flexible medium / large bars and `CenterAlignedTopAppBar` are superseded), `title`, `subtitle`, `titleAlign` = `start | center`, `navigationIcon`, `actions`, `scrollBehavior` = `pinned | enter-always | exit-until-collapsed` and `scrollRef` (the window by default). It renders a `<header>`; consumers wrap the title in a heading when it names the page.
- **Values** (Compose `AppBar.kt`, `AppBar` / `AppBarSmall` / `AppBarMediumFlexible` / `AppBarLargeFlexible` tokens):
  - Heights: small 64px; medium 112px (136px with a subtitle); large 120px (152px); both collapse to 64px.
  - Type: small `title-large` + `label-medium`; medium `headline-medium` + `label-large`; large `display-small` + `title-medium`. The collapsed top row uses the small type.
  - Colours: `surface`, turning `surface-container` (`OnScrollContainerColor`; the `color-mix` reads `--md-sys-color-*`, which follow a `ThemeScope` and dark mode where the bar is: until 2026-10-13 it read Tailwind's `--color-*`, which resolve once at `:root`, so a bar in a dark scope stayed light); navigation icon and title `on-surface`; subtitle and actions `on-surface-variant`. No elevation (the code draws no shadow; the level 2 on-scroll token is unused).
  - Spacing with our 40px icon buttons reproduces Compose's 48px ones: the navigation icon 8px from the start, the title 56px in (16px with no icon), actions 8px apart and 8px from the end.
  - Centred titles use a grid of equal side columns (`minmax(max-content, 1fr)`), so the title is centred in the whole bar until a side needs more room, as Compose's clamped placement does.
  - **Expanded title:** Compose places it by its baseline, 24px (medium) / 28px (large) above the row's bottom, then clamps that padding when the row is too short. With the M3 type scale it is always clamped, which puts the title at the top of the row, and a wrapped title grows the row. Top-aligning the title in a min-height row (48 / 72 / 56 / 88px) reproduces that exactly. With a custom type scale small enough to avoid the clamp, ours would differ.
- **Scrolling on the web:**
  - Compose shrinks the bar's height through nested scrolling while the content stops scrolling. On the web, shrinking an in-flow bar would move the content twice as fast. So with a `scrollBehavior` the bar is `sticky` (with the `--md-sys-z-sticky` layer) and keeps its layout height. Compose's `heightOffset` (0 down to minus the collapsible height) becomes its `top`, `--m3-app-bar-offset`, so the bar slides up instead and the content moves exactly with the scroll.
  - In two-row bars the top row is itself `sticky top-0`, so the expanded row scrolls up beneath it. The collapsible height is measured each frame (the expanded row, or the whole small bar).
  - Offsets: `exit-until-collapsed` = −min(scroll, limit); `enter-always` moves by each scroll delta within [−limit, 0] (any scroll up brings it back); `pinned` = 0. **Two-row `enter-always`** (M3 spec, 2026-10-13: medium and large flexible bars "should remain small until the page is scrolled back to the top"): the expanded row collapses as with `exit-until-collapsed` (it expands only near the top), and past that the 64px top row hides on scroll down and comes back on scroll up, so the bar comes back small. Before, any scroll up re-expanded the large title.
  - Long expanded titles wrap to two lines at most (`line-clamp-2`; M3: "wrap the headline to two lines maximum").
  - Colour: a single row switches when content is under it (scroll > 0) on the default effects spring. Two-row bars blend with the collapsed fraction through fast-out-linear-in in Oklab (`color-mix`), as Compose's `lerp`. **A pinned two-row bar** never collapses, so it switches as a whole like a single row (2026-10-13; M3: "App bars should initially be the same color as the background, then fill with a contrasting color on scroll", for every variant): the `pinned` style variant puts the transition on the bar and makes its top row see-through. Before, its fill followed the collapsed fraction, which pinned is always 0, so it stayed `surface` (Compose does the same; the spec wins). The collapsed title's alpha follows `TopTitleAlphaEasing` (0.8, 0, 0.8, 0.15), the expanded title's 1 − fraction.
  - Everything is written as custom properties from a `requestAnimationFrame` scroll handler, so scrolling causes no React renders. React state flips only when the bar starts or stops being scrolled (`data-scrolled`) or crosses half collapsed (`data-collapsed`, which also swaps which title is `aria-hidden`, as Compose clears one title's semantics).
- **Bottom slot** (2026-10-13; M3: app bars "can animate on and off screen with another bar of controls, like a row of chips"; Compose has no equivalent): `bottom` takes an accessory row (filter chips, tabs) as the bar's last row, inside the sticky `<header>` (`classNames.bottom`). It's transparent on the bar's colour, so it fills with it. In a medium or large bar the expanded row collapses beneath the sticky top row, so the accessory row stays right below the collapsed 64px row; under `enter-always` (and a small bar's `exit-until-collapsed`) the collapsible height includes it, so it hides and comes back with the bar. It brings its own padding.
- **Scrolled colour** (2026-10-13; M3: "consider setting the app bar container to be transparent on scroll … icon buttons have a container fill"): `scrolledColor` = `container` (default, `surface-container`) | `transparent`. The fill mixes `--m3-app-bar-scrolled-color` (default `--md-sys-color-surface-container`) into `surface`; `transparent` sets it to `transparent`, so the bar fades from `surface` to see-through with the same timing (switch or collapse blend). The docs say to give icon buttons a container fill (e.g. `tonal`) then, and that a title sits over the content.
- **Deviations:** no fling settle / snap (Compose snaps a part-collapsed bar after a fling; here the offset follows the scroll position or delta exactly), and no dragging the bar itself. A consumer `fixed` class replaces `sticky`; the offset still applies as `top`.

### Search (built, Tier 3)
- `SearchBar`: `value` / `defaultValue` / `onChange`, `onSubmit` (Enter, the keyboard's search action), `expanded` / `defaultExpanded` / `onExpandedChange`, `view` = `auto | docked | full-screen` (default `auto`), `placeholder`, `leadingIcon` / `trailingIcon` (nodes, or functions of `{ expanded, collapse, view }` so a back or clear button can appear while expanded), `textAlign` = `start | center` (the collapsed text; M3's search app bar supports centred text), `resultsAnnouncement` and the expanded content as `children`. A name is required by the types. `inputProps` (2026-10-13) passes attributes to both inputs, the collapsed and the expanded one (`aria-keyshortcuts`, `aria-describedby`, `enterKeyHint`, `autoComplete`, `spellCheck`, handlers): they replace the defaults (`enterKeyHint="search"`, `autoComplete="off"`, `spellCheck={false}`), handlers are chained before the bar's (`mergeProps`), and the bar's role, name, value, type and popup state always win; `id` and `name` are left out, since the expanded view renders a second input. `SearchAppBar` (Compose's `AppBarWithSearch`) holds a `SearchBar` with `navigationIcon`, `actions` and `scrollBehavior` = `pinned | enter-always`.
- **Values** (Compose `SearchBar.kt`: `SearchBar`, `AppBarWithSearch`, `ExpandedDockedSearchBarWithGap`, `ExpandedFullScreenSearchBar`, `SearchBarDefaults.InputField`; SearchBar / SearchView tokens):
  - Field: 56px, full corners, `surface-container-high`; 360px wide by default, at most 720px (Compose's `sizeIn`; a consumer `w-*` wins). `body-large` text `on-surface`, placeholder `on-surface-variant`.
  - Icons sit in 48px boxes shifted 4px inwards (leading `on-surface`, trailing `on-surface-variant`, plain SVGs at 24px). **The text keeps 4px from the tap targets** (2026-10-13; the spec's measurements "Leading icon and label padding (from tap target): 4dp" and "Label and trailing icon padding (from tap target): 4dp", unfocused and focused, over Compose's code, which leaves none): it starts 56px in after a leading icon (it was 52px) and ends 4px before the first trailing target; without an icon it keeps 16px from the pill's edge. This applies to the collapsed bar, the expanded views' field, the bar in `SearchAppBar` and the search field of a searchable `Select` / its sheet (it shares `searchBarStyles`); the bar's size is unchanged, and the gaps mirror in RTL (logical padding).
  - Compose shows an inset focus ring around the pill whenever the field is focused outside touch mode; ours appears while the input has keyboard focus (React Aria's text-input focus-visible), via `focus-ring-inset`.
  - App bar: `surface`, becoming `surface-container` when content is under it (default effects spring); its search field is `surface-container` and becomes `surface-container-highest` at once (Compose doesn't animate it). Navigation icon 8px from the start, the search bar 8px from its neighbours and 4px from the top and bottom (64px tall), actions 8px apart and 8px from the end.
- **Expanded views:**
  - Like Compose, which renders the input field again in its popup, the expanded view has its own input; the collapsed one becomes `inert` and `aria-hidden` while it is open, and focus returns to it on close. The collapsed input is a `combobox` with `aria-haspopup="dialog"` and `aria-expanded`; the view is a modal dialog named like the bar (`useModalOverlay` + `useDialog`, portalled through `Overlay`).
  - **Docked** (Compose's default with-gap style): the expanded field sits over the bar, 12px wider on each side and 56px tall whatever the bar's height (the spec's focused "Search bar container Height 56dp"; 2026-10-13, it used to take the collapsed bar's height, so a bar a consumer made shorter stayed short), centred on the bar vertically; a dropdown 2px below (12px corners, `surface-container-high`, 240px to 2/3 of the window tall with the field) slides down from half its height on the default spatial spring (fast spatial back) while fading over 100ms after 50ms (standard accelerate; out over 100ms standard decelerate). A 32% scrim covers the page; pressing it collapses the view.
  - **Full screen** (contained): a `surface-container-low` surface grows from the bar's bounds (28px corners) to the window through `clip-path: inset(… round …)` on the slow spatial spring (default spatial back), so nothing is transformed. The field moves to 8px from the top, 16px from each side, keeping its `surface-container-high` pill; the content starts 72px down and fades like the dropdown.
- **Reduced motion** (2026-10-13): under `prefers-reduced-motion` nothing moves or grows. The full-screen view fades in and out over the window on the fast effects spring (its clip stays open, and `usePresence` waits for the fade), its field is in place at once; the docked field is at its focused width at once and the dropdown only fades. The spatial classes are `motion-safe:`. Before, the clip still grew and the dropdown still slid, on standard springs.
- **Adaptive view** (2026-10-13; M3: "Docked layout: Best for medium and expanded windows. Full-screen layout: Default for compact breakpoints", and the bar "should swap from full-screen in compact windows to docked in larger breakpoints"): `view="auto"`, the default, is full screen below 600px wide (the compact window class, `COMPACT_WINDOW` through `useMediaQuery`, as the date and time pickers use) and docked from there up, following the window as it resizes. The server and the first client render see docked, so hydration matches. `docked` and `full-screen` stay for a fixed layout; the root carries the resolved one as `data-view`, and the icon functions get it as `view`, so a back button can show in the full-screen view only. A full-screen view needs a way back on touch screens (a back button), so a bar that had relied on the docked default should add one or pass `view="docked"`; the site's examples pass `docked`. Before, the default was `docked` at every width. The site's own search passes its view explicitly, so it's unchanged.
- **Keyboard and expansion** follow Compose's input field: a press, typing (the query getting longer) or ↓ expands the bar; Tab focus alone doesn't. In the expanded view ↓ moves focus to the first focusable element of the content (Compose moves focus down); Escape or a press outside collapses it.
- **M3 Expressive spec fixes** (2026-10-13):
  - **Contained full screen:** the spec's Expressive default is the contained style ("Divided — Not recommended. Use contained"), so the full-screen view is `surface-container-low` and its field keeps the `surface-container-high` pill, 16px from each side (it was Compose's transparent field on a `surface-container-high` view, the divided look). The divided style isn't offered.
  - **The docked bar widens when focused** ("The margins change from 24dp to 12dp"): the expanded field grows 12px on each side from the bar's bounds on the default spatial spring (back on fast spatial), within the window and, unless the bar is wider already, 720px.
  - **Docked height:** with the bar, at least 240px and at most 2/3 of the window (the dropdown is `min(182px, 66.67dvh − 58px)` to `66.67dvh − 58px`; it was capped at half).
  - **Trailing content:** one or two icon buttons, or an avatar (an `img` drawn at 30px) and an icon button; the trailing slot is at least 48px and grows.
  - **Announcing results:** a polite `role="status"` region inside the view speaks `resultsAnnouncement` (e.g. "5 results") when the view opens and whenever it changes ("the screen reader must announce the change").
  - **After a search:** Enter in the expanded input submits and moves focus to the results container (`tabIndex=-1`), leaving the query visible ("the input text should remain visible, but not in focus").
  - **In a search app bar** the collapsed field is `surface-container` (`surface-container-highest` once content scrolls under the bar) — the spec's "Search container: surface container" — and is `max(min(100%, 312px), 50%)` of the free space, at most 720px ("fill 100% … until it reaches 312dp. Then … 50% of that space").
- **Deviations / not in v1:** no predictive back, and the docked view without a gap isn't offered. The content is any node; with Lists built, the suggestion list is composed from them.

### Badges and dividers (built, Tier 3)
- `Badge`: no children = Compose's small 6px dot; children = the large badge (16px tall, 16 to 34px wide, full corners, 4px side padding, `label-small`), both `error` / `on-error` (`BadgeTokens`).
  - **Length** (m3.material.io, 2026-10-13: "four characters, including a +", "16x34dp" at most): numeric children are formatted for the locale and capped at `max` (999, so "999+"); a count is laid out left to right (`dir="ltr"`) so it reads "999+", never "+999", in right-to-left layouts; a text badge stops at 34px and truncates longer text (a capped count is never truncated, since "999+" in `label-small` is a pixel wider than 34px).
  - **Announced** (the spec's accessibility tab): a count is read as part of the text around it, a small badge reads "New notification" (`labels.newNotification`, visually hidden text), and `label` replaces either ("3 unread messages", the visible content then hidden). An anchor with its own `aria-label` (an icon button) hides the badge's text, so that label carries the meaning ("Messages, 12 unread"). The spec reads the badge after the destination's name; navigation items take it through their `badge` prop, which hides the badge and describes the item with it (see Navigation), so the story and site examples use that prop (2026-10-13; the story had put a `BadgedBox` in the item's `icon`, where the count was never announced).
- `BadgedBox` (`badge`, anchor as `children`) places it like Compose's `BadgedBox`: a small badge starts 6px inside the anchor's end with its top on the anchor's top; a large one starts 12px inside the end with its bottom 14px below the anchor's top (so it hangs 2px above and past the end).
  - **No positioning:** the anchor and a zero-size box share one grid cell; the box sits at `margin-inline-start: calc(100% − offset)` and bottom-aligns the badge (flex `items-end`), so the badge overflows it without changing the anchor's size, and mirrors in RTL. Compose's badge rulers (clamping to an outer bound) aren't ported.
  - A bare SVG anchor gets Compose's default 24px icon size; other sizes go in a sized wrapper.
- `Divider`: `orientation` = `horizontal | vertical`, `inset` = `none | start | middle` (16px at the start or both ends, from m3.material.io; Compose leaves insets to padding), `decorative` (role `none`). 1px of `outline-variant` (`DividerTokens`), drawn as the background clipped to the content box so insets are padding and the root keeps no margins. It is a `div` with `role="separator"`, since an `<hr>` can't take a vertical orientation.
- `LabeledDivider` (2026-10-13, the spec's divider with supporting text): a horizontal `Divider` with text 4px below it and 8px clear at the end and below (padding, not margins). The spec names no type role for the text; it is `label-small` `on-surface-variant`. `inset` insets the line and the text alike.

### Lists (built, Tier 3)
- `List` with `ListItem` children (collection elements read like React Stately's `Item`, identified by `key`; `ListItem` has its own `getCollectionNode` so `childItems` can nest items while `children` stays the headline): `variant` = `standard | segmented`; items take the headline as `children`, `overline`, `supportingText`, `leading`, `trailing`, `href`, `textValue` and `childItems`. A name is required by the types.
- **Forms** (the spec's web roles, 2026-10-13):
  - **List box** (`selectionMode` without `onAction` or links): `useListBox` / `useOption`, `listbox` / `option` with `aria-selected`, as the spec's single- and multi-select lists ask on the web. Options can't hold interactive content (a development warning says so); give the list `onAction` to keep separate trailing actions.
  - **Grid list** (`onAction`, or links with `onAction`): `useGridList` / `useGridListItem`, ← / → into trailing controls (following the DOM direction via `DomDirectionLocale`), with selection too when `selectionMode` is also set (multi-action lists).
  - **Tree grid** (any item with `childItems`): `useTreeState` / `useTree` / `useTreeItem`, the spec's expand and collapse ("List items containing other list items can expand and collapse in a folder-like manner"). `expandedKeys` / `defaultExpandedKeys` / `onExpandedChange`. A press on an item without `onAction` or selection toggles it; → / ← expand and collapse; a trailing chevron button (out of the Tab order, 48px target) toggles it too and turns over on the fast spatial spring. Nested items are indented 16px per level (`--m3-list-level`; the spec gives no value) and get `aria-level` / `aria-posinset` / `aria-setsize`. React Aria's tree item reads siblings through `collection.getChildren`, which React Stately's legacy `TreeCollection` lacks, so the row gives the collection the nested order for the duration of that hook. The spec's expand token set isn't published (not in Compose either). **Nested items open and close** (2026-10-13, the spec: "To expand a list item, display a parent-child transition"): each row sits in a wrapper whose height opens and closes (grid rows `0fr ↔ 1fr`) on the default spatial spring while it fades on the default effects spring, only the fade under reduced motion. Rows added after the first render open in (`data-appear` + `@starting-style`); rows that leave the tree (a collapsed item's nested rows) stay in their old place as an `inert`, `aria-hidden` picture of the row at rest (`data-exiting`) until their transitions finish (`getAnimations()`), then go. Before, nested items appeared and disappeared at once.
  - Otherwise a plain `ul` of `li`s that nothing focuses. **Lists of links** stay real anchors in that `ul`, each a Tab stop, and ↑ / ↓ move focus between the links, wrapping, with Home / End to the first and last (2026-10-13, the spec: single-action lists "navigate within the list using arrow keys"); disabled items have no link and are skipped, and a control in an item keeps its own keys.
  - In every interactive form ↑ / ↓ move between items and **wrap at the ends** (the spec's keyboard table; `shouldFocusWrap`), with type-ahead, `selectedKeys` / `onSelectionChange` / `disabledKeys`. This covers Compose's clickable, selectable and checkable `ListItem` overloads and `SegmentedListItem`.
- **Sections** (`ListSection`, 2026-10-13): a labelled group of items under a subheader (`title`, or `aria-label` when it shows none; one of them is required by the types), identified by `key` like its items; its `getCollectionNode` yields a React Stately section, so the collection hooks handle it. Items take their position (segmented corners, dividers) within their section, and runs of items outside sections form their own groups.
  - **No type checks** (2026-10-13): `List` never compares a child's element type. A plain list renders its entries, each inside a `ListEntryContext` that gives its index, its position and whether a section holds it; `ListItem` and `ListSection` render themselves from it (they render nothing elsewhere). A section hands its own items their positions within it, and tells the list it's a section from a layout effect (`registerSection`), so the loose items around it become their own groups before the first paint; on the server, and in the first client render, every top-level entry counts as an item, so a list that mixes loose items and sections can show square-cornered neighbours until it hydrates. A radio list renders its entries the same way (`RadioListContext`): an item checks its own `value`, and a section refuses to render there. Interactive lists keep React Stately's collection builder, which reads each child through its `getCollectionNode`; the list reads the built collection (`useCollectionScan`) for its kind, its disabled keys and the control and `childItems` checks. A section or item created in a Server Component reaches the client with a lazy type; React resolves it when rendering, so nothing reads React's internals.
  - **Roles:** in a plain list a section is an `li` holding the subheader and a nested `ul` named by it; in a grid list a `rowgroup` named by it, starting with a header `row` holding a `rowheader` (React Aria's `useGridListSection`, as its `GridListSection`); in a list box a `presentation` wrapper, the subheader and a `group` of options (`useListBoxSection`). An `aria-label` names the group instead of the subheader.
  - **Keyboard:** ↑ / ↓ move from the last item of one section to the first of the next (React Aria's list keyboard delegate skips the section nodes), still wrapping at the ends of the whole list, with type-ahead across sections.
  - **Subheader:** 48px tall, `title-small` `on-surface-variant`, 16px from each side so its text lines up with the headlines (logical padding, so it mirrors in RTL). **Flagged:** the M3 spec and its tokens (`md.comp.list.*`) define no list subheader; this follows the deprecated navigation drawer's section headline. Segmented sections without a subheader stand 16px apart.
  - **Not in** radio lists or lists with `childItems` (both throw an error naming the alternative).
- **Selection cue:** selected items show a 20px check at their end besides the `secondary-container` colour ("don't rely on color as the only visual cue"); `selectionIndicator={false}` removes it.
- **Values** (Compose `ListItem.kt` interactive overloads, `ListItemDefaults`, `ListTokens`):
  - Padding 16px start / end, 10px top / bottom; 12px between leading content, the text and trailing content. **The 12px belongs to the leading and trailing cells** (their `me-[12px]` / `ms-[12px]`; the grid has no column gap), which render only when there's content, so a text-only item's text spans 16px to 16px (2026-10-13, the spec's "label left padding 16dp" for text-only and one-sided items; the grid's gap had kept 12px beside empty columns). A tree row's trailing cell exists only for a selection check or a chevron.
  - Heights: at least 56px (one line), 72px (overline or supporting text) and 88px (both). Three-line items align to the top, the others to the centre (Compose's breakpoint). Compose also treats a multi-line supporting text as three lines; that needs measuring and isn't done.
  - Type and colour: headline `body-large` `on-surface`; supporting `body-medium`, overline `label-small`, leading content (`title-medium` for avatar letters, 20px icons: the Expressive `ItemLeadingIconExpressiveSize`) and trailing content (`label-small` text, 20px icons) `on-surface-variant`. Selected items are `secondary-container` with `on-secondary-container` content; disabled content `on-surface` 38%. Segmented items are `surface` (`ItemSegmentedContainerColor`), so segmented lists usually sit on a `surface-container` background. **Deviation:** standard items are transparent rather than `ItemContainerColor` (`surface`), so a list takes the colour of its sheet, card or pane; in Compose consumers override the colour for that.
  - **Shapes:** Compose's precedence is pressed, then selected or focused (all 16px), then hovered (12px), else 4px. They're computed into one `data-shape` (`rest | hovered | active`), so no two rules compete, and morph on the fast spatial spring while colours change on the default effects spring. Segmented lists are 2px apart and round the outer corners of the first and last items to 16px at rest (`data-position`), as `segmentedShapes` does. Static items in a standard list have no corners.
- **Media** (Expressive tokens): `ListItemImage` 56px with 8px corners (`ItemLeadingImageExpressiveShape`), `ListItemVideo` 100 × 56px or 114 × 64px (large) with 8px corners, and `ListItemAvatar` (the spec's leading avatar): 40px, round, `primary-container` / `on-primary-container`, `title-medium` initials (hidden from assistive tech) or a photo cropped to fill.
- **Not in v1:** drag-to-reorder and its dragged state (`ReorderListTokens`, `ItemDraggedContainerExpressiveShape`; deferred until reordering lands) and swipe-to-reveal (Android Views only in the spec).

### Sliders (built, Tier 3)
- `Slider` (`value` / `defaultValue` / `onChange` / `onChangeEnd`, `centered`, `startIcon`, `endIcon`) and `RangeSlider` (`[start, end]`, `thumbLabels`), sharing `size` = `xs | sm | md | lg | xl`, `orientation`, `minValue` / `maxValue` / `step` (React Aria's 0–100 by 1), `ticks`, `disabled`, `showValueLabel`, `formatOptions` and `name`. Built on React Aria `useSlider` / `useSliderThumb` (hidden range inputs, arrows, Page Up / Down, Home / End), following the DOM direction via `DomDirectionLocale`. A name is required by the types.
- **Sizes:** Compose's code ships one size (16px track, 44px handle). The Expressive sizes come from the M3 token values in Material Components Android (`m3_comp_slider_{xsmall…xlarge}_*`), generated from the same token database: track 16 / 24 / 40 / 56 / 96px, corner 8 / 8 / 12 / 16 / 28px, handle 44 / 44 / 52 / 68 / 108px, inset icons 24 / 24 / 32px (md, lg, xl). **The medium handle is 52px**, as the M3 spec's measurements table states (2026-10-13; the MDC token value of 44px had been used before).
- **Theme scoping:** the disabled handle's composite (`on-surface` 38% over `surface`) mixes `var(--md-sys-color-*)`, never Tailwind's `var(--color-*)` aliases, which resolve once at `:root` and ignored a `ThemeScope` or dark mode (2026-10-13; a unit test bans the aliases in slider styles, and an e2e test checks the colour in a dark scope).
- **Values** (Compose `Slider.kt`, `SliderTokens`): active track and handle `primary`, inactive track `secondary-container`; a 4px handle that narrows to 2px while pressed, dragged or keyboard-focused (not after a pointer release that leaves it focused; M3 spec, 2026-10-13); a 6px gap each side (10px while keyboard-focused, Compose's inset focus ring padding); 2px inside corners; 4px stop indicators a corner's length from the ends, and ticks. **Stop indicator and tick colours follow the live m3.material.io token table** (sliders specs, "Tokens & specs", read through Playwright on 2026-10-13): on the active track `on-primary` ("Slider active stop indicator container color", opacity 1), on the inactive track and at the end `on-secondary-container` ("Slider inactive stop indicator container color", opacity 1); disabled, `inverse-on-surface` on the active track and `on-surface` at 38% on the inactive one ("Slider disabled active / inactive stop indicator container color"; the table's only disabled opacity, 0.38, is in its deprecated group, so it is applied to the `on-surface` dot, which was 38% before, and not to the `inverse-on-surface` one). Until then they followed Compose's code (`Slider.kt:1729-1731`: `secondary-container` on the active track, `primary` on the inactive one), which ignores Compose's own tokens. Enabled dots keep at least 3:1 against their track in light and dark (an e2e contrast check). Disabled: active `on-surface` 38%, inactive 12%, handle `on-surface` 38% over `surface`.
- **Track drawing** ports `SliderDefaults.drawTrack` and `SliderImpl`'s placement as CSS length expressions (`slider-geometry.ts`, unit-tested): discrete values sit between the corners (except at the ends); segments draw only past Compose's thresholds, done with `min(len, max(0, (len − threshold) × 10⁴))`; the centred track leaves a plain 6px gap at the centre; range and centred tracks have stops at both ends; ticks under a thumb, at the centre, or replaced by a stop are left out. Because it is all CSS on the custom properties, the first server render is exact and resizing needs no measuring.
- **Layout:** the track is one grid cell; segments, ticks, thumbs and the value indicator are placed with logical margins (`margin-inline-start`, `inline-size`), so nothing is positioned (the layout-safety check now ignores visually hidden inputs). A vertical slider writes its track with `writing-mode: vertical-lr` + `direction: rtl`, so the inline axis runs bottom to top and the same geometry and logical radii serve both orientations and RTL. Vertical sliders run bottom to top (Compose's `reverseVerticalDirection = true`) and default to 240px tall; horizontal ones fill the width.
- **Inset icons** follow MDC (`BaseSlider`): the start icon 10px inside the active track's start, the end icon 10px inside the inactive track's end (replacing the stop indicator), each shown only when its segment fits it plus 20px; `on-primary` / `on-secondary-container`. **When the active track is too short for the start icon, it moves to the inactive track** (M3 spec: "the icon moves to the inactive track"; 2026-10-13): a copy placed on the track 10px after the inactive segment's start, sized by the complement of the active copy's CSS condition, so exactly one shows and nothing is measured. Centred sliders ignore inset icons, and so do XS and S sliders, with a development warning (M3: "Avoid adding inset icons to XS or S"; 2026-10-13, they had rendered unsized), and a vertical `RangeSlider` warns in development (M3: "Don't use inset icons on centered or range sliders", "Avoid using range sliders vertically").
- **Keyboard:** besides React Aria's arrows, Page Up / Down and Home / End, an arrow with **Space held** steps by the page size (M3 spec: "Space & Arrows — … by one interval"; 2026-10-13), as Shift + arrow already does.
- **Value indicator** (`showValueLabel`): while dragging or keyboard-focused, a 44px `inverse-surface` pill with `label-large` `inverse-on-surface` text, 12px above the handle (left of a vertical one), from `ValueIndicator*` tokens. Compose's default slider has none.
- **Deviations:** pressing the track maps linearly to the value (React Aria) while discrete thumbs are drawn between the corners, so a press near the ends of a discrete track can land one step off Compose; no haptics.

### Sheets (built, Tier 3)
- `SheetTrigger` (trigger + sheet, `open` / `defaultOpen` / `onOpenChange`, like `DialogTrigger`), `BottomSheet` (`variant` = `modal | standard`) and `SideSheet` (`variant` = `modal | standard`, `detached`, `title`, `onBack`, `actions`, `footer`, `footerDivider`, `divider`). Modal sheets are `useModalOverlay` + `useDialog` dialogs portalled through `Overlay`; children, `actions` and `footer` may be functions of `{ close }`. Names: `aria-label` / `aria-labelledby`, or a side sheet's `title`. Announced words are in `labels` (bottom: `expand`, `collapse`, `dismiss`, `close`; side: `close`, `back`), with English defaults; they replaced the bottom sheet's `expandLabel` / `dismissLabel` (2026-10-13).
- **Bottom sheet values** (m3.material.io, Compose `ModalBottomSheet.kt`, `BottomSheet.kt`, `SheetDefaults.kt`, `SheetBottomTokens`): at most 640px wide, centred; a **72px top margin, and above 640px a 56px top margin and 56px side margins** (m3.material.io specs, 2026-10-13; until then a full sheet reached the top of the window); 28px top corners; `surface-container-low` at **level 1** (`DockedModalContainerElevation`, a shadow since 2026-10-13); a 32 × 4px `on-surface-variant` handle with 22px above and below; a 32% scrim on the default effects spring. It shows on the default spatial spring and hides on the **fast spatial** spring, since the exit moves the sheet and position moves on spatial springs (m3.material.io motion, 2026-10-13; it used Compose's fast effects `hideMotionSpec` before). The exit travels **112% of the sheet's size** (side sheets too), so the spring's overshoot (about 9.5% of the distance on the expressive fast spatial spring) settles out of view: m3.material.io's exits leave the screen for good, and with a 100% exit the sheet sprang a few pixels back into the window before unmounting (2026-10-13). A unit test checks the distance against every scheme's fast spatial spring, and an e2e test samples the exit frames.
- **Standard bottom sheet** (`variant="standard"`, 2026-10-13, m3.material.io: "Two variants: standard and modal", and Compose's `BottomSheetScaffold`): no scrim, no focus containment, nothing hidden from assistive tech and focus isn't moved, so the page stays usable; the panel is a non-modal `role="dialog"`. It renders in place (not portalled), `fixed` to the bottom of the window below every overlay (`--md-sys-z-sticky`); `classNames.container` can place it differently, e.g. `absolute` in a bounded region. It is open by default and rests collapsed at `peekHeight` (56px, Compose's `SheetPeekHeight`); the handle (press, Enter / Space, or a drag) expands and collapses it, Escape inside it collapses it, and it never closes itself (`open` hides it).
- **Detents:** like Compose's legacy anchors, a modal sheet taller than half the window opens to half (`PartiallyExpanded` at window / 2) and can expand to its full height (up to the top margin); shorter sheets open fully. `skipPartiallyExpanded` opens fully.
- **Handle and dragging:** the handle is a button. Pressed (or Enter / Space), it expands a half-open or collapsed sheet, collapses a full standard one and closes a full modal one, as Compose's handle click does; its label says which. Dragging it moves the sheet (pointer capture after 4px, no transition while dragging) and releasing settles with Compose's `AnchoredDraggableState` rules (`sheet-settle.ts`, unit-tested): a fling over 125px/s goes to the next anchor in its direction; otherwise the sheet moves on after 56px and springs back if not; settling past the bottom closes a modal sheet. **Without a handle** (`dragHandle={false}`) a drag starting in the top 48px of the sheet still moves it (m3.material.io accessibility, 2026-10-13).
- **Dragging from the content** (2026-10-13; m3.material.io lists "swiping down" among the ways to dismiss a sheet): a touch or pen drag that starts on the content moves the sheet when it heads down (more vertical than sideways, past the 4px slop) while the content, and any scroller between it and the touch, is at its top; it then drags, settles and dismisses exactly as the handle does (`settleTarget`), with the same transitions, so reduced motion applies alike. An upward drag, or any drag while the content is scrolled, scrolls the content, and a mostly sideways drag is left to horizontal scrollers and text. The first decision holds until the pointer lifts (`sheet-gesture.ts`, unit-tested). Drags starting on form fields or on elements with `touch-action: none` (sliders, nested sheets) are ignored, and mouse drags select text as on any page. Mechanics: the panel listens in the capture phase (pressable content stops its pointer events bubbling) and captures the pointer once dragging, which cancels the press underneath; while the content is at its top it is `touch-action: pan-x pan-down pinch-zoom`, so the browser only scrolls it for upward and sideways moves and a downward one stays a pointer gesture; a non-passive `touchmove` listener cancels a drag's moves for browsers without `pan-down` (iOS Safari), and `overscroll-behavior: contain` stops rubber-banding and scroll chaining. Playwright drives real touch gestures through CDP for drag-to-dismiss, scrolling back, an upward scroll and a horizontal scroller.
- **Close affordance:** while a sheet fills the window up to its top margin, a close button (modal) or a collapse button (standard, "a collapse icon … to return to their initial position") shows at its top end (m3.material.io guidelines, 2026-10-13). `closeButton={false}` hides it; `closeIcon` / `collapseIcon` replace the icons.
- **Dismissal:** a press on the scrim closes a modal sheet (Compose's `animateToDismiss`); Escape behaves like the back button (`settleToDismiss`): a fully open sheet with a half detent returns to half, otherwise it closes.
- **Side sheets** aren't in Compose; values follow m3.material.io and Material Components Android (`m3_comp_sheet_side_*`): 256px wide and **at most 400px** (m3.material.io's maximum, 2026-10-13: a consumer width stops there, and at the window's width); modal `surface-container-low` at level 1 with 16px corners on its free (start) edge over a 32% scrim, sliding in from the end edge (mirrored in RTL); detached sheets (modal or standard) float 16px from the edges with 16px corners all round; standard sheets are `surface`, level 0, no corners, with an `outline-variant` divider on their content edge (`divider`, default on; not when detached), and sit in the layout, opening and closing their width on a grid track (`0fr ↔ 1fr`, default spatial) and becoming `inert` while closed. They use the bottom sheet's springs rather than MDC's 275ms tween.
  - **Role:** both variants are dialogs (m3.material.io: "The accessibility role for a side sheet is Dialog"); the standard one is non-modal (no `aria-modal`, focus isn't moved). Until 2026-10-13 the standard sheet was a role-less `div`.
  - **Header:** an optional back button (`onBack`, `labels.back`, `backIcon`, mirrored in RTL), a `title-large` `on-surface-variant` headline, then `actions` and **a built-in close button** (`labels.close`, `closeIcon`), in a 72px row with 24px start padding (16px with the back button), 12px end padding and 12px between parts. m3.material.io requires the close affordance in every side sheet, so it is always shown (2026-10-13); this supersedes decision #11's "no bundled icon" for this button, which ships the Material Symbols "close" path as the dialog's full-screen header does. Content has 24px sides.
  - **No horizontal scrolling** (m3.material.io: "Side sheets cannot scroll horizontally", 2026-10-13): the content scrolls vertically and clips anything wider (`overflow-x-hidden`); `overflow-y-auto` alone let it scroll sideways.
  - **Bottom actions** (`footer`): at least 72px, 16px above and 24px below, 24px sides, start-aligned with 8px between buttons; `footerDivider` adds an `outline-variant` divider above it (m3.material.io anatomy and specs, 2026-10-13).
- **Motion and layout safety:** sheets move by `translate` on a library-owned wrapper; the consumer's `className` and `style` go on the panel. The in-flow standard side sheet runs the layout-safety matrix.
- **Not in v1:** predictive back, and detents beyond half / full (modal) or peek / full (standard).

### Carousel (built, Tier 3)
- `Carousel` with `variant` = `multi-browse | uncontained | multi-aspect | hero | full-screen`, `orientation` (vertical by default for full-screen), `preferredItemSize` (multi-browse 186px by default, hero the whole carousel), `itemSize` (uncontained, 240px), `itemSpacing` (8px; 16px full-screen), `heroAlignment` = `start | center`, `minSmallItemSize` / `maxSmallItemSize` (40 / 56px), `contentPadding` (`{ start, end, cross }`), `snap` = `none | item` (uncontained and multi-aspect), `onAction(index)`, `disabledIndexes` and `labels` (`slide(position, count)`, numbers formatted in the locale). Children are the items (any elements, usually images), each filling its slot. The consumer gives the carousel its cross-axis size. It is a `region` with `aria-roledescription="carousel"` and a required name; items are `group`s labelled "n of N" (`slide`).
- **Layouts** (the M3 Expressive spec's six, 2026-10-13): multi-browse and hero (centre-aligned with `heroAlignment="center"`) on keylines; **uncontained**: items of one size (`itemSize`) that flow past the end edge, never masked or resized (2026-10-13, from the spec: "items are a single size and flow past the edge of the screen … without the text being masked or cropped"; until then it used Compose's uncontained keylines, which shrank and cropped items that were fully on screen); **multi-aspect** (uncontained multi-aspect ratio): each item keeps its own width at the carousel's height, clamped between 9:16 and 16:9 (`--m3-carousel-cross-size`, measured), no keylines; **full-screen**: one edge-to-edge item per viewport (the slot is the scroller's size), 16px apart, no padding or corners, snapping to every item.
- **Padding** (spec, 2026-10-13): multi-browse and hero 16px before and after the items and 8px across; uncontained and multi-aspect 16px before only, 8px across; full-screen none. The cross padding is the scroller's. Along the carousel, keyline layouts handle it as Compose does (`Strategy` with `beforeContentPadding` / `afterContentPadding`): the last start and end shift steps are shifted by the padding, and the shift distances are at least the padding, so items start inside it and scroll over it. The scroll range and snap positions don't change. Layouts without keylines (uncontained, multi-aspect, reduced motion) pad the scroller itself, with matching `scroll-padding`.
- **Small items stay 40–56px at the start and end** (2026-10-13, departing from Compose's maths to meet the spec: "Small carousel items have a minimum width of 40dp and a maximum width of 56dp"). Compose's `createShiftedKeylineListForContentPadding` takes an equal share of the padding from every item, so with 16px padding a 40px small item was 34.67px at the ends (360px multi-browse: 181 · 113 · 34.7). Here only the large and medium keylines give it up (those wider than `maxSmallItemSize`, passed to `createStrategy`), so the same carousel starts 178 · 110 · 40. The total taken is still the padding, so the anchors, snap positions and scroll range are unchanged; mid-scroll the keylines are the defaults, as before.
- **Keylines** are a TypeScript port of Compose's `carousel` package (`carousel-keylines.ts`, unit-tested): `Arrangement` (lowest-cost fit of large / medium / small items, the 10% medium flex), `multiBrowseKeylineList`, `heroKeylineList` (Compose's `uncontainedKeylineList` was dropped on 2026-10-13 with the uncontained keylines), keyline lists with pivots and cutoffs, `Strategy` (start / end shift steps and interpolation points, content padding), `getKeylineListForScrollOffset`, `getSnapPositionOffset` and `carouselItem`'s placement (keyline before / after the item's centre, interpolated size and offset, out-of-bounds offset). With 360px, 186px preferred and 8px spacing that gives 186 · 118 · 40, mirrored at the end, as Compose does.
- **Web rendering:** Compose drives a pager; here the carousel scrolls natively. Each item keeps a natural slot the size of the large item (so the scroll range is Compose's `calculateMaxScrollOffset`), and on every scroll frame a library-owned mask layer inside it is translated and clipped (`clip-path: inset(… round var(--m3-carousel-item-corner))`) to its keyline. The root and slots are never transformed; nothing re-renders while scrolling. `--m3-carousel-item-size` on each mask exposes the visible size (Compose's `carouselItemDrawInfo`) for parallax.
- **Reduced motion** (spec, 2026-10-13): items no longer change size as they scroll. Every item keeps the large size, unmasked and untranslated, so a hero carousel shows part of the next item; the docs ask for such carousels to reach the window's edges.
- **Snapping** (spec, 2026-10-13: "Hero carousels swipe through one item at a time. Multi-browse carousels scroll through many items at once."): hero and full-screen stop at every item (`scroll-snap-stop: always`, Compose's `singleAdvanceFlingBehavior`); multi-browse snaps with `snap-mandatory` but lets a fling cross several items; uncontained and multi-aspect scroll freely (`noSnapFlingBehavior`) unless `snap="item"`. Each keyline item's snap point is placed by `scroll-margin` from `getSnapPositionOffset`. Mouse drag scrolls (snapping pauses while dragging, and a drag never activates an item); touch and trackpads scroll natively. RTL reads the absolute scroll offset and mirrors the translation.
- **Keyboard and focus** (spec, 2026-10-13): the container is never focusable. Every item is a tab stop ("use Tab or the arrow keys to navigate the carousel items"); ←/→ (↑/↓ vertical, mirrored in RTL) move focus to the previous or next item and Home / End to the ends, and ↑/↓ (←/→ vertical) leave the carousel for the previous or next tabbable element, such as the "Show all" button the spec puts below it. A keyboard-focused item scrolls to its snap position (smoothly, instantly under reduced motion); a pressed one doesn't move. The focus ring is the item slot's outline with the item's corners (inside the edge for full-screen).
- **Item states** (with `onAction`): a press, Enter or Space activates an item (`useM3Interaction`). Hover, focus and the pressed ripple paint on a library-owned state layer (`on-surface`) sharing the mask's grid cell, over the item; a pressed item's corners tighten from `--m3-carousel-corner` (28px) to `--m3-carousel-pressed-corner` (20px, large-increased) on the fast spatial spring (`--m3-carousel-item-corner` is a registered `<length>`), the spec's "changes the shape slightly". Disabled items (`disabledIndexes`) are `aria-disabled`, at 38% opacity, and can't be activated.
- **Container colour** (2026-10-13, the spec's colour table: "Container — Surface"): each item's mask is `surface`, so transparent or still-loading content never shows what's behind the carousel.
- **Full-screen has no corners** (2026-10-13; it fills the window edge to edge): the variant sets `--m3-carousel-corner` and `--m3-carousel-pressed-corner` to 0 on the root, where they kept 28px before.
- **Corners and spacing:** items are masked with 28px (extra-large) corners, as Compose's samples use `maskClip(MaterialTheme.shapes.extraLarge)`; `--m3-carousel-corner` overrides it. Spacing defaults to 8px (m3.material.io; Compose's default is 0 and its samples use 8dp).
- **Deviations / not in v1:** no parallax helper, items aren't z-ordered by distance from the current item, and before hydration items render unmasked at the preferred size. The "Show all" button is the app's, as the spec places it outside the carousel.

### Date and time pickers (built, Tier 3)

## 10. Layout safety (consumer positioning never breaks a component)

**Principle:** a component's internal visuals never depend on the root element's `position`, `overflow`, `display` or `transform`. Consumers may put any layout class on any component — e.g. `<Button className="fixed bottom-4 right-4">` — and it must look and behave the same.

### Failure modes this prevents
- `static` on a root that relied on `relative` → absolutely-positioned state layer escapes and covers the parent/page.
- `overflow-visible` → ripple spills outside rounded corners.
- Motion animating the root's `transform` → fights consumer `translate`/`rotate`/`style.transform`, and turns the component into the containing block for any `fixed` descendant.
- `className` landing on an inner element of a multi-part component → `fixed` moves only part of it.

### Rules
1. **`className` and `style` always go on the outermost element.** Layout utilities apply to the whole component. `style` is merged, never replaced.
2. **State layer and ripple are painted as background layers on the root**, not as absolutely-positioned children: state layer = `linear-gradient` overlay using state colour × state opacity token; ripple = `radial-gradient` animated via registered `@property` custom properties. They follow `border-radius` automatically and need neither `relative` nor `overflow-hidden`. Components add their own transitions (corners, colours, elevation) through the `--m3-transition-{property,duration,easing,delay}` lists, which the `container-motion` utility fills. Setting `transition-*` directly would cancel the state layer's transitions.
3. **Unavoidable inner overlays** (FAB morph shape, badges, touch targets) live inside a library-owned inner wrapper with its own `relative`/clipping. Consumer classes go on the outer element.
4. **Motion never animates the root's `transform`.** Springs, press-scale and morph run on inner layers. One exception (2026-10-13, for the spec's FAB appear / disappear and toolbar exit-on-scroll motion): a FAB or toolbar hidden with `visible={false}` (or a FAB appearing with `appear`) scales or slides through the root's `transform` property, set only while hidden or appearing, so at rest the root has no transform and traps no `fixed` children. It uses `transform` only, never the `translate` / `scale` / `rotate` properties that Tailwind's utilities set, so consumer positioning classes compose with it.
5. **Containers never trap `fixed` children.** Card, Dialog content, Sheet etc. never put `transform`, `filter`, `backdrop-filter`, `contain` or `will-change: transform` on their root.
6. **Focus ring = CSS `outline` (+ `outline-offset`)**, so `overflow-hidden`, `fixed` or clipping ancestors can't hide it.
7. **Layout-neutral roots**: no outer margins, no own `z-index`, no own positioning. Overlays portal to `body` with a z-index token scale (`--md-sys-z-*`) consumers can override.
8. **`cn()` conflict resolution** guarantees the consumer's layout class wins whenever the library does set a conflicting one.

### Verification
An **override matrix** in CI: every component rendered with `fixed`, `absolute`, `sticky`, `static`, `overflow-hidden`, `overflow-visible`, `w-full`, a transform, inside a transformed ancestor, and in RTL — Playwright visual snapshots plus interaction checks. Each component gets a `LayoutOverride` story (`apps/docs`) and a Playwright test that checks layout size, the background state layer, corner radius, the absence of positioned children, pressing and the keyboard focus ring for every combination.

  - **Hooks** (`use*`) run only in client components.
  - **Client-only by their props:** functions (event handlers, render-function children, label functions) and class instances (a `SnackbarHostState`, `@internationalized/date` values) can't cross from a Server Component. ### Releasing (2026-10-13)

Only `@windmorph/react` is published to npm. `@windmorph/test-utils`, Storybook, the playground and the site are private workspace packages, and Windmorph Pro is published from its own repository. Versions and changelogs come from Changesets (`.changeset/`): every user-visible change adds a changeset (`pnpm changeset`).

- **Package metadata:** `repository` (with `directory`), `homepage`, `bugs`, `keywords` and `publishConfig` (`access: public`, `provenance: true`). The tarball holds `dist` (ESM, `.d.ts`, the CSS entry points, the CLI with its shebang, and source maps that embed their sources, since `src` isn't published), `NOTICE`, `README.md` and the root `LICENSE`, which pnpm adds. There is no `engines` field: Node 24 is the repo's toolchain, and consumers' requirements come from the peer dependencies. To check a release candidate, run `pnpm --filter @windmorph/react pack`, then `npx publint` and `npx @arethetypeswrong/cli --profile esm-only` (leaving out the CSS entry points) on the tarball.
- **Workflow** (`.github/workflows/release.yml`, on every push to `main`): Changesets' `select-mode` picks one of three modes.
  - *version*: pending changesets exist, so it opens or updates the "chore(release): version packages" pull request (bumped version, `CHANGELOG.md`, changesets removed).
  - *publish*: no pending changesets, and the package's version isn't on npm yet. The `pack` job runs CI's checks (format, traces, `turbo run build typecheck lint test`, with Windmorph Pro installed through `PRO_READ_TOKEN`) and packs the tarball with `pnpm pack`. The `publish` job publishes it with `pnpm publish` and npm provenance, then pushes a `@windmorph/react@<version>` tag and a GitHub release. Only `publish` has `id-token: write`, and it runs in the `npm` GitHub environment, where required reviewers can gate releases.
  - *none*: nothing to do.
- **A release:** merge pull requests that carry changesets → merge the release pull request the workflow opens → that merge publishes. The release pull request is opened with `GITHUB_TOKEN`, so CI doesn't start on it by itself: close and reopen it (or push to its branch) to run the checks before merging.
- **Authentication:** npm trusted publishing (OIDC) once it's configured for `@windmorph/react` on npmjs.com (repository `XManhTrinh/windmorph`, workflow `release.yml`, environment `npm`); npm then adds provenance automatically. Until then, the **`NPM_TOKEN`** secret: a granular access token with read and write access to the `@windmorph` scope (allowed to bypass two-factor authentication if the account requires it for publishing), written to the runner's `~/.npmrc`, since pnpm doesn't read tokens from environment variables in a project `.npmrc`. Once trusted publishing works, delete `NPM_TOKEN` and set the package to require two-factor authentication and disallow tokens.
- **Repository settings:** Actions → General → "Allow GitHub Actions to create and approve pull requests" must be on; `NPM_TOKEN` is a secret of the `npm` environment (or of the repository); `PRO_READ_TOKEN` as for CI.
- **0.1.0, the first publish:** the package is already at 0.1.0, and the pending changesets are dropped when the 0.1.0 work is squashed into one release commit, so 0.1.0 has no version pull request. When that commit reaches `main`, `select-mode` finds no changesets and no 0.1.0 on npm, and the workflow publishes 0.1.0 directly (`pnpm changeset publish-plan` shows the plan locally). Before that merge, the `@windmorph` scope must belong to the publishing npm account or organisation, and `NPM_TOKEN` (or a trusted publisher, which must publish within two days of being created) must be in place. Later releases go through changesets and the release pull request.
- **Manual fallback:** the root `pnpm release` script (build, then `changeset publish`) publishes from a local checkout; such a publish carries no provenance.
